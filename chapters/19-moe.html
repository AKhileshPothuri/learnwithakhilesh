25 Mixture of Experts (MoE)

25.1 The Core Intuition

Think of a dense transformer FFN as a single massive generalist employee who handles every question that comes in — they must be good at coding, math, French, legal reasoning, and everything else simultaneously. A Mixture of Experts model instead hires a team of specialists: one expert for code, one for math, one for multilingual tasks, one for factual recall. When a question comes in, a smart router decides which one or two specialists to consult rather than taxing everyone.

The clever engineering insight: you only pay the compute cost of the specialists you consult, but you get to hire as many specialists as you want. Storage is cheap; computation is expensive. MoE exploits this asymmetry directly.

More precisely: a MoE model replaces the feed-forward network (FFN) sublayer inside each transformer block with a bank of E parallel expert FFNs, plus a gating network that routes each token to only the top-k experts. The critical word is “only” — in a dense model, every token activates all the parameters of the FFN. In a sparse MoE, a token with k=2 activates exactly 2 of the E experts regardless of how large E is. This is sparse activation — the mechanism that decouples total parameter count (all experts combined) from active parameter count (the k experts used per token), and it is the source of every MoE tradeoff that follows.

Warning

Common Misconception: “MoE is just model ensembling.” Wrong. Ensembling runs multiple full models and averages results — the cost scales linearly with the number of models. MoE routes each token to a tiny fraction of experts with a single forward pass. The experts share embedding layers, attention layers, and are trained jointly. MoE is a single model with a conditional execution pattern, not an ensemble.

25.2 How MoE Works: The Mechanics

25.2.1 The Gating Network

The router is a small learned linear layer followed by softmax. For each token’s hidden state h ∈ ℝ^d after the attention sublayer, the router computes:

logits = W_r · h        where W_r ∈ ℝ^{E × d}
probs  = softmax(logits)
selected = top-k(probs)
output = Σ_{i ∈ selected} (p_i / Σ_{j ∈ selected} p_j) × FFN_i(h)

For a model with hidden dimension 4096 and 8 experts, W_r has only ~32K parameters — negligible compared to the expert FFNs. The gating computation adds essentially no FLOP cost; the bottleneck is expert FFN computations and, at scale, the communication needed to dispatch tokens to the right experts.

import torch
import torch.nn as nn
import torch.nn.functional as F

class MoELayer(nn.Module):
    """
    Minimal MoE FFN layer illustrating top-k routing.
    In production (Mixtral, DeepSeek), this is much more optimized.
    """
    def __init__(self, d_model: int, d_ffn: int, num_experts: int, top_k: int = 2):
        super().__init__()
        self.num_experts = num_experts
        self.top_k = top_k

        # Router: small linear projection
        self.router = nn.Linear(d_model, num_experts, bias=False)

        # Expert FFNs — each is a standard two-layer FFN
        self.experts = nn.ModuleList([
            nn.Sequential(
                nn.Linear(d_model, d_ffn),
                nn.SiLU(),
                nn.Linear(d_ffn, d_model),
            )
            for _ in range(num_experts)
        ])

    def forward(self, x: torch.Tensor):
        # x: (batch, seq_len, d_model)
        B, T, D = x.shape
        x_flat = x.view(-1, D)  # (B*T, d_model)

        # Router scores
        router_logits = self.router(x_flat)          # (B*T, num_experts)
        router_probs  = F.softmax(router_logits, dim=-1)

        # Top-k selection
        top_k_probs, top_k_indices = torch.topk(router_probs, self.top_k, dim=-1)
        # Normalize selected probs to sum to 1
        top_k_probs = top_k_probs / top_k_probs.sum(dim=-1, keepdim=True)

        # Dispatch: for each token, compute selected expert outputs and blend
        output = torch.zeros_like(x_flat)
        for k in range(self.top_k):
            expert_idx = top_k_indices[:, k]   # (B*T,)
            weight     = top_k_probs[:, k]     # (B*T,)
            for e in range(self.num_experts):
                mask = (expert_idx == e)
                if mask.any():
                    expert_out = self.experts[e](x_flat[mask])   # run expert
                    output[mask] += weight[mask].unsqueeze(-1) * expert_out

        return output.view(B, T, D)

    def aux_load_balancing_loss(self, router_logits: torch.Tensor, alpha: float = 0.01):
        """
        Switch Transformer auxiliary loss to prevent expert collapse.
        L_aux = alpha * num_experts * sum_i(f_i * p_i)
        f_i = fraction of tokens routed to expert i  (hard, non-differentiable)
        p_i = mean routing probability toward expert i (differentiable)
        """
        probs   = F.softmax(router_logits, dim=-1)          # (tokens, E)
        # Hard routing fractions (argmax assignment)
        one_hot = F.one_hot(probs.argmax(dim=-1), self.num_experts).float()
        f = one_hot.mean(dim=0)   # (E,)  -- non-differentiable fraction
        p = probs.mean(dim=0)     # (E,)  -- differentiable mean probability
        loss = alpha * self.num_experts * (f * p).sum()
        return loss

25.2.2 Expert Capacity and Token Dropping

Expert capacity is a practical constraint in batched execution. If you have 8 experts and 800 tokens in a batch, perfect load balance means each expert processes 100 tokens. But expert capacity sets a maximum — tokens exceeding this limit are dropped (their contribution to the output is zeroed; they fall back to the residual connection).

The capacity factor CF scales this limit:

capacity_per_expert = CF × (total_tokens / num_experts)

A CF of 1.25 allows 25% oversubscription. Setting CF too low causes dropped tokens and quality degradation. Setting it too high wastes GPU memory allocation.

def route_with_capacity(
    tokens: torch.Tensor,      # (T, d)
    router_probs: torch.Tensor,# (T, E)
    top_k: int,
    capacity_factor: float,
    num_experts: int,
):
    """
    Demonstrates capacity-based token dropping logic.
    Returns dispatched token assignments and drop mask.
    """
    T = tokens.shape[0]
    capacity = int(capacity_factor * T / num_experts)

    top_k_probs, top_k_indices = torch.topk(router_probs, top_k, dim=-1)

    # Per-expert token count tracker
    expert_counts = torch.zeros(num_experts, dtype=torch.long)
    assignments   = []   # list of (token_idx, expert_idx, weight)
    dropped       = []

    for t in range(T):
        for k in range(top_k):
            e = top_k_indices[t, k].item()
            if expert_counts[e] < capacity:
                assignments.append((t, e, top_k_probs[t, k].item()))
                expert_counts[e] += 1
            else:
                # Token t is dropped for expert e — falls back to residual
                dropped.append((t, e))

    drop_rate = len(dropped) / (T * top_k)
    print(f"Drop rate: {drop_rate:.2%} | Expert loads: {expert_counts.tolist()}")
    return assignments, dropped
Warning

Production Gotcha — Token Drop Rate: Monitor your token drop rate during training. Anything above 1-2% on validation data signals that your capacity factor is too low or your load balancing is failing. Systematic drops on specific input types (long documents, code) can cause subtle quality degradation that only shows up in domain-specific evals, not aggregate benchmarks. Add expert_drop_rate to your training metrics dashboard.

25.3 Router Design & Load Balancing

25.3.1 Top-1 vs. Top-2 Routing

Top-1 routing (select one expert per token) maximizes sparsity but produces high variance in routing decisions. A small perturbation in the hidden state can flip which expert is selected, making training less stable. Top-2 routing provides a weighted blend of two experts, smoothing gradients and generally producing better quality at the cost of doubled expert computation per token. Nearly all competitive MoE models (Mixtral, DeepSeek V2/V3) use top-2. Some research has explored k > 2, but the quality gains beyond k=2 are typically marginal relative to the compute cost.

Routing Active FLOPs Stability Quality Used By
Top-1 1× expert Lower Good Switch Transformer
Top-2 2× experts Higher Better Mixtral, DeepSeek V2/V3
Top-4 4× experts Highest Best GPT-4 (rumored)
Expert Choice Fixed per expert N/A (no drop) Research Google research

25.3.2 Expert Collapse: The Dominant Failure Mode

Expert collapse is a self-reinforcing positive feedback loop. A slightly stronger expert receives more gradient signal, becomes better, attracts more tokens, receives more gradients, becomes better still. Within a few thousand training steps, the distribution can be 80%+ concentrated on two experts. The remaining experts starve and become useless, and the MoE behaves like a model with far fewer actual experts — losing all the capacity benefits.

Detecting collapse: Monitor the fraction of tokens routed to each expert. Healthy routing shows roughly uniform distribution with standard deviation well below the mean. Collapsed routing shows one or two experts handling 80%+ of traffic.

import numpy as np
import matplotlib.pyplot as plt

def analyze_expert_routing(routing_counts: list[int]) -> dict:
    """
    Analyzes expert routing statistics.
    routing_counts: list of token counts per expert over evaluation set.
    """
    counts = np.array(routing_counts, dtype=float)
    total  = counts.sum()
    fracs  = counts / total

    stats = {
        "mean_frac":     fracs.mean(),
        "std_frac":      fracs.std(),
        "max_frac":      fracs.max(),
        "min_frac":      fracs.min(),
        "cv":            fracs.std() / fracs.mean(),      # coefficient of variation
        "top1_pct":      fracs.max() * 100,
        "top2_pct":      np.sort(fracs)[-2:].sum() * 100,
        "is_collapsed":  fracs.max() > 0.4,               # heuristic: any expert > 40% → collapse
    }

    print("=== Expert Routing Analysis ===")
    for e, f in enumerate(fracs):
        bar = "█" * int(f * 50)
        print(f"Expert {e:2d}: {f:.3f} {bar}")
    print(f"\nCV (coefficient of variation): {stats['cv']:.3f}")
    print(f"Top-1 expert load: {stats['top1_pct']:.1f}%")
    print(f"Top-2 expert combined: {stats['top2_pct']:.1f}%")
    if stats["is_collapsed"]:
        print("WARNING: Routing collapse detected!")
    return stats

# Example: healthy routing (8 experts, roughly uniform)
healthy_counts   = [120, 115, 125, 118, 122, 119, 121, 116]
analyze_expert_routing(healthy_counts)

# Example: collapsed routing
collapsed_counts = [480, 220, 40, 35, 50, 45, 60, 70]
analyze_expert_routing(collapsed_counts)

25.3.3 Auxiliary Load Balancing Loss

The standard fix is a differentiable penalty added to the training objective:

L_aux = α × E × Σ_i (f_i × p_i)

where f_i is the fraction of tokens routed to expert i (hard, non-differentiable), and p_i is the mean routing probability toward expert i (differentiable through softmax). Their product is a proxy for load imbalance that admits gradients.

The coefficient α is critical: - Too small (α < 0.001): collapse still occurs - Typical range: α ∈ [0.001, 0.01] - Too large (α ≥ 0.1): forces uniform routing, destroying specialization

Warning

The α Tuning Trap: The auxiliary loss creates a fundamental tension. It pushes the router toward uniformity, which prevents collapse but also prevents the specialization that makes MoE valuable. If you raise α to aggressively prevent collapse, you may end up with a model that routes tokens uniformly regardless of content — essentially a random router. You can detect over-regularized routing by measuring routing entropy: if it is near maximum (log E), your α is too high.

25.3.4 DeepSeek’s Auxiliary-Loss-Free Approach

DeepSeek V2 and V3 introduced an elegant alternative: per-expert bias terms added to routing logits.

class DeepSeekRouter(nn.Module):
    """
    Auxiliary-loss-free load balancing via per-expert bias update.
    Overloaded experts get their bias decreased, underloaded get it increased.
    No auxiliary loss term needed — quality is preserved.
    """
    def __init__(self, d_model: int, num_experts: int, top_k: int = 2):
        super().__init__()
        self.num_experts = num_experts
        self.top_k = top_k
        self.router = nn.Linear(d_model, num_experts, bias=False)
        # Bias terms for load balancing (not trained by gradient)
        self.register_buffer("bias", torch.zeros(num_experts))

    def forward(self, x):
        logits = self.router(x) + self.bias   # add bias to shift routing
        probs  = F.softmax(logits, dim=-1)
        top_k_probs, top_k_indices = torch.topk(probs, self.top_k, dim=-1)
        return top_k_probs, top_k_indices, logits

    @torch.no_grad()
    def update_bias(self, token_counts: torch.Tensor, target_per_expert: float, delta: float = 0.001):
        """
        Called after each forward pass.
        Decrease bias for overloaded experts, increase for underloaded.
        """
        fracs = token_counts.float() / token_counts.sum()
        target_frac = 1.0 / self.num_experts
        overloaded  = fracs > target_frac
        underloaded = fracs < target_frac
        self.bias[overloaded]  -= delta
        self.bias[underloaded] += delta

The DeepSeek approach avoids gradient-level interference with the routing signal — the router learns to be as discriminative as the task requires, while the bias correction prevents sustained collapse. DeepSeek V3’s benchmarks show better performance than models trained with auxiliary loss at equivalent scale.

25.3.5 Expert Choice Routing

Expert choice routing inverts the standard setup. Instead of each token choosing its top-k experts, each expert selects its top-k tokens from the batch.

Key properties: - Load balance guaranteed by construction — every expert processes exactly k tokens - No auxiliary loss needed - No token dropping

Drawbacks: - Some tokens may not be processed by any expert if k × E < total_tokens - Requires full batch visibility before routing — complicates streaming and autoregressive decoding - Less commonly used in generative models; more common in encoder models

25.5 MoE in Production

25.5.1 Memory vs. Compute: The Defining Tradeoff

Because the gating network might route any token to any expert during any forward pass, all experts must be loaded into GPU memory simultaneously. You cannot load experts on demand at inference time without millisecond-level latency spikes.

25.5.2 Expert Parallelism

Expert parallelism is the standard strategy at scale. Different GPUs host different experts. When the router assigns tokens to experts, tokens must be sent to the GPU hosting the target expert — requiring all-to-all communication.

Step 1: Router decides expert assignments for all tokens in batch
Step 2: All-to-all send: each GPU sends tokens to their target expert GPUs
Step 3: Each GPU computes its hosted expert FFN on received tokens
Step 4: All-to-all receive: each GPU receives results back
Step 5: Router reconstructs weighted sum and continues forward pass

All-to-all communication is expensive: bandwidth requirements scale with the number of experts and batch size, and it cannot be overlapped with computation as easily as tensor parallel communication.

NVLink vs. PCIe matters enormously for MoE:

# Rough latency model for expert dispatch
def expert_dispatch_latency_ms(
    batch_tokens: int,
    hidden_dim: int,
    num_experts: int,
    top_k: int,
    interconnect: str = "nvlink"   # "nvlink" or "pcie"
) -> float:
    bytes_per_token = hidden_dim * 2  # FP16
    tokens_dispatched = batch_tokens * top_k
    total_bytes = tokens_dispatched * bytes_per_token

    bandwidth_GB_s = 600 if interconnect == "nvlink" else 64  # A100 NVLink vs PCIe 4.0
    latency_ms = (total_bytes / 1e9) / bandwidth_GB_s * 1000

    print(f"Dispatch latency ({interconnect}): {latency_ms:.3f} ms")
    print(f"  Tokens dispatched: {tokens_dispatched:,}")
    print(f"  Data moved: {total_bytes / 1e6:.1f} MB")
    return latency_ms

# Single sequence, interactive inference
expert_dispatch_latency_ms(512, 4096, 8, 2, "nvlink")   # ~0.007 ms — negligible
expert_dispatch_latency_ms(512, 4096, 8, 2, "pcie")     # ~0.065 ms — 9x slower

# Large batch inference
expert_dispatch_latency_ms(32768, 4096, 8, 2, "nvlink")  # ~0.45 ms
expert_dispatch_latency_ms(32768, 4096, 8, 2, "pcie")    # ~4.2 ms  — noticeable at each of 32 layers
Warning

Production Gotcha — PCIe vs. NVLink for MoE: Consumer GPUs (RTX 4090) connect over PCIe. Enterprise GPUs (A100, H100) use NVLink. For a MoE model with 32 layers, each MoE layer requires two all-to-all operations. On PCIe at large batch sizes, communication can consume 30-50% of total step time. Always benchmark on your actual interconnect before committing to MoE serving infrastructure.

25.6 Fine-Tuning MoE Models

25.6.1 What Actually Changes During Fine-Tuning

Standard supervised fine-tuning updates all parameters: attention layers, router weights, and all expert FFN weights. The risk: fine-tuning on a small dataset can disrupt the routing patterns learned during pretraining. Expert specialization is an emergent property — different experts have developed affinity for code, multilingual content, numerical reasoning. Fine-tuning on a narrow dataset can collapse this specialization.

Monitor expert utilization distribution throughout fine-tuning. If you see routing collapsing, reduce learning rate or freeze router weights.

25.6.2 LoRA on MoE: Target Layer Strategy

LoRA applied to MoE models follows the same mechanics as dense models but target layer selection requires care.

from peft import LoraConfig, get_peft_model

# Strategy 3: Freeze router, fine-tune experts
# - Preserves routing structure from pretraining
# - Allows expert content adaptation
# - Use when fine-tuning data is out-of-distribution
def freeze_router(model):
    for name, param in model.named_parameters():
        if "gate" in name or "router" in name:
            param.requires_grad = False
    print("Router frozen. Only expert FFNs will update.")

25.8 Cheat Sheet

  • MoE core idea: Replace one large FFN per layer with E smaller expert FFNs plus a router; only top-k experts activate per token
  • Sparse activation: Total params >> active params; FLOPs scale with active, memory scales with total
  • Router = small linear layer: W ∈ ℝ^{E×d} → softmax → top-k selection; negligible FLOP cost
  • Top-2 routing is standard: Weighted blend of 2 experts; more stable than top-1, better quality
  • Expert collapse: Self-reinforcing loop where 1-2 experts dominate; diagnosed by routing histogram
  • Aux load balancing loss: L_aux = α × E × Σ(f_i × p_i); α ≈ 0.001–0.01; fights collapse during training
  • DeepSeek bias approach: Per-expert bias terms updated post-hoc; no gradient interference; better quality
  • Expert choice routing: Experts pick tokens instead of tokens picking experts; perfect load balance; bad for streaming
  • Capacity factor CF: Max tokens per expert = CF × (T / E); higher CF = less dropping, more memory
  • Mixtral 8x7B: 46.7B total params, ~12.9B active/token, ~93GB FP16, comparable FLOPs to 13B dense
  • Memory requirement = full model, not active model: All experts must reside in VRAM simultaneously
  • Expert parallelism: Different GPUs host different experts; requires all-to-all communication
  • NVLink >> PCIe for MoE: PCIe all-to-all can be 30-50% of step time at large batch; NVLink is negligible
  • Fine-tuning risk: Router disruption collapses specialization; monitor routing histogram, freeze router if needed
  • LoRA strategy: Attention-only LoRA for instruction tuning; expert LoRA for domain adaptation
  • Production inference recommendation: MoE wins on throughput at batch ≥ 64; dense wins for interactive latency-critical single-user workloads

25.9 Interview Questions

25.9.1 Entry Level

Entry Level — Q1

What is Mixture of Experts and how does it differ from a dense model?

Model Answer

A Mixture of Experts (MoE) model replaces the feed-forward network sublayer in a transformer with a bank of multiple expert FFNs and a gating network that routes each token to only a subset — typically the top 2. A dense model activates all parameters for every token; a sparse MoE model activates only the k selected experts per token, leaving the rest of the parameters untouched.

The result is a model that has a large total parameter count (all experts summed) but a much smaller active parameter count per token (only k experts). Mixtral-8x7B has ~47B total parameters but only ~12.9B active per token. This means the FLOP cost per token is similar to a 13B dense model, but the model has access to 47B worth of stored capacity — different experts can specialize in different types of knowledge or processing, giving the model higher quality at the same inference cost.

The tradeoff: all experts must reside in memory simultaneously, even though most are idle per token, so GPU memory requirements correspond to the full 47B, not the active 13B.

Entry Level — Q2

Why does a 47B MoE model run with similar FLOPs to a 12B dense model?

Model Answer

FLOPs scale with the number of multiplications actually performed — not the parameters sitting in memory unused. In Mixtral-8x7B, each token activates 2 of 8 experts per MoE layer. Each expert has the same FFN structure as a ~1.5B-parameter model’s FFN block. Two active experts contribute roughly the same computation as one larger FFN in a ~3B-parameter model per MoE layer.

When you add up the attention layers (dense, equal in both models) plus the active expert FFN layers across all 32 transformer blocks, the total FLOP count per token is approximately equivalent to running a 12-13B dense model. The 47B total parameters are partitioned across 8 experts per layer; only 25% (2/8) of those FFN parameters compute anything for a given token. The other 75% consume memory and do nothing for that token — this is the fundamental memory-compute tradeoff of sparse MoE.

Entry Level — Q3

What is “expert collapse” and how is it prevented?

Model Answer

Expert collapse is when the gating network converges to routing most or all tokens to the same one or two experts. It is self-reinforcing: an expert that is slightly better gets routed to more often, receives more gradient updates, improves more, attracts even more traffic. Unused experts receive no gradients and stagnate. The model ends up behaving as if it has 1-2 experts despite having 8.

The primary prevention is an auxiliary load balancing loss added during training: L_aux = α × E × Σ_i(f_i × p_i), where f_i is the fraction of tokens routed to expert i and p_i is the mean routing probability. This differentiable penalty pushes the router toward uniform load. The coefficient α is critical — too small fails to prevent collapse; too large forces uniformity and destroys specialization.

DeepSeek’s alternative: per-expert bias terms in routing logits. Overloaded experts get their bias decreased; underloaded experts get it increased. This closed-loop feedback maintains balance without any gradient-level interference with the quality objective.

Entry Level — Q4

What is the auxiliary load balancing loss in detail?

Model Answer

The auxiliary load balancing loss is: L_aux = α × E × Σ_i (f_i × p_i)

  • f_i: fraction of tokens in the current batch actually routed to expert i. This is a hard count (argmax-based), so it is non-differentiable.
  • p_i: mean routing probability assigned to expert i across the batch — computed via softmax, fully differentiable.
  • Their product is a proxy for load imbalance that admits gradients through p_i.
  • α: coefficient controlling penalty strength. Typical values: 0.001–0.01.
  • E: number of experts, included so the scale of the loss is invariant to E.

When expert 1 dominates routing, f_1 and p_1 are both large, making the loss large. Gradient descent then reduces p_1, making expert 1 less likely to be selected next step. This breaks the self-reinforcing collapse loop.

Key diagnostic: plot the per-expert token fraction histogram every 1,000 training steps. A healthy model shows all experts at roughly 1/E ± 10%. A collapsing model shows one or two experts rising above 40-50%.

Entry Level — Q5

What happens to a token when it exceeds expert capacity?

Model Answer

When an expert has reached its capacity limit (capacity_factor × tokens_per_batch / num_experts), any additional tokens assigned to that expert are “dropped.” The dropped token still flows through the residual connection — its hidden state passes through unchanged, missing the FFN transformation entirely. For a few tokens per batch, this is inconsequential — the residual connection preserves the embedding, and the next attention layer can compensate. For systematic overload (all tokens from long documents routing to the same expert), dropped tokens can cause significant quality degradation for specific input types.

In practice: monitor your token drop rate as a training metric. If it exceeds 2% consistently, either increase the capacity factor (CF) to allow more tokens per expert, or strengthen the load balancing mechanism. Higher CF costs more GPU memory allocation but prevents quality degradation from systematic dropping.

25.9.2 Mid Level

Mid Level — Q6

Walk through the routing mechanism in detail — how does a token get assigned to experts?

Model Answer

The routing mechanism begins with the token’s hidden state h ∈ ℝ^d after the attention sublayer. The router is a linear projection W ∈ ℝ^{E×d} that maps h to E scalar logits — one per expert. These logits pass through a softmax to produce routing probabilities p ∈ ℝ^E, where p_i represents the router’s confidence in sending this token to expert i.

The top-k selection takes the k highest-probability experts (typically k=2) and normalizes their weights so they sum to 1. Token h is sent to each selected expert’s FFN independently, producing k output vectors. These outputs are linearly combined using the normalized routing probabilities as weights:

output = Σ_{i ∈ topk} (p_i / Σ_{j ∈ topk} p_j) × FFN_i(h)

In distributed execution, expert dispatch involves: (1) each device determines which tokens to send where, (2) an all-to-all communication sends tokens to the GPUs hosting their target experts, (3) each GPU computes its expert FFN on received tokens, (4) another all-to-all sends results back, (5) the routing device reconstructs the weighted sum. Token dropping occurs if a target expert has already reached capacity; dropped tokens pass through the residual connection without any FFN transformation.

Important detail: the routing decision for each token is made independently — there is no global optimization over the batch. This local, greedy routing is what makes expert collapse possible and why auxiliary loss or bias correction is necessary.

Mid Level — Q7

Why does MoE require more GPU memory than a dense model of equivalent active parameters?

Model Answer

GPU memory requirements for MoE are determined by total parameters, not active parameters, because the gating network can route any token to any expert at any time. Unlike a dense model where you know exactly which parameters will execute, a MoE model’s routing is data-dependent — you cannot predict at model-load time which experts will be needed. Therefore, all expert parameters must be resident in GPU memory for every forward pass.

Mixtral-8x7B illustrates this starkly: active parameters per token are ~12.9B, but GPU memory requirement for weights is ~93GB (at FP16), corresponding to the full 46.7B parameter count. A dense 13B model requires ~26GB at FP16. You need approximately 3.5× more GPU memory to serve Mixtral-8x7B versus a dense model with the same compute cost per token.

The activation memory during forward pass scales with the active parameter count (plus attention KV cache), so peak activation memory is similar to the 13B dense equivalent — the memory penalty is entirely in weight storage. This is why MoE serving typically requires high-memory GPUs or expert parallelism across multiple GPUs, while the inference throughput (tokens/sec) is competitive with the smaller dense equivalent.

Mid Level — Q8

What is the load balancing auxiliary loss and why does removing it (DeepSeek approach) work?

Model Answer

The auxiliary load balancing loss L_aux = α × E × Σ_i (f_i × p_i) adds a differentiable penalty to the training objective when expert loads are uneven. f_i is the fraction of tokens in a batch routed to expert i (hard count, non-differentiable) and p_i is the mean routing probability toward expert i across the batch (differentiable). Their product is a proxy for load imbalance that can receive gradients, pushing routing probabilities toward uniformity.

The problem with auxiliary loss is that it degrades model quality. The routing network simultaneously tries to minimize task loss (route tokens to the most capable expert) and auxiliary loss (distribute tokens uniformly). These objectives are in tension — the best expert for a math problem should not be uniformly chosen. The auxiliary loss acts as a regularizer that prevents routing from being as discriminative as it could be.

DeepSeek’s auxiliary-loss-free approach replaces training-time objective pressure with inference-time correction via per-expert bias terms added to routing logits. After each forward pass, a monitoring system tracks expert utilization; overloaded experts have their bias decreased by a small δ, underloaded experts have their bias increased. This closed-loop feedback maintains approximate load balance without gradient-level interference with the routing network’s quality signal. The router learns to be as discriminative as the task requires, while the bias correction prevents sustained collapse. DeepSeek V2/V3 shows better benchmark performance than models trained with auxiliary loss at equivalent scale, validating the approach.

Mid Level — Q9

What is expert choice routing and when would you use it?

Model Answer

Standard top-k routing is token-choice: each token selects its top-k preferred experts. Expert choice routing inverts this: each expert selects its top-k preferred tokens from the batch. The expert scores every token in the batch, sorts them, and processes the highest-scoring k tokens.

The key property: load balance is guaranteed by construction. In token-choice routing, popular experts receive more tokens than capacity allows, causing drops, while unpopular experts sit idle. In expert choice, every expert processes exactly k tokens per batch — no capacity overflow, no dropped tokens, no auxiliary loss needed.

Drawbacks are real: (1) Not every token is guaranteed to be processed by any expert — if k × E < total_tokens, some tokens miss all FFN transformations and rely solely on the residual connection. You must set k × E ≥ total_tokens for full coverage, which constrains the capacity factor. (2) Expert choice requires knowing the full batch before routing decisions — selection is global over the batch. This complicates autoregressive generation where future tokens are unknown.

In practice, expert choice is used in research settings or encoder models where the full sequence is available at routing time. It is not commonly used in production generative models.

## The Core Intuition

Think of a dense transformer FFN as a single massive generalist employee who handles every question that comes in — they must be good at coding, math, French, legal reasoning, and everything else simultaneously. A Mixture of Experts model instead hires a team of specialists: one expert for code, one for math, one for multilingual tasks, one for factual recall. When a question comes in, a smart router decides which one or two specialists to consult rather than taxing everyone.

The clever engineering insight: you only pay the compute cost of the specialists you consult, but you get to hire as many specialists as you want. Storage is cheap; computation is expensive. MoE exploits this asymmetry directly.

More precisely: a MoE model replaces the feed-forward network (FFN) sublayer inside each transformer block with a bank of E parallel expert FFNs, plus a gating network that routes each token to only the top-k experts. The critical word is "only" — in a dense model, every token activates all the parameters of the FFN. In a sparse MoE, a token with k=2 activates exactly 2 of the E experts regardless of how large E is. This is sparse activation — the mechanism that decouples total parameter count (all experts combined) from active parameter count (the k experts used per token), and it is the source of every MoE tradeoff that follows.

::: {.callout-warning}
**Common Misconception:** "MoE is just model ensembling." Wrong. Ensembling runs multiple full models and averages results — the cost scales linearly with the number of models. MoE routes each token to a tiny fraction of experts with a single forward pass. The experts share embedding layers, attention layers, and are trained jointly. MoE is a single model with a conditional execution pattern, not an ensemble.
:::

## How MoE Works: The Mechanics

### The Gating Network

The router is a small learned linear layer followed by softmax. For each token's hidden state **h** ∈ ℝ^d after the attention sublayer, the router computes:

```
logits = W_r · h        where W_r ∈ ℝ^{E × d}
probs  = softmax(logits)
selected = top-k(probs)
output = Σ_{i ∈ selected} (p_i / Σ_{j ∈ selected} p_j) × FFN_i(h)
```

For a model with hidden dimension 4096 and 8 experts, W_r has only ~32K parameters — negligible compared to the expert FFNs. The gating computation adds essentially no FLOP cost; the bottleneck is expert FFN computations and, at scale, the communication needed to dispatch tokens to the right experts.

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class MoELayer(nn.Module):
    """
    Minimal MoE FFN layer illustrating top-k routing.
    In production (Mixtral, DeepSeek), this is much more optimized.
    """
    def __init__(self, d_model: int, d_ffn: int, num_experts: int, top_k: int = 2):
        super().__init__()
        self.num_experts = num_experts
        self.top_k = top_k

        # Router: small linear projection
        self.router = nn.Linear(d_model, num_experts, bias=False)

        # Expert FFNs — each is a standard two-layer FFN
        self.experts = nn.ModuleList([
            nn.Sequential(
                nn.Linear(d_model, d_ffn),
                nn.SiLU(),
                nn.Linear(d_ffn, d_model),
            )
            for _ in range(num_experts)
        ])

    def forward(self, x: torch.Tensor):
        # x: (batch, seq_len, d_model)
        B, T, D = x.shape
        x_flat = x.view(-1, D)  # (B*T, d_model)

        # Router scores
        router_logits = self.router(x_flat)          # (B*T, num_experts)
        router_probs  = F.softmax(router_logits, dim=-1)

        # Top-k selection
        top_k_probs, top_k_indices = torch.topk(router_probs, self.top_k, dim=-1)
        # Normalize selected probs to sum to 1
        top_k_probs = top_k_probs / top_k_probs.sum(dim=-1, keepdim=True)

        # Dispatch: for each token, compute selected expert outputs and blend
        output = torch.zeros_like(x_flat)
        for k in range(self.top_k):
            expert_idx = top_k_indices[:, k]   # (B*T,)
            weight     = top_k_probs[:, k]     # (B*T,)
            for e in range(self.num_experts):
                mask = (expert_idx == e)
                if mask.any():
                    expert_out = self.experts[e](x_flat[mask])   # run expert
                    output[mask] += weight[mask].unsqueeze(-1) * expert_out

        return output.view(B, T, D)

    def aux_load_balancing_loss(self, router_logits: torch.Tensor, alpha: float = 0.01):
        """
        Switch Transformer auxiliary loss to prevent expert collapse.
        L_aux = alpha * num_experts * sum_i(f_i * p_i)
        f_i = fraction of tokens routed to expert i  (hard, non-differentiable)
        p_i = mean routing probability toward expert i (differentiable)
        """
        probs   = F.softmax(router_logits, dim=-1)          # (tokens, E)
        # Hard routing fractions (argmax assignment)
        one_hot = F.one_hot(probs.argmax(dim=-1), self.num_experts).float()
        f = one_hot.mean(dim=0)   # (E,)  -- non-differentiable fraction
        p = probs.mean(dim=0)     # (E,)  -- differentiable mean probability
        loss = alpha * self.num_experts * (f * p).sum()
        return loss
```

### Expert Capacity and Token Dropping

Expert capacity is a practical constraint in batched execution. If you have 8 experts and 800 tokens in a batch, perfect load balance means each expert processes 100 tokens. But expert capacity sets a maximum — tokens exceeding this limit are dropped (their contribution to the output is zeroed; they fall back to the residual connection).

The capacity factor CF scales this limit:

```
capacity_per_expert = CF × (total_tokens / num_experts)
```

A CF of 1.25 allows 25% oversubscription. Setting CF too low causes dropped tokens and quality degradation. Setting it too high wastes GPU memory allocation.

```python
def route_with_capacity(
    tokens: torch.Tensor,      # (T, d)
    router_probs: torch.Tensor,# (T, E)
    top_k: int,
    capacity_factor: float,
    num_experts: int,
):
    """
    Demonstrates capacity-based token dropping logic.
    Returns dispatched token assignments and drop mask.
    """
    T = tokens.shape[0]
    capacity = int(capacity_factor * T / num_experts)

    top_k_probs, top_k_indices = torch.topk(router_probs, top_k, dim=-1)

    # Per-expert token count tracker
    expert_counts = torch.zeros(num_experts, dtype=torch.long)
    assignments   = []   # list of (token_idx, expert_idx, weight)
    dropped       = []

    for t in range(T):
        for k in range(top_k):
            e = top_k_indices[t, k].item()
            if expert_counts[e] < capacity:
                assignments.append((t, e, top_k_probs[t, k].item()))
                expert_counts[e] += 1
            else:
                # Token t is dropped for expert e — falls back to residual
                dropped.append((t, e))

    drop_rate = len(dropped) / (T * top_k)
    print(f"Drop rate: {drop_rate:.2%} | Expert loads: {expert_counts.tolist()}")
    return assignments, dropped
```

::: {.callout-warning}
**Production Gotcha — Token Drop Rate:** Monitor your token drop rate during training. Anything above 1-2% on validation data signals that your capacity factor is too low or your load balancing is failing. Systematic drops on specific input types (long documents, code) can cause subtle quality degradation that only shows up in domain-specific evals, not aggregate benchmarks. Add `expert_drop_rate` to your training metrics dashboard.
:::

## Router Design & Load Balancing

### Top-1 vs. Top-2 Routing

Top-1 routing (select one expert per token) maximizes sparsity but produces high variance in routing decisions. A small perturbation in the hidden state can flip which expert is selected, making training less stable. Top-2 routing provides a weighted blend of two experts, smoothing gradients and generally producing better quality at the cost of doubled expert computation per token. Nearly all competitive MoE models (Mixtral, DeepSeek V2/V3) use top-2. Some research has explored k > 2, but the quality gains beyond k=2 are typically marginal relative to the compute cost.

| Routing | Active FLOPs | Stability | Quality | Used By |
|---------|-------------|-----------|---------|---------|
| Top-1   | 1× expert   | Lower     | Good    | Switch Transformer |
| Top-2   | 2× experts  | Higher    | Better  | Mixtral, DeepSeek V2/V3 |
| Top-4   | 4× experts  | Highest   | Best    | GPT-4 (rumored) |
| Expert Choice | Fixed per expert | N/A (no drop) | Research | Google research |

### Expert Collapse: The Dominant Failure Mode

Expert collapse is a self-reinforcing positive feedback loop. A slightly stronger expert receives more gradient signal, becomes better, attracts more tokens, receives more gradients, becomes better still. Within a few thousand training steps, the distribution can be 80%+ concentrated on two experts. The remaining experts starve and become useless, and the MoE behaves like a model with far fewer actual experts — losing all the capacity benefits.

**Detecting collapse:** Monitor the fraction of tokens routed to each expert. Healthy routing shows roughly uniform distribution with standard deviation well below the mean. Collapsed routing shows one or two experts handling 80%+ of traffic.

```python
import numpy as np
import matplotlib.pyplot as plt

def analyze_expert_routing(routing_counts: list[int]) -> dict:
    """
    Analyzes expert routing statistics.
    routing_counts: list of token counts per expert over evaluation set.
    """
    counts = np.array(routing_counts, dtype=float)
    total  = counts.sum()
    fracs  = counts / total

    stats = {
        "mean_frac":     fracs.mean(),
        "std_frac":      fracs.std(),
        "max_frac":      fracs.max(),
        "min_frac":      fracs.min(),
        "cv":            fracs.std() / fracs.mean(),      # coefficient of variation
        "top1_pct":      fracs.max() * 100,
        "top2_pct":      np.sort(fracs)[-2:].sum() * 100,
        "is_collapsed":  fracs.max() > 0.4,               # heuristic: any expert > 40% → collapse
    }

    print("=== Expert Routing Analysis ===")
    for e, f in enumerate(fracs):
        bar = "█" * int(f * 50)
        print(f"Expert {e:2d}: {f:.3f} {bar}")
    print(f"\nCV (coefficient of variation): {stats['cv']:.3f}")
    print(f"Top-1 expert load: {stats['top1_pct']:.1f}%")
    print(f"Top-2 expert combined: {stats['top2_pct']:.1f}%")
    if stats["is_collapsed"]:
        print("WARNING: Routing collapse detected!")
    return stats

# Example: healthy routing (8 experts, roughly uniform)
healthy_counts   = [120, 115, 125, 118, 122, 119, 121, 116]
analyze_expert_routing(healthy_counts)

# Example: collapsed routing
collapsed_counts = [480, 220, 40, 35, 50, 45, 60, 70]
analyze_expert_routing(collapsed_counts)
```

### Auxiliary Load Balancing Loss

The standard fix is a differentiable penalty added to the training objective:

```
L_aux = α × E × Σ_i (f_i × p_i)
```

where f_i is the fraction of tokens routed to expert i (hard, non-differentiable), and p_i is the mean routing probability toward expert i (differentiable through softmax). Their product is a proxy for load imbalance that admits gradients.

The coefficient α is critical:
- Too small (α < 0.001): collapse still occurs
- Typical range: α ∈ [0.001, 0.01]
- Too large (α ≥ 0.1): forces uniform routing, destroying specialization

::: {.callout-warning}
**The α Tuning Trap:** The auxiliary loss creates a fundamental tension. It pushes the router toward uniformity, which prevents collapse but also prevents the specialization that makes MoE valuable. If you raise α to aggressively prevent collapse, you may end up with a model that routes tokens uniformly regardless of content — essentially a random router. You can detect over-regularized routing by measuring routing entropy: if it is near maximum (log E), your α is too high.
:::

### DeepSeek's Auxiliary-Loss-Free Approach

DeepSeek V2 and V3 introduced an elegant alternative: per-expert bias terms added to routing logits.

```python
class DeepSeekRouter(nn.Module):
    """
    Auxiliary-loss-free load balancing via per-expert bias update.
    Overloaded experts get their bias decreased, underloaded get it increased.
    No auxiliary loss term needed — quality is preserved.
    """
    def __init__(self, d_model: int, num_experts: int, top_k: int = 2):
        super().__init__()
        self.num_experts = num_experts
        self.top_k = top_k
        self.router = nn.Linear(d_model, num_experts, bias=False)
        # Bias terms for load balancing (not trained by gradient)
        self.register_buffer("bias", torch.zeros(num_experts))

    def forward(self, x):
        logits = self.router(x) + self.bias   # add bias to shift routing
        probs  = F.softmax(logits, dim=-1)
        top_k_probs, top_k_indices = torch.topk(probs, self.top_k, dim=-1)
        return top_k_probs, top_k_indices, logits

    @torch.no_grad()
    def update_bias(self, token_counts: torch.Tensor, target_per_expert: float, delta: float = 0.001):
        """
        Called after each forward pass.
        Decrease bias for overloaded experts, increase for underloaded.
        """
        fracs = token_counts.float() / token_counts.sum()
        target_frac = 1.0 / self.num_experts
        overloaded  = fracs > target_frac
        underloaded = fracs < target_frac
        self.bias[overloaded]  -= delta
        self.bias[underloaded] += delta
```

The DeepSeek approach avoids gradient-level interference with the routing signal — the router learns to be as discriminative as the task requires, while the bias correction prevents sustained collapse. DeepSeek V3's benchmarks show better performance than models trained with auxiliary loss at equivalent scale.

### Expert Choice Routing

Expert choice routing inverts the standard setup. Instead of each token choosing its top-k experts, each expert selects its top-k tokens from the batch.

**Key properties:**
- Load balance guaranteed by construction — every expert processes exactly k tokens
- No auxiliary loss needed
- No token dropping

**Drawbacks:**
- Some tokens may not be processed by any expert if k × E < total_tokens
- Requires full batch visibility before routing — complicates streaming and autoregressive decoding
- Less commonly used in generative models; more common in encoder models

## MoE in Production

### Memory vs. Compute: The Defining Tradeoff

Because the gating network might route any token to any expert during any forward pass, all experts must be loaded into GPU memory simultaneously. You cannot load experts on demand at inference time without millisecond-level latency spikes.

| Model | Total Params | Active Params/Token | FP16 Memory | Minimum Hardware |
|-------|-------------|--------------------|-----------  |-----------------|
| Llama-3 8B | 8B | 8B | 16 GB | 1× A10G 24GB |
| Llama-3 70B | 70B | 70B | 140 GB | 2× A100 80GB |
| Mixtral 8x7B | 46.7B | 12.9B | 93 GB | 2× A100 80GB |
| Mixtral 8x22B | 141B | 39B | 282 GB | 4× A100 80GB |
| DeepSeek V3 | 671B | 37B | ~1,342 GB | 16× H100 80GB+ |

### Expert Parallelism

Expert parallelism is the standard strategy at scale. Different GPUs host different experts. When the router assigns tokens to experts, tokens must be sent to the GPU hosting the target expert — requiring all-to-all communication.

```
Step 1: Router decides expert assignments for all tokens in batch
Step 2: All-to-all send: each GPU sends tokens to their target expert GPUs
Step 3: Each GPU computes its hosted expert FFN on received tokens
Step 4: All-to-all receive: each GPU receives results back
Step 5: Router reconstructs weighted sum and continues forward pass
```

All-to-all communication is expensive: bandwidth requirements scale with the number of experts and batch size, and it cannot be overlapped with computation as easily as tensor parallel communication.

**NVLink vs. PCIe matters enormously for MoE:**

```python
# Rough latency model for expert dispatch
def expert_dispatch_latency_ms(
    batch_tokens: int,
    hidden_dim: int,
    num_experts: int,
    top_k: int,
    interconnect: str = "nvlink"   # "nvlink" or "pcie"
) -> float:
    bytes_per_token = hidden_dim * 2  # FP16
    tokens_dispatched = batch_tokens * top_k
    total_bytes = tokens_dispatched * bytes_per_token

    bandwidth_GB_s = 600 if interconnect == "nvlink" else 64  # A100 NVLink vs PCIe 4.0
    latency_ms = (total_bytes / 1e9) / bandwidth_GB_s * 1000

    print(f"Dispatch latency ({interconnect}): {latency_ms:.3f} ms")
    print(f"  Tokens dispatched: {tokens_dispatched:,}")
    print(f"  Data moved: {total_bytes / 1e6:.1f} MB")
    return latency_ms

# Single sequence, interactive inference
expert_dispatch_latency_ms(512, 4096, 8, 2, "nvlink")   # ~0.007 ms — negligible
expert_dispatch_latency_ms(512, 4096, 8, 2, "pcie")     # ~0.065 ms — 9x slower

# Large batch inference
expert_dispatch_latency_ms(32768, 4096, 8, 2, "nvlink")  # ~0.45 ms
expert_dispatch_latency_ms(32768, 4096, 8, 2, "pcie")    # ~4.2 ms  — noticeable at each of 32 layers
```

::: {.callout-warning}
**Production Gotcha — PCIe vs. NVLink for MoE:** Consumer GPUs (RTX 4090) connect over PCIe. Enterprise GPUs (A100, H100) use NVLink. For a MoE model with 32 layers, each MoE layer requires two all-to-all operations. On PCIe at large batch sizes, communication can consume 30-50% of total step time. Always benchmark on your actual interconnect before committing to MoE serving infrastructure.
:::

## Fine-Tuning MoE Models

### What Actually Changes During Fine-Tuning

Standard supervised fine-tuning updates all parameters: attention layers, router weights, and all expert FFN weights. The risk: fine-tuning on a small dataset can disrupt the routing patterns learned during pretraining. Expert specialization is an emergent property — different experts have developed affinity for code, multilingual content, numerical reasoning. Fine-tuning on a narrow dataset can collapse this specialization.

**Monitor expert utilization distribution throughout fine-tuning.** If you see routing collapsing, reduce learning rate or freeze router weights.

### LoRA on MoE: Target Layer Strategy

LoRA applied to MoE models follows the same mechanics as dense models but target layer selection requires care.

```python
from peft import LoraConfig, get_peft_model

# Strategy 1: LoRA on attention layers only
# - Adapts reasoning/retrieval patterns
# - Preserves expert specialization structure
# - Fewer LoRA adapters (1× per layer vs. 8× per layer)
# - Best for: instruction following, tool use, format adaptation
lora_config_attention_only = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],  # attention only
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)

# Strategy 2: LoRA on expert FFN weights
# - 8× more LoRA adapters (one per expert per layer)
# - Adapts domain knowledge stored in FFN weights
# - Higher parameter count but still much less than full fine-tuning
# - Best for: domain adaptation (medical, legal, scientific)
lora_config_experts = LoraConfig(
    r=8,
    lora_alpha=16,
    target_modules=["w1", "w2", "w3"],   # Mixtral expert weight names
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)

# Strategy 3: Freeze router, fine-tune experts
# - Preserves routing structure from pretraining
# - Allows expert content adaptation
# - Use when fine-tuning data is out-of-distribution
def freeze_router(model):
    for name, param in model.named_parameters():
        if "gate" in name or "router" in name:
            param.requires_grad = False
    print("Router frozen. Only expert FFNs will update.")
```

::: {.callout-tip}
**Rule of thumb for MoE fine-tuning strategy:**
- Instruction following, safety RLHF, format changes → LoRA on attention layers only
- Domain adaptation (medical, legal, code) → LoRA on attention + expert FFNs
- Routing collapse occurring → Freeze router, reduce LR to 1e-5, add aux loss
- Catastrophic forgetting → Lower LR for expert FFNs (1e-5) vs. attention (1e-4)
:::

## Cheat Sheet

- **MoE core idea:** Replace one large FFN per layer with E smaller expert FFNs plus a router; only top-k experts activate per token
- **Sparse activation:** Total params >> active params; FLOPs scale with active, memory scales with total
- **Router = small linear layer:** W ∈ ℝ^{E×d} → softmax → top-k selection; negligible FLOP cost
- **Top-2 routing is standard:** Weighted blend of 2 experts; more stable than top-1, better quality
- **Expert collapse:** Self-reinforcing loop where 1-2 experts dominate; diagnosed by routing histogram
- **Aux load balancing loss:** L_aux = α × E × Σ(f_i × p_i); α ≈ 0.001–0.01; fights collapse during training
- **DeepSeek bias approach:** Per-expert bias terms updated post-hoc; no gradient interference; better quality
- **Expert choice routing:** Experts pick tokens instead of tokens picking experts; perfect load balance; bad for streaming
- **Capacity factor CF:** Max tokens per expert = CF × (T / E); higher CF = less dropping, more memory
- **Mixtral 8x7B:** 46.7B total params, ~12.9B active/token, ~93GB FP16, comparable FLOPs to 13B dense
- **Memory requirement = full model, not active model:** All experts must reside in VRAM simultaneously
- **Expert parallelism:** Different GPUs host different experts; requires all-to-all communication
- **NVLink >> PCIe for MoE:** PCIe all-to-all can be 30-50% of step time at large batch; NVLink is negligible
- **Fine-tuning risk:** Router disruption collapses specialization; monitor routing histogram, freeze router if needed
- **LoRA strategy:** Attention-only LoRA for instruction tuning; expert LoRA for domain adaptation
- **Production inference recommendation:** MoE wins on throughput at batch ≥ 64; dense wins for interactive latency-critical single-user workloads
- **Token drop rate:** Alert if >2% of tokens are dropped in production; increase CF or fix load balancing
- **GPT-4 rumored MoE:** ~8 experts of ~220B each, but unconfirmed; MoE at frontier scale is an open research area

## Interview Questions

### Entry Level

::: {.callout-tip title="Entry Level — Q1"}
**What is Mixture of Experts and how does it differ from a dense model?**

::: {.callout-note collapse="true" title="Model Answer"}
A Mixture of Experts (MoE) model replaces the feed-forward network sublayer in a transformer with a bank of multiple expert FFNs and a gating network that routes each token to only a subset — typically the top 2. A dense model activates all parameters for every token; a sparse MoE model activates only the k selected experts per token, leaving the rest of the parameters untouched.

The result is a model that has a large total parameter count (all experts summed) but a much smaller active parameter count per token (only k experts). Mixtral-8x7B has ~47B total parameters but only ~12.9B active per token. This means the FLOP cost per token is similar to a 13B dense model, but the model has access to 47B worth of stored capacity — different experts can specialize in different types of knowledge or processing, giving the model higher quality at the same inference cost.

The tradeoff: all experts must reside in memory simultaneously, even though most are idle per token, so GPU memory requirements correspond to the full 47B, not the active 13B.
:::
:::

::: {.callout-tip title="Entry Level — Q2"}
**Why does a 47B MoE model run with similar FLOPs to a 12B dense model?**

::: {.callout-note collapse="true" title="Model Answer"}
FLOPs scale with the number of multiplications actually performed — not the parameters sitting in memory unused. In Mixtral-8x7B, each token activates 2 of 8 experts per MoE layer. Each expert has the same FFN structure as a ~1.5B-parameter model's FFN block. Two active experts contribute roughly the same computation as one larger FFN in a ~3B-parameter model per MoE layer.

When you add up the attention layers (dense, equal in both models) plus the active expert FFN layers across all 32 transformer blocks, the total FLOP count per token is approximately equivalent to running a 12-13B dense model. The 47B total parameters are partitioned across 8 experts per layer; only 25% (2/8) of those FFN parameters compute anything for a given token. The other 75% consume memory and do nothing for that token — this is the fundamental memory-compute tradeoff of sparse MoE.
:::
:::

::: {.callout-tip title="Entry Level — Q3"}
**What is "expert collapse" and how is it prevented?**

::: {.callout-note collapse="true" title="Model Answer"}
Expert collapse is when the gating network converges to routing most or all tokens to the same one or two experts. It is self-reinforcing: an expert that is slightly better gets routed to more often, receives more gradient updates, improves more, attracts even more traffic. Unused experts receive no gradients and stagnate. The model ends up behaving as if it has 1-2 experts despite having 8.

The primary prevention is an auxiliary load balancing loss added during training: L_aux = α × E × Σ_i(f_i × p_i), where f_i is the fraction of tokens routed to expert i and p_i is the mean routing probability. This differentiable penalty pushes the router toward uniform load. The coefficient α is critical — too small fails to prevent collapse; too large forces uniformity and destroys specialization.

DeepSeek's alternative: per-expert bias terms in routing logits. Overloaded experts get their bias decreased; underloaded experts get it increased. This closed-loop feedback maintains balance without any gradient-level interference with the quality objective.
:::
:::

::: {.callout-tip title="Entry Level — Q4"}
**What is the auxiliary load balancing loss in detail?**

::: {.callout-note collapse="true" title="Model Answer"}
The auxiliary load balancing loss is: L_aux = α × E × Σ_i (f_i × p_i)

- f_i: fraction of tokens in the current batch actually routed to expert i. This is a hard count (argmax-based), so it is non-differentiable.
- p_i: mean routing probability assigned to expert i across the batch — computed via softmax, fully differentiable.
- Their product is a proxy for load imbalance that admits gradients through p_i.
- α: coefficient controlling penalty strength. Typical values: 0.001–0.01.
- E: number of experts, included so the scale of the loss is invariant to E.

When expert 1 dominates routing, f_1 and p_1 are both large, making the loss large. Gradient descent then reduces p_1, making expert 1 less likely to be selected next step. This breaks the self-reinforcing collapse loop.

Key diagnostic: plot the per-expert token fraction histogram every 1,000 training steps. A healthy model shows all experts at roughly 1/E ± 10%. A collapsing model shows one or two experts rising above 40-50%.
:::
:::

::: {.callout-tip title="Entry Level — Q5"}
**What happens to a token when it exceeds expert capacity?**

::: {.callout-note collapse="true" title="Model Answer"}
When an expert has reached its capacity limit (capacity_factor × tokens_per_batch / num_experts), any additional tokens assigned to that expert are "dropped." The dropped token still flows through the residual connection — its hidden state passes through unchanged, missing the FFN transformation entirely. For a few tokens per batch, this is inconsequential — the residual connection preserves the embedding, and the next attention layer can compensate. For systematic overload (all tokens from long documents routing to the same expert), dropped tokens can cause significant quality degradation for specific input types.

In practice: monitor your token drop rate as a training metric. If it exceeds 2% consistently, either increase the capacity factor (CF) to allow more tokens per expert, or strengthen the load balancing mechanism. Higher CF costs more GPU memory allocation but prevents quality degradation from systematic dropping.
:::
:::

### Mid Level

::: {.callout-warning title="Mid Level — Q6"}
**Walk through the routing mechanism in detail — how does a token get assigned to experts?**

::: {.callout-note collapse="true" title="Model Answer"}
The routing mechanism begins with the token's hidden state h ∈ ℝ^d after the attention sublayer. The router is a linear projection W ∈ ℝ^{E×d} that maps h to E scalar logits — one per expert. These logits pass through a softmax to produce routing probabilities p ∈ ℝ^E, where p_i represents the router's confidence in sending this token to expert i.

The top-k selection takes the k highest-probability experts (typically k=2) and normalizes their weights so they sum to 1. Token h is sent to each selected expert's FFN independently, producing k output vectors. These outputs are linearly combined using the normalized routing probabilities as weights:

```
output = Σ_{i ∈ topk} (p_i / Σ_{j ∈ topk} p_j) × FFN_i(h)
```

In distributed execution, expert dispatch involves: (1) each device determines which tokens to send where, (2) an all-to-all communication sends tokens to the GPUs hosting their target experts, (3) each GPU computes its expert FFN on received tokens, (4) another all-to-all sends results back, (5) the routing device reconstructs the weighted sum. Token dropping occurs if a target expert has already reached capacity; dropped tokens pass through the residual connection without any FFN transformation.

Important detail: the routing decision for each token is made independently — there is no global optimization over the batch. This local, greedy routing is what makes expert collapse possible and why auxiliary loss or bias correction is necessary.
:::
:::

::: {.callout-warning title="Mid Level — Q7"}
**Why does MoE require more GPU memory than a dense model of equivalent active parameters?**

::: {.callout-note collapse="true" title="Model Answer"}
GPU memory requirements for MoE are determined by total parameters, not active parameters, because the gating network can route any token to any expert at any time. Unlike a dense model where you know exactly which parameters will execute, a MoE model's routing is data-dependent — you cannot predict at model-load time which experts will be needed. Therefore, all expert parameters must be resident in GPU memory for every forward pass.

Mixtral-8x7B illustrates this starkly: active parameters per token are ~12.9B, but GPU memory requirement for weights is ~93GB (at FP16), corresponding to the full 46.7B parameter count. A dense 13B model requires ~26GB at FP16. You need approximately 3.5× more GPU memory to serve Mixtral-8x7B versus a dense model with the same compute cost per token.

The activation memory during forward pass scales with the active parameter count (plus attention KV cache), so peak activation memory is similar to the 13B dense equivalent — the memory penalty is entirely in weight storage. This is why MoE serving typically requires high-memory GPUs or expert parallelism across multiple GPUs, while the inference throughput (tokens/sec) is competitive with the smaller dense equivalent.
:::
:::

::: {.callout-warning title="Mid Level — Q8"}
**What is the load balancing auxiliary loss and why does removing it (DeepSeek approach) work?**

::: {.callout-note collapse="true" title="Model Answer"}
The auxiliary load balancing loss L_aux = α × E × Σ_i (f_i × p_i) adds a differentiable penalty to the training objective when expert loads are uneven. f_i is the fraction of tokens in a batch routed to expert i (hard count, non-differentiable) and p_i is the mean routing probability toward expert i across the batch (differentiable). Their product is a proxy for load imbalance that can receive gradients, pushing routing probabilities toward uniformity.

The problem with auxiliary loss is that it degrades model quality. The routing network simultaneously tries to minimize task loss (route tokens to the most capable expert) and auxiliary loss (distribute tokens uniformly). These objectives are in tension — the best expert for a math problem should not be uniformly chosen. The auxiliary loss acts as a regularizer that prevents routing from being as discriminative as it could be.

DeepSeek's auxiliary-loss-free approach replaces training-time objective pressure with inference-time correction via per-expert bias terms added to routing logits. After each forward pass, a monitoring system tracks expert utilization; overloaded experts have their bias decreased by a small δ, underloaded experts have their bias increased. This closed-loop feedback maintains approximate load balance without gradient-level interference with the routing network's quality signal. The router learns to be as discriminative as the task requires, while the bias correction prevents sustained collapse. DeepSeek V2/V3 shows better benchmark performance than models trained with auxiliary loss at equivalent scale, validating the approach.
:::

::: {.callout-warning title="Mid Level — Q9"}
**What is expert choice routing and when would you use it?**

::: {.callout-note collapse="true" title="Model Answer"}
Standard top-k routing is token-choice: each token selects its top-k preferred experts. Expert choice routing inverts this: each expert selects its top-k preferred tokens from the batch. The expert scores every token in the batch, sorts them, and processes the highest-scoring k tokens.

The key property: load balance is guaranteed by construction. In token-choice routing, popular experts receive more tokens than capacity allows, causing drops, while unpopular experts sit idle. In expert choice, every expert processes exactly k tokens per batch — no capacity overflow, no dropped tokens, no auxiliary loss needed.

Drawbacks are real: (1) Not every token is guaranteed to be processed by any expert — if k × E < total_tokens, some tokens miss all FFN transformations and rely solely on the residual connection. You must set k × E ≥ total_tokens for full coverage, which constrains the capacity factor. (2) Expert choice requires knowing the full batch before routing decisions — selection is global over the batch. This complicates autoregressive generation where future tokens are unknown.

In practice, expert choice is used in research settings or encoder models where the full sequence is available at routing time. It is not commonly used in production generative models.

**Step 3: Throughput analysis.**

::: {.callout-important title="FDE — Q12"}
**A customer is fine-tuning Mixtral 8x7B on their proprietary dataset and seeing quality regression after 2 epochs. How do you diagnose and fix it?**

> **What great looks like:** Candidate immediately asks to inspect expert routing histograms before changing any hyperparameters — then proposes targeted interventions based on what the diagnostics show.

> **Common Mistake:** Immediately suggesting lower learning rate without first diagnosing whether the issue is routing collapse, overfitting, data quality, or catastrophic forgetting.

::: {.callout-note collapse="true" title="Model Answer"}
Quality regression after 2 epochs can stem from multiple causes. Diagnose before prescribing.

**Step 1: Look at expert routing distribution.**
Pull the per-expert routing histogram from your fine-tuning validation loop. If one or two experts now handle >40% of tokens (up from ~12.5% at uniform routing), you have routing collapse. If the distribution is still roughly uniform, the problem is elsewhere.

**Step 2: Identify the failure mode from the histogram.**

**If routing collapsed:**
- Root cause: learning rate too high on router weights, or fine-tuning data is very different from pretraining distribution
- Fix A: Freeze the router (`requires_grad = False` for all gate/router parameters) and continue training — lets experts adapt while preserving routing structure
- Fix B: Reduce router LR to 10× lower than expert LR using parameter groups
- Fix C: Re-enable auxiliary loss with α = 0.01 during fine-tuning

**If routing is healthy but quality is regressing:**
- Suspect overfitting: is validation loss diverging from training loss after epoch 1? Reduce epochs, add dropout, or reduce dataset repetition
- Suspect catastrophic forgetting: run benchmarks on a held-out general task set (MMLU, HumanEval). If those degrade, you are overwriting pretrained knowledge with fine-tuning
  - Fix: reduce learning rate to 1e-5 or lower; use cosine decay; consider LoRA instead of full fine-tuning to limit parameter movement

**If data quality is the issue:**
- Run perplexity analysis: what is the model's perplexity on your fine-tuning data vs. a general corpus? If perplexity on fine-tuning data is very high initially, the data is noisy or out-of-distribution
- Filter training data: remove examples with perplexity >3× the dataset median

**Recommended production diagnostic workflow:**
```python
# After each epoch, log these metrics:
metrics_to_track = [
    "eval_loss",
    "routing_entropy",        # should stay near log(8) ≈ 2.08 for 8 experts
    "max_expert_load_frac",   # should stay near 0.125 ± 0.03
    "token_drop_rate",        # should be < 0.02
    "general_benchmark_score", # MMLU or equivalent
    "task_benchmark_score",    # your actual task metric
]
# If general_benchmark_score drops by >5% vs. base model: catastrophic forgetting
# If routing_entropy drops by >30%: routing collapse underway
```
