34  Synthetic Data for LLM Training

35 Synthetic Data for LLM Training

💡 Senior Tip: Synthetic data is not a shortcut — it’s a force multiplier. The difference between good and bad synthetic data is curation quality, not generation volume.

35.1 Why Synthetic Data?

Plain-English definition: Machine-generated training data, typically produced by a powerful teacher model, used to train or fine-tune a weaker student model.

Reasons to use it:

  • No labeled data: Human annotation costs $5–$50/example for expert domains
  • Privacy constraints: Real user data can’t leave the customer’s environment
  • Rare edge cases: Synthetic can produce 10,000 examples of a critical failure mode where real data has 10
  • Capability distillation: Teach a 7B model to behave like GPT-4
  • Verifiable tasks: Generate math/code problems with guaranteed correct answers

Analogy: A textbook is synthetic data — not “real” conversations but still how experts transmit knowledge efficiently.

Common Misconception

More synthetic data is always better. Wrong. The LIMA paper showed 1,000 carefully curated examples beat 52,000 noisy Alpaca examples. Quality dominates quantity.

35.2 Core Approaches

35.2.1 Teacher-Student Distillation

Use GPT-4 or Claude as teacher → generate (instruction, response) pairs → filter → fine-tune smaller student.

Key examples: | Dataset | Teacher | Student | Key Insight | |—|—|—|—| | Alpaca | GPT-3.5 | LLaMA-7B | 52k examples, first major distillation | | Orca | GPT-4 | LLaMA-13B | Add reasoning traces via system prompts | | Phi-1/2 | GPT-4 | 1.3B/2.7B | “Textbook quality” filtering beats raw scale | | WizardLM | GPT-4 | LLaMA | Evol-Instruct for harder examples |

from openai import OpenAI
client = OpenAI()

def generate_synthetic_pair(instruction: str, persona: str = "helpful assistant") -> dict:
    """Generate a high-quality (instruction, response) pair via teacher model."""
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": f"You are a {persona}. Be thorough and accurate."},
            {"role": "user", "content": instruction}
        ],
        temperature=0.7
    )
    return {
        "instruction": instruction,
        "output": response.choices[0].message.content,
        "model": "gpt-4o",  # Always log the teacher model version
    }

# Production Gotcha: Pin the teacher model version (gpt-4o-2024-11-20, not gpt-4o).
# Model updates silently shift your training distribution.

35.2.2 Self-Instruct

Model generates its own instructions from a seed set, then generates responses, then filters.

def evolve_instruction(instruction: str, evolution_type: str) -> str:
    """Evol-Instruct: make an instruction harder and more diverse."""
    prompts = {
        "constraint": f"Rewrite with 2 specific technical constraints: '{instruction}'",
        "reasoning": f"Rewrite to require multi-step reasoning: '{instruction}'",
        "concrete":  f"Add a specific real-world context: '{instruction}'",
    }
    resp = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompts[evolution_type]}]
    )
    return resp.choices[0].message.content

35.2.3 Verifiable Synthetic Data

The most powerful form — check correctness programmatically, enabling RL training.

import sympy as sp

def generate_verified_math_problem() -> dict:
    """Generate a math problem with a provably correct solution."""
    x = sp.Symbol('x')
    a, b, c = 3, 7, 2  # or random
    expr = a*x**2 + b*x - c
    solutions = sp.solve(expr, x)
    return {
        "instruction": f"Solve for x: {a}x² + {b}x - {c} = 0",
        "answer": [str(s) for s in solutions],
        "verified": True  # SymPy guarantees algebraic correctness
    }

def verify_code_solution(code: str, test_cases: list[dict]) -> bool:
    """Execute generated code against test cases."""
    import subprocess, json
    for tc in test_cases:
        result = subprocess.run(
            ["python", "-c", f"{code}\nprint(solution({tc['input']}))"],
            capture_output=True, text=True, timeout=5
        )
        if result.stdout.strip() != str(tc["expected"]):
            return False
    return True

💡 Senior Tip: Verifiable data powers reasoning models. DeepSeek R1’s breakthrough came from RL on verifiable math/code — the model gets a binary reward signal based on actual execution results, not human preference.

35.3 Filtering Pipeline

Quality filtering is non-negotiable. A 4-stage pipeline:

Stage Method Cost What It Catches
Deduplication MinHash (threshold 0.85) Very low Near-duplicate instructions
Format validation JSON parse / regex Low Malformed outputs
Length filter Token count bounds Low Empty or bloated responses
Quality scoring Reward model or LLM-as-judge High Low-quality completions 
from datasketch import MinHash, MinHashLSH

def deduplicate(examples: list[dict], threshold: float = 0.85) -> list[dict]:
    lsh = MinHashLSH(threshold=threshold, num_perm=128)
    unique = []
    for i, ex in enumerate(examples):
        m = MinHash(num_perm=128)
        for word in ex["instruction"].lower().split():
            m.update(word.encode('utf8'))
        if not lsh.query(m):
            lsh.insert(f"ex_{i}", m)
            unique.append(ex)
    return unique

Synthetic Data Pitfalls

Mode collapse: Single teacher model → student inherits the same style. Use multiple models or varied system prompts. Hallucinated facts: GPT-4 confidently generates wrong facts in specialized domains. Verify against a knowledge base. Distribution narrowing: Synthetic data covers what you prompted, not what users actually ask. Always eval on real queries. Teacher bias propagation: GPT-4 has political/stylistic biases. Distilling at scale inherits them.

  • Self-Instruct: generate instructions → responses → filter → train → repeat
  • Evol-Instruct: add constraints, depth, complexity, concrete context
  • Verifiable data: execution-based checking enables RL training (DeepSeek R1)
  • Filter chain: dedup → format → length → quality score → diversity sample
  • Teacher model: must be significantly stronger than student

35.6 Interview Questions

35.6.1 🟢 Entry Level (0–2 years)

Q: What is synthetic data and why is it used in LLM training?

Weak answer: “It’s fake data made by AI.”

Strong answer: Synthetic data is machine-generated training data, typically produced by a powerful teacher model like GPT-4 or Claude, used to train or fine-tune a smaller student model. It’s valuable when labeled data is scarce, expensive, or impossible to collect (e.g., due to privacy). The LIMA paper showed 1,000 high-quality synthetic examples outperformed 52,000 noisier ones — proving quality and curation matter far more than volume.

Q: What is teacher-student distillation?

A large capable model (teacher) generates instruction-response pairs. A smaller model (student) is fine-tuned on those pairs to approximate the teacher’s quality. Examples: Stanford Alpaca (GPT-3.5 → LLaMA), Phi-2 (GPT-4 generated “textbook-quality” data → 2.7B model that beats much larger models on many benchmarks).

Q: Why is verifiable synthetic data especially powerful?

When you can automatically check if a generated answer is correct — for math (run SymPy), code (execute it), or logic (verify constraints) — you can scale quality control without human reviewers and enable reinforcement learning with a real reward signal. This is the foundation of reasoning models like DeepSeek R1 and OpenAI o1.

Q: What filtering should you always apply to synthetic data?

Minimum pipeline: deduplication (MinHash to remove near-duplicates), format validation (correct structure), length filtering (remove empty or bloated responses), and quality scoring (reward model or LLM-as-judge). Order matters: cheap filters first, expensive last.

Q: What is the risk of training only on synthetic data?

Model collapse: models recursively trained on AI outputs gradually lose output diversity and quality — like making photocopies of photocopies. Also: hallucinated facts from the teacher model, inherited biases, and distribution mismatch (synthetic data covers what you prompted, not what real users ask).

35.6.2 🟡 Mid Level (2–5 years)

Q: How does Evol-Instruct work and what problem does it solve?

Evol-Instruct iteratively rewrites instructions to be harder. Starting from “write a Python function,” it applies transformations: add constraints (“use only stdlib, O(n) time”), deepen reasoning (“explain algorithm choice”), concretize context (“for a streaming log processor”). WizardLM used this to improve benchmark performance significantly. It solves the easy-data problem: human-written instruction sets tend to be too simple, so models quickly overfit and fail on harder real queries.

Follow-up: How do you prevent evolved instructions from becoming nonsensical? Generate the response before accepting the evolved instruction — if GPT-4 can’t answer it coherently, it’s too hard.

Q: Walk through designing a synthetic pipeline for a customer support fine-tune.

  1. Mine 500 real tickets (privacy-scrubbed) + 200 expert-written edge cases as seeds
  2. Evol-Instruct to generate 50k diverse instructions across issue categories
  3. GPT-4 response generation with persona-specific system prompt
  4. Filter: dedup → format validate → remove PII/competitor mentions → reward model score (keep top 80%)
  5. Diversity sample across issue categories
  6. Hold out 100 real tickets for evaluation — never eval only on synthetic

Q: How do you validate a synthetic dataset before committing to a full training run?

Three layers: (1) Automatic metrics — instruction diversity (embedding distribution should be spread), response length distribution, format compliance rate. (2) Human spot-check — review 50–100 examples for factual accuracy and tone. (3) Proxy training — train a LoRA on 10% of the data and evaluate on your real holdout set. If the proxy doesn’t move metrics, the full dataset won’t either.

Q: What’s the difference between Self-Instruct and direct distillation?

Direct distillation: you write the instructions, teacher generates responses. Self-Instruct: model generates its own instructions from a small seed set, then generates responses, then you filter. Self-Instruct is cheaper to scale (no human instruction writing) but less targeted. Direct distillation gives you more control over what capabilities you’re teaching.

Q: When would you use synthetic data for RAG evaluation?

Generate (question, retrieved context, gold answer) triples using GPT-4: given a document, ask GPT-4 to write a question that can only be answered from that document, then write the correct answer. This creates a retrieval test set for RAGAS metrics (faithfulness, relevancy, context recall) without expensive human annotation. Critical: validate a random sample of generated QA pairs for factual correctness.

35.6.3 🔴 Senior / Lead / Staff Level (5+ years)

Q: Design a 100k synthetic data pipeline for fine-tuning a 7B customer support model. Walk through generation, filtering, and risk mitigation.

Phase 1 — Seed: 500 real tickets (privacy-scrubbed with Presidio) + 200 expert-written edge cases + 100 model failure examples.

Phase 2 — Instruction generation: Evol-Instruct across 4 axes (constraints, persona variation, emotional complexity, scenario depth). Target 50k raw instructions from seed.

Phase 3 — Response generation: GPT-4o with persona system prompt. Generate 2 responses per instruction (temp 0.7) for optional preference data.

Phase 4 — Filtering: MinHash dedup (0.85 threshold) → format check → length filter (50–800 tokens) → reward model score (keep top 80%) → cluster + diversity sample. Target: 100k from ~200k raw.

Phase 5 — Validation: 500-example human review. Proxy LoRA training on 10% sample, eval on 200 real tickets. Check for PII leakage, hallucinated policies, competitor mentions.

Risk mitigation: use GPT-4o + Claude-3.5 as teachers to reduce style monoculture. Pin model versions. Log provenance per example. Maintain 500-example real holdout permanently.

🎯 What great looks like: Proxy training to validate quality before committing to full run; separating generation from filtering as distinct phases with quality gates; proactively addressing bias, PII, and model collapse risks; mentioning that 10–20% real data dramatically slows collapse.

Q: What are the signs of model collapse and how do you prevent it?

Signs: decreased output entropy (model becomes deterministic), loss of rare vocabulary, outputs sound “corporate” and homogeneous, self-BLEU score increases (outputs become more similar to each other), performance on rare/diverse queries drops while common queries still pass.

Prevention: always mix 10–20% real human data; use multiple diverse teacher models; monitor output diversity metrics in production; maintain a golden holdout of real examples and track performance across model generations; never let evaluation datasets contain any synthetic examples from the current teacher lineage.

⚠️ Common Mistake: Treating synthetic eval performance as a proxy for real performance. A model can score 95% on synthetic evals and fail noticeably on real user queries. Always maintain a human-labeled holdout set.

Critical: validate a random sample of generated QA pairs for factual correctness.

### 🔴 Senior / Lead / Staff Level (5+ years)

**Q: Design a 100k synthetic data pipeline for fine-tuning a 7B customer support model. Walk through generation, filtering, and risk mitigation.**

Phase 1 — Seed: 500 real tickets (privacy-scrubbed with Presidio) + 200 expert-written edge cases + 100 model failure examples.

Phase 2 — Instruction generation: Evol-Instruct across 4 axes (constraints, persona variation, emotional complexity, scenario depth). Target 50k raw instructions from seed.

Phase 3 — Response generation: GPT-4o with persona system prompt. Generate 2 responses per instruction (temp 0.7) for optional preference data.

Phase 4 — Filtering: MinHash dedup (0.85 threshold) → format check → length filter (50–800 tokens) → reward model score (keep top 80%) → cluster + diversity sample. Target: 100k from ~200k raw.

Phase 5 — Validation: 500-example human review. Proxy LoRA training on 10% sample, eval on 200 real tickets. Check for PII leakage, hallucinated policies, competitor mentions.

Risk mitigation: use GPT-4o + Claude-3.5 as teachers to reduce style monoculture. Pin model versions. Log provenance per example. Maintain 500-example real holdout permanently.

> 🎯 **What great looks like:** Proxy training to validate quality before committing to full run; separating generation from filtering as distinct phases with quality gates; proactively addressing bias, PII, and model collapse risks; mentioning that 10–20% real data dramatically slows collapse.

**Q: What are the signs of model collapse and how do you prevent it?**

Signs: decreased output entropy (model becomes deterministic), loss of rare vocabulary, outputs sound "corporate" and homogeneous, self-BLEU score increases (outputs become more similar to each other), performance on rare/diverse queries drops while common queries still pass.

Prevention: always mix 10–20% real human data; use multiple diverse teacher models; monitor output diversity metrics in production; maintain a golden holdout of real examples and track performance across model generations; never let evaluation datasets contain any synthetic examples from the current teacher lineage.

> ⚠️ **Common Mistake:** Treating synthetic eval performance as a proxy for real performance. A model can score 95% on synthetic evals and fail noticeably on real user queries. Always maintain a human-labeled holdout set.
