38  LLM Interpretability

39 LLM Interpretability

💡 Senior Tip: Be honest about what interpretability can and cannot do today. Interviewers who work on safety and alignment will respect a calibrated answer more than an overconfident one.

39.1 Why Interpretability Matters

Plain-English definition: Interpretability is the study of what’s happening inside a neural network — which components do what, why the model produces specific outputs, and whether that behavior is reliable.

Why it matters in interviews: - Debugging: when a model fails, understanding internals helps fix it faster than blind prompt tuning - Safety: demonstrating that a model won’t behave badly requires understanding what drives its behavior - Regulatory compliance: EU AI Act and FDA guidance for AI-based medical tools require explanations - Trust: a model that can explain its reasoning is more deployable in high-stakes settings

Honest limitation: Current interpretability tools can explain narrow behaviors in small models. They don’t yet fully explain emergent capabilities in frontier LLMs. Anyone who claims otherwise is overselling.

39.2 Probing Classifiers

Definition: Train a simple (usually linear) classifier on the internal activations of a model to test whether a specific concept is encoded at a given layer.

How it works: 1. Run inputs through the model, extract activations at layer L (the “probing layer”) 2. Create labeled pairs: (activation vector, label) — e.g., (activation for “Paris is in France”, label=True for “factual”) 3. Train a logistic regression on these pairs 4. High accuracy = the model encodes this concept at layer L

What probes reveal: - Syntactic structure (POS tags) encoded in early layers - Semantic concepts (sentiment, entity type) in middle layers - Task-specific information in later layers

import torch
import numpy as np
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from transformers import AutoTokenizer, AutoModel

def probe_layer(model_name: str, texts: list[str], labels: list[int], layer: int) -> float:
    """Train a probing classifier on activations from a specific layer."""
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModel.from_pretrained(model_name, output_hidden_states=True)
    model.eval()

    activations = []
    with torch.no_grad():
        for text in texts:
            inputs = tokenizer(text, return_tensors="pt", truncation=True, max_length=128)
            outputs = model(**inputs)
            # Mean-pool the hidden states at the target layer
            hidden = outputs.hidden_states[layer]  # (batch, seq, hidden_dim)
            pooled = hidden.mean(dim=1).squeeze().numpy()
            activations.append(pooled)

    X = np.array(activations)
    clf = LogisticRegression(max_iter=1000)
    scores = cross_val_score(clf, X, labels, cv=5)
    return scores.mean()

# Production Gotcha: High probe accuracy can be spurious.
# Always compare against a shuffled-label baseline.
# If shuffled accuracy is also high, your probe is learning dataset artifacts.
Common Misconception

High probing accuracy means the model “uses” that information for its predictions. Wrong — it means the information is present in the activations. The model may not route through that information when making decisions. Probes tell you what’s stored, not what’s causally relevant.

39.3 Attention Visualization

Definition: Visualize the attention weight matrices to see which tokens attend to which other tokens.

The controversy: Jain & Wallace (2019) showed that attention weights often do not correlate with feature importance — you can change attention weights significantly without changing model predictions. However, in practice, attention visualization is still useful for: - Catching obvious errors (model ignoring key context) - Debugging cross-attention in encoder-decoder models - Getting quick hypotheses to test further

import matplotlib.pyplot as plt
import seaborn as sns
from transformers import AutoTokenizer, AutoModel
import torch

def visualize_attention(text: str, model_name: str = "bert-base-uncased", layer: int = 6, head: int = 0):
    """Visualize attention weights for a single layer and head."""
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModel.from_pretrained(model_name, output_attentions=True)
    model.eval()

    inputs = tokenizer(text, return_tensors="pt")
    tokens = tokenizer.convert_ids_to_tokens(inputs["input_ids"][0])

    with torch.no_grad():
        outputs = model(**inputs)

    # Shape: (batch, heads, seq, seq)
    attn = outputs.attentions[layer][0, head].numpy()

    plt.figure(figsize=(8, 6))
    sns.heatmap(attn, xticklabels=tokens, yticklabels=tokens, cmap="Blues")
    plt.title(f"Attention Layer {layer}, Head {head}")
    plt.tight_layout()
    plt.show()

39.4 Activation Patching (Causal Intervention)

Definition: Run two forward passes — one with the original input, one with a corrupted input — then “patch” the activations from the original run into the corrupted run at specific components. If patching a component restores the original behavior, that component is causally responsible.

Why it’s powerful: Unlike probing (correlation), activation patching gives you causal evidence about which model components drive specific behaviors.

Classic example: Identifying which attention heads are responsible for “indirect object identification” — e.g., in “Mary gave John the book. She gave it to ___“, the model must attend back to”John”. Activation patching reveals which heads perform this lookup.

from functools import partial

def run_with_patch(model, clean_tokens, corrupted_tokens, patch_layer: int, patch_head: int):
    """Activation patching: run corrupted input but patch clean activations at target layer."""
    clean_activations = {}

    def save_activation(name, module, input, output):
        clean_activations[name] = output[0].detach()  # Save clean activations

    # First pass: get clean activations
    hook = model.transformer.h[patch_layer].attn.register_forward_hook(
        partial(save_activation, f"layer_{patch_layer}")
    )
    with torch.no_grad():
        clean_out = model(clean_tokens)
    hook.remove()

    # Second pass: run corrupted input but inject clean activations at target
    def patch_activation(name, module, input, output):
        patched = list(output)
        patched[0] = clean_activations[name]  # Replace with clean activations
        return tuple(patched)

    hook = model.transformer.h[patch_layer].attn.register_forward_hook(
        partial(patch_activation, f"layer_{patch_layer}")
    )
    with torch.no_grad():
        patched_out = model(corrupted_tokens)
    hook.remove()

    return patched_out

39.5 Logit Lens

Definition: Project intermediate layer hidden states directly to the vocabulary using the model’s final unembedding matrix. This shows what token the model is “thinking about” at each layer.

What it reveals: In GPT-2 and similar models, you can see how predictions evolve through the network — early layers often predict syntactically plausible tokens, middle layers show semantic refinement, and later layers converge on the final prediction.

39.6 Sparse Autoencoders (SAEs)

Definition: Train a sparse autoencoder to decompose the model’s residual stream activations into a sparse linear combination of interpretable “features.”

Why it matters: Transformers represent many concepts as superpositions in the same activation dimensions (polysemanticity). SAEs find a basis where each direction corresponds to a single interpretable concept.

Anthropic’s work: By training SAEs on Claude’s intermediate activations, researchers found ~millions of interpretable features: specific names, concepts, emotional states, even “planning” features that activate before complex reasoning. The “Golden Gate Claude” experiment amplified the feature for “Golden Gate Bridge” — the model became obsessed with mentioning it in every response.

Practical SAE training:

import torch
import torch.nn as nn

class SparseAutoencoder(nn.Module):
    """Simple SAE for decomposing model activations into sparse interpretable features."""
    def __init__(self, input_dim: int, hidden_dim: int, l1_coeff: float = 0.001):
        super().__init__()
        self.encoder = nn.Linear(input_dim, hidden_dim, bias=True)
        self.decoder = nn.Linear(hidden_dim, input_dim, bias=True)
        self.l1_coeff = l1_coeff

    def forward(self, x):
        features = torch.relu(self.encoder(x))  # Sparse features
        reconstruction = self.decoder(features)
        # Loss = reconstruction + L1 sparsity penalty
        recon_loss = (x - reconstruction).pow(2).mean()
        sparsity_loss = self.l1_coeff * features.abs().mean()
        return reconstruction, features, recon_loss + sparsity_loss

# Production Gotcha: SAEs are expensive to train and interpret.
# You need ~millions of activations and significant compute.
# Start with TransformerLens for exploratory work.

39.8 What You Can (and Cannot) Debug Today

Can debug: - Which layers encode specific concepts (probing) - Which attention heads perform specific operations (activation patching) - How predictions evolve through layers (logit lens) - What features a specific neuron or direction responds to (SAEs) - Why a specific input triggers a specific output (attribution methods)

Cannot yet explain: - Emergent capabilities (why does scale create reasoning ability?) - Full circuit descriptions for complex behaviors in frontier models - Why a model hallucinates in one context but not another - How knowledge is distributed across billions of parameters

39.9 Cheat Sheet

  • Probing classifiers: correlation evidence — what’s stored in activations, not what’s causally used
  • Attention visualization: useful for hypothesis generation, not proof (Jain & Wallace 2019)
  • Activation patching: causal evidence — patch activations to find what drives specific behavior
  • Logit lens: project intermediate states to vocab to see prediction evolution through layers
  • SAEs: decompose superposed representations into sparse interpretable features
  • TransformerLens: the standard tool for mechanistic interpretability research
  • Induction heads: attention heads that perform in-context learning (copy patterns from earlier context)
  • Golden gate Claude: amplifying a single SAE feature causes model to fixate on one concept
  • Current limit: interpretability tools explain narrow behaviors; full model behavior still opaque
  • Polysemanticity: one neuron encodes multiple unrelated concepts — why SAEs are needed
  • Circuit discovery: find minimal set of components responsible for specific behavior
  • Probing baseline: always compare against shuffled-label control to rule out dataset artifacts
  • SAE training cost: millions of activations, hours of compute — expensive but revealing
  • Practical use today: debugging refusals, analyzing bias, safety audits, not production monitoring
  • Regulatory angle: interpretability is increasingly required for high-stakes AI deployments

39.10 Interview Questions

39.10.1 🟢 Entry Level (0–2 years)

Q: What is interpretability in the context of LLMs?

Weak answer: “It means the AI can explain itself.”

Strong answer: LLM interpretability is the study of what’s happening inside a neural network — which components are responsible for specific behaviors, what information is encoded in activations, and why the model produces specific outputs. It’s different from explainability in simpler ML models because transformers are far more complex. Current tools can explain narrow behaviors (which attention head does indirect object identification) but can’t fully explain emergent capabilities like reasoning.

Q: What is a probing classifier?

A probing classifier trains a simple (usually linear) model on the internal activations of a neural network to test whether a specific concept is encoded at a given layer. For example: extract hidden states from BERT’s layer 6 for sentences with different sentiment labels, train a logistic regression, and if accuracy is high, layer 6 encodes sentiment. Probes show correlation (what’s stored) but not causation (whether the model uses that information for predictions).

Q: Do attention weights tell you what the model is paying attention to?

Not reliably. Jain & Wallace (2019) showed that attention weights often don’t correlate with feature importance — you can change attention weights significantly without changing predictions. The model can achieve the same output through many different attention patterns. Attention visualization is useful for generating hypotheses and catching obvious issues, but you need activation patching for causal evidence.

Q: What is the “golden gate Claude” experiment?

Anthropic trained sparse autoencoders (SAEs) on Claude’s activations and found interpretable features — directions in activation space corresponding to specific concepts. They identified a feature for “Golden Gate Bridge” and artificially amplified it. The result: Claude became fixated on the Golden Gate Bridge, mentioning it constantly even in unrelated conversations. This demonstrated that SAEs can identify meaningful, causal features in LLMs.

Q: What practical use does interpretability have today?

Debugging model failures (which components activate for problematic outputs), safety audits (does the model have dangerous concepts represented?), bias analysis (which demographic concepts are associated with which attributes), and regulatory compliance (demonstrating model behavior is predictable). It’s not yet mature enough for real-time production monitoring or fully explaining emergent capabilities.

39.10.2 🟡 Mid Level (2–5 years)

Q: Explain activation patching and why it gives stronger evidence than probing.

Probing is correlational: you show that information exists in activations, but not that the model uses it. Activation patching is causal: you run two forward passes (clean and corrupted inputs), then inject the clean activations at specific components into the corrupted run. If this “restores” the original output, that component is causally responsible. Example: corrupting the subject token in “Mary gave John the book. She gave it to ___” then patching specific attention heads to see which ones restore the correct “John” completion.

Follow-up: What are the limitations of activation patching? It’s expensive (multiple forward passes per component), doesn’t scale well to frontier model sizes, and can give false positives if two components are redundant.

Q: What are sparse autoencoders (SAEs) and why are they needed for interpretability?

Transformers exhibit polysemanticity: a single neuron or activation dimension encodes multiple unrelated concepts (superposition). This makes direct neuron analysis unreliable. SAEs learn a sparse linear decomposition of the residual stream into a larger dictionary of features, where each feature ideally corresponds to a single interpretable concept. The encoder maps activations to sparse features (most are zero), and the decoder reconstructs the original activations. Anthropic’s and OpenAI’s SAE work has found millions of interpretable features in frontier models.

Q: What is the logit lens technique and what can you learn from it?

The logit lens projects the hidden state at each layer to the vocabulary using the model’s unembedding matrix, producing a probability distribution over tokens at each layer. This lets you see how predictions evolve: early layers predict syntactically plausible but semantically wrong tokens; middle layers show semantic refinement; later layers converge on the final answer. It’s particularly useful for understanding how the model builds up multi-step reasoning and for identifying where errors in factual recall are introduced.

Q: What’s the difference between mechanistic interpretability and attribution methods?

Attribution methods (SHAP, integrated gradients, attention rollout) assign importance scores to input features — they answer “which input tokens influenced this output?” Mechanistic interpretability goes deeper: it identifies the internal components (attention heads, MLPs, circuits) responsible for specific computations — “which attention head performs indirect object identification?” Attribution is input-space; mechanistic interp is activation-space and architectural. Both are useful but answer different questions.

Q: How would you use interpretability to debug a model that over-refuses valid requests?

  1. Collect examples of false refusals (valid requests incorrectly refused)
  2. Use activation patching: compare activations for refused vs accepted similar requests
  3. Identify which components (attention heads, MLP layers) are causally responsible for the refusal decision
  4. Use probing to check which concepts those components encode — likely “harmful content” detectors
  5. If using SAEs: find which features activate for refused inputs that don’t activate for accepted ones
  6. Based on findings: either fine-tune with more diverse rejection training data, or add a calibration layer that down-weights over-sensitive safety features

39.10.3 🔴 Senior / Lead / Staff Level (5+ years)

Q: What are the practical limits of current LLM interpretability? What can you actually debug today?

Strong answer:

What works today: Probing for specific encoded concepts (factual knowledge, syntax, entity types). Activation patching for identifying which components causally drive specific narrow behaviors. Logit lens for tracing prediction evolution. SAEs for identifying polysemantic features in small-to-medium models. Circuit discovery for specific algorithmic behaviors (induction, copying, indirect object identification).

What doesn’t work yet: Explaining emergent capabilities — we don’t know why scale creates reasoning ability. Full model descriptions — even small models have too many circuits to enumerate. Predicting novel failure modes before they occur. Interpreting frontier models at production scale (SAEs for GPT-4 class models are computationally prohibitive).

Practical debugging you can do today: Which attention head is causing a specific error, whether a model has a “dangerous concept” feature, why a model consistently refuses a class of prompts, whether two model versions have meaningfully different internal representations.

🎯 What great looks like: A candidate who distinguishes between what’s possible in research settings vs production, who knows the difference between correlation (probing) and causation (patching), and who can give concrete examples of debugging value without overstating the field’s maturity.

Q: How would you design an interpretability study to understand why a model fails on a specific task?

Step 1 — Characterize the failure: collect 100+ failure examples and 100+ success examples on the same task type. Step 2 — Behavioral analysis: what’s systematically different between failures and successes? (input length, specific entity types, reasoning depth needed?) Step 3 — Activation analysis: extract activations at multiple layers for both groups, train probes to find where failures diverge from successes. Step 4 — Causal analysis: use activation patching on the divergent layers to confirm causality. Step 5 — Feature identification: if SAEs are available, find which features activate differently in failures. Step 6 — Hypothesize and test: form a mechanistic hypothesis about why failures occur, design an intervention (prompt change, fine-tuning, post-processing), and test it against your holdout set.

⚠️ Common Mistake: Jumping to activation patching before characterizing the failure. You need a clear hypothesis about what’s wrong before you start patching — otherwise you’re fishing in a huge space.

```python
import torch
import torch.nn as nn

class SparseAutoencoder(nn.Module):
    """Simple SAE for decomposing model activations into sparse interpretable features."""
    def __init__(self, input_dim: int, hidden_dim: int, l1_coeff: float = 0.001):
        super().__init__()
        self.encoder = nn.Linear(input_dim, hidden_dim, bias=True)
        self.decoder = nn.Linear(hidden_dim, input_dim, bias=True)
        self.l1_coeff = l1_coeff

        reconstruction = self.decoder(features)
        # Loss = reconstruction + L1 sparsity penalty
        recon_loss = (x - reconstruction).pow(2).mean()
        sparsity_loss = self.l1_coeff * features.abs().mean()
        return reconstruction, features, recon_loss + sparsity_loss

# Production Gotcha: SAEs are expensive to train and interpret.
# You need ~millions of activations and significant compute.
# Start with TransformerLens for exploratory work.
```

## What You Can (and Cannot) Debug Today

**Can debug:**
- Which layers encode specific concepts (probing)
- Which attention heads perform specific operations (activation patching)
- How predictions evolve through layers (logit lens)
- What features a specific neuron or direction responds to (SAEs)
- Why a specific input triggers a specific output (attribution methods)

**Cannot yet explain:**
- Emergent capabilities (why does scale create reasoning ability?)
- Full circuit descriptions for complex behaviors in frontier models
- Why a model hallucinates in one context but not another
- How knowledge is distributed across billions of parameters

## Cheat Sheet

- Probing classifiers: correlation evidence — what's stored in activations, not what's causally used
- Attention visualization: useful for hypothesis generation, not proof (Jain & Wallace 2019)
- Activation patching: causal evidence — patch activations to find what drives specific behavior
- Logit lens: project intermediate states to vocab to see prediction evolution through layers
- SAEs: decompose superposed representations into sparse interpretable features
- TransformerLens: the standard tool for mechanistic interpretability research
- Induction heads: attention heads that perform in-context learning (copy patterns from earlier context)
- Golden gate Claude: amplifying a single SAE feature causes model to fixate on one concept
- Current limit: interpretability tools explain narrow behaviors; full model behavior still opaque
- Polysemanticity: one neuron encodes multiple unrelated concepts — why SAEs are needed
- Circuit discovery: find minimal set of components responsible for specific behavior
- Probing baseline: always compare against shuffled-label control to rule out dataset artifacts
- SAE training cost: millions of activations, hours of compute — expensive but revealing
- Practical use today: debugging refusals, analyzing bias, safety audits, not production monitoring
- Regulatory angle: interpretability is increasingly required for high-stakes AI deployments

## Interview Questions

### 🟢 Entry Level (0–2 years)

**Q: What is interpretability in the context of LLMs?**

**Weak answer:** "It means the AI can explain itself."

**Strong answer:** LLM interpretability is the study of what's happening inside a neural network — which components are responsible for specific behaviors, what information is encoded in activations, and why the model produces specific outputs. It's different from explainability in simpler ML models because transformers are far more complex. Current tools can explain narrow behaviors (which attention head does indirect object identification) but can't fully explain emergent capabilities like reasoning.

---

**Q: What is a probing classifier?**

A probing classifier trains a simple (usually linear) model on the internal activations of a neural network to test whether a specific concept is encoded at a given layer. For example: extract hidden states from BERT's layer 6 for sentences with different sentiment labels, train a logistic regression, and if accuracy is high, layer 6 encodes sentiment. Probes show correlation (what's stored) but not causation (whether the model uses that information for predictions).

---

**Q: Do attention weights tell you what the model is paying attention to?**

Not reliably. Jain & Wallace (2019) showed that attention weights often don't correlate with feature importance — you can change attention weights significantly without changing predictions. The model can achieve the same output through many different attention patterns. Attention visualization is useful for generating hypotheses and catching obvious issues, but you need activation patching for causal evidence.

---

**Q: What is the "golden gate Claude" experiment?**

Anthropic trained sparse autoencoders (SAEs) on Claude's activations and found interpretable features — directions in activation space corresponding to specific concepts. They identified a feature for "Golden Gate Bridge" and artificially amplified it. The result: Claude became fixated on the Golden Gate Bridge, mentioning it constantly even in unrelated conversations. This demonstrated that SAEs can identify meaningful, causal features in LLMs.

---

**Q: What practical use does interpretability have today?**

Debugging model failures (which components activate for problematic outputs), safety audits (does the model have dangerous concepts represented?), bias analysis (which demographic concepts are associated with which attributes), and regulatory compliance (demonstrating model behavior is predictable). It's not yet mature enough for real-time production monitoring or fully explaining emergent capabilities.

---

### 🟡 Mid Level (2–5 years)

**Q: Explain activation patching and why it gives stronger evidence than probing.**

Probing is correlational: you show that information *exists* in activations, but not that the model uses it. Activation patching is causal: you run two forward passes (clean and corrupted inputs), then inject the clean activations at specific components into the corrupted run. If this "restores" the original output, that component is causally responsible. Example: corrupting the subject token in "Mary gave John the book. She gave it to ___" then patching specific attention heads to see which ones restore the correct "John" completion.

*Follow-up: What are the limitations of activation patching?*
It's expensive (multiple forward passes per component), doesn't scale well to frontier model sizes, and can give false positives if two components are redundant.

---

**Q: What are sparse autoencoders (SAEs) and why are they needed for interpretability?**

Transformers exhibit polysemanticity: a single neuron or activation dimension encodes multiple unrelated concepts (superposition). This makes direct neuron analysis unreliable. SAEs learn a sparse linear decomposition of the residual stream into a larger dictionary of features, where each feature ideally corresponds to a single interpretable concept. The encoder maps activations to sparse features (most are zero), and the decoder reconstructs the original activations. Anthropic's and OpenAI's SAE work has found millions of interpretable features in frontier models.

---

**Q: What is the logit lens technique and what can you learn from it?**

The logit lens projects the hidden state at each layer to the vocabulary using the model's unembedding matrix, producing a probability distribution over tokens at each layer. This lets you see how predictions evolve: early layers predict syntactically plausible but semantically wrong tokens; middle layers show semantic refinement; later layers converge on the final answer. It's particularly useful for understanding how the model builds up multi-step reasoning and for identifying where errors in factual recall are introduced.

---

**Q: What's the difference between mechanistic interpretability and attribution methods?**

Attribution methods (SHAP, integrated gradients, attention rollout) assign importance scores to input features — they answer "which input tokens influenced this output?" Mechanistic interpretability goes deeper: it identifies the internal components (attention heads, MLPs, circuits) responsible for specific computations — "which attention head performs indirect object identification?" Attribution is input-space; mechanistic interp is activation-space and architectural. Both are useful but answer different questions.

---

**Q: How would you use interpretability to debug a model that over-refuses valid requests?**

1. Collect examples of false refusals (valid requests incorrectly refused)
2. Use activation patching: compare activations for refused vs accepted similar requests
3. Identify which components (attention heads, MLP layers) are causally responsible for the refusal decision
4. Use probing to check which concepts those components encode — likely "harmful content" detectors
5. If using SAEs: find which features activate for refused inputs that don't activate for accepted ones
6. Based on findings: either fine-tune with more diverse rejection training data, or add a calibration layer that down-weights over-sensitive safety features

---

### 🔴 Senior / Lead / Staff Level (5+ years)

**Q: What are the practical limits of current LLM interpretability? What can you actually debug today?**

**Strong answer:**

*What works today:* Probing for specific encoded concepts (factual knowledge, syntax, entity types). Activation patching for identifying which components causally drive specific narrow behaviors. Logit lens for tracing prediction evolution. SAEs for identifying polysemantic features in small-to-medium models. Circuit discovery for specific algorithmic behaviors (induction, copying, indirect object identification).

*What doesn't work yet:* Explaining emergent capabilities — we don't know why scale creates reasoning ability. Full model descriptions — even small models have too many circuits to enumerate. Predicting novel failure modes before they occur. Interpreting frontier models at production scale (SAEs for GPT-4 class models are computationally prohibitive).

*Practical debugging you can do today:* Which attention head is causing a specific error, whether a model has a "dangerous concept" feature, why a model consistently refuses a class of prompts, whether two model versions have meaningfully different internal representations.

> 🎯 **What great looks like:** A candidate who distinguishes between what's possible in research settings vs production, who knows the difference between correlation (probing) and causation (patching), and who can give concrete examples of debugging value without overstating the field's maturity.

---

**Q: How would you design an interpretability study to understand why a model fails on a specific task?**

Step 1 — Characterize the failure: collect 100+ failure examples and 100+ success examples on the same task type. Step 2 — Behavioral analysis: what's systematically different between failures and successes? (input length, specific entity types, reasoning depth needed?) Step 3 — Activation analysis: extract activations at multiple layers for both groups, train probes to find where failures diverge from successes. Step 4 — Causal analysis: use activation patching on the divergent layers to confirm causality. Step 5 — Feature identification: if SAEs are available, find which features activate differently in failures. Step 6 — Hypothesize and test: form a mechanistic hypothesis about why failures occur, design an intervention (prompt change, fine-tuning, post-processing), and test it against your holdout set.

> ⚠️ **Common Mistake:** Jumping to activation patching before characterizing the failure. You need a clear hypothesis about what's wrong before you start patching — otherwise you're fishing in a huge space.
