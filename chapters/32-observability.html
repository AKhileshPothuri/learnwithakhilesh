40 LLM Observability & Production Monitoring

💡 Senior Tip: The hardest part of LLM observability isn’t logging — it’s detecting silent degradation: no errors, no latency spikes, just gradually worse answers. Design your system to catch this from day one.

40.1 What to Log

The rule: Log everything you need to diagnose failures and measure quality. Don’t log what you don’t need, especially PII.

Field Why Type
request_id Trace end-to-end UUID
user_id (hashed) Per-user analysis SHA-256 hash
session_id Conversation context UUID
model_name + version Catch model update regressions String
prompt (input tokens) Reproduce issues Text (encrypted)
completion (output) Quality analysis Text (encrypted)
ttft_ms Time To First Token Float
tpot_ms Time Per Output Token Float
latency_ms End-to-end Float

output_tokens Cost attribution Int
cost_usd Budget tracking Float

What NOT to log: Raw PII (names, SSNs, credit cards, passwords), unencrypted medical/legal content. Log the SHA-256 hash of user ID, not the ID itself.

40.3 Cost Attribution

Track cost at the granularity you need to make decisions:

import json
from datetime import datetime

PRICING = {  # Per 1M tokens as of 2024
    "gpt-4o": {"input": 2.50, "output": 10.00},
    "gpt-4o-mini": {"input": 0.15, "output": 0.60},
    "claude-3-5-sonnet-20241022": {"input": 3.00, "output": 15.00},
}

def calculate_cost(model: str, input_tokens: int, output_tokens: int) -> float:
    pricing = PRICING.get(model, {"input": 0, "output": 0})
    return (input_tokens * pricing["input"] + output_tokens * pricing["output"]) / 1_000_000

def log_request(request_id: str, user_id: str, feature: str,
                model: str, input_tokens: int, output_tokens: int) -> dict:
    cost = calculate_cost(model, input_tokens, output_tokens)
    record = {
        "timestamp": datetime.utcnow().isoformat(),
        "request_id": request_id,
        "user_id": hash(user_id),  # Never log raw user IDs
        "feature": feature,         # "chat", "search", "summarize"
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "cost_usd": cost,
    }
    # Write to your logging backend (DataDog, Splunk, BigQuery, etc.)
    return record

40.4 Detecting Silent Degradation

This is the hardest problem. No errors, no latency changes, but outputs gradually get worse.

Detection strategy:

from openai import OpenAI
import random

client = OpenAI()

GOLDEN_SET = [
    {"question": "What is the capital of France?", "expected_contains": ["Paris"]},
    {"question": "Summarize our refund policy.", "expected_contains": ["30 days", "receipt"]},
    # 50-100 representative queries with expected characteristics
]

def llm_judge_quality(question: str, answer: str, rubric: str) -> float:
    """Use GPT-4 as judge to score a response 0-10."""
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{
            "role": "user",
            "content": f"""Score this response 0-10 for {rubric}.
Question: {question}
Response: {answer}
Score (just the integer):"""
        }]
    )
    try:
        return float(response.choices[0].message.content.strip())
    except ValueError:
        return -1.0

def monitor_quality_on_production_sample(production_logs: list[dict],
                                          sample_size: int = 50) -> dict:
    """Sample production traffic and evaluate quality with LLM-as-judge."""
    sample = random.sample(production_logs, min(sample_size, len(production_logs)))

    scores = []
    for log in sample:
        score = llm_judge_quality(
            log["prompt"], log["completion"],
            rubric="helpfulness, accuracy, and coherence"
        )
        scores.append(score)

    avg_score = sum(scores) / len(scores)
    return {
        "avg_quality_score": avg_score,
        "p10_score": sorted(scores)[len(scores)//10],
        "low_quality_rate": sum(1 for s in scores if s < 5) / len(scores)
    }

# Production Gotcha: LLM-as-judge has its own biases (verbosity, recency).
# Calibrate against human labels on a test set before trusting it for monitoring.

40.5 Semantic Caching

Cache responses for semantically similar queries — reduces cost and latency:

import numpy as np
import redis
import hashlib
from openai import OpenAI

client = OpenAI()
cache = redis.Redis(host='localhost', port=6379)
SIMILARITY_THRESHOLD = 0.95

def get_embedding(text: str) -> list[float]:
    response = client.embeddings.create(model="text-embedding-3-small", input=text)
    return response.data[0].embedding

def cosine_similarity(a: list[float], b: list[float]) -> float:
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def cached_completion(prompt: str) -> str:
    """Return cached response if semantically similar query exists."""
    query_embedding = get_embedding(prompt)

    # Check all cached embeddings (use a vector DB for scale)
    for key in cache.scan_iter("emb:*"):
        cached_emb = list(map(float, cache.lrange(key, 0, -1)))
        if cosine_similarity(query_embedding, cached_emb) > SIMILARITY_THRESHOLD:
            response_key = key.decode().replace("emb:", "resp:")
            cached_response = cache.get(response_key)
            if cached_response:
                return cached_response.decode()  # Cache hit

    # Cache miss — generate and cache
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )
    answer = response.choices[0].message.content

    cache_key = hashlib.md5(prompt.encode()).hexdigest()
    cache.rpush(f"emb:{cache_key}", *[str(v) for v in query_embedding])
    cache.set(f"resp:{cache_key}", answer, ex=3600)  # 1 hour TTL

    return answer

40.6 The Production Feedback Loop

User feedback → Evaluation dataset → Regression tests → Model/prompt improvements → Production
       ↑                                                                                  |
       └──────────────────────── New examples added ────────────────────────────────────┘

Feedback signal hierarchy (best to worst): 1. Explicit corrections (“Actually the answer should be…”) 2. Thumbs down + regenerate 3. Thumbs down 4. Session abandonment after a response 5. No feedback (assume OK)

40.7 Cheat Sheet

  • Log: request_id, hashed user_id, model+version, prompt, completion, TTFT, latency, tokens, cost, error_type
  • Never log: raw PII, passwords, payment info — use hashed/encrypted versions
  • Silent degradation: no errors but worse outputs — detect with LLM-as-judge on production samples vs golden set
  • Semantic cache: embed queries, cache responses for similar ones (cosine sim > 0.95) — 20-40% cost reduction typical
  • Cost attribution: track at user, feature, and team level; set budget alerts
  • LangSmith: traces LangChain apps automatically; Helicone: zero-code proxy for any OpenAI API call
  • Feedback loop: user feedback → eval dataset → regression tests → improvements → production
  • TTFT vs TPOT: separate these — TTFT degrades with prefill load, TPOT degrades with decode load
  • Sampling rate for quality monitoring: 1-5% of traffic for LLM-as-judge scoring is sufficient
  • Golden set: 50-100 representative queries with expected characteristics — monitor score weekly
  • Drift detection: watch embedding distribution of queries (cosine similarity to training distribution)
  • A/B testing: run prompt/model changes on 5-10% traffic, measure downstream metrics not just LLM scores
  • Anomaly alerts: cost/request spike > 2σ, refusal rate spike > 2σ, latency p99 > threshold
  • Trace granularity: separate spans for retrieval, generation, tool calls — trace IDs link them
  • Never use synthetic queries for your quality golden set — they don’t reflect real user behavior

40.8 Interview Questions

40.8.1 🟢 Entry Level (0–2 years)

Q: What should you always log for an LLM application in production?

Weak answer: “The inputs and outputs.”

Strong answer: Log: request ID (for tracing), hashed user ID (never raw PII), model name and version, input prompt, completion, time to first token, end-to-end latency, input/output token counts, cost, and any error types. Also log user feedback (thumbs up/down) when available. Version the model explicitly — a model update without a version change is one of the hardest production bugs to diagnose.

Q: What is semantic caching and why does it matter in production?

Semantic caching stores LLM responses and retrieves them for semantically similar future queries (cosine similarity above a threshold like 0.95). Unlike exact-match caching, it handles paraphrases. Benefits: 20-40% cost reduction on typical workloads, latency improvement for cached queries. Tradeoff: stale responses if the underlying data changes, and the cache itself has memory costs. Use a vector database or Redis with embedding storage.

Q: How do you detect that your LLM application’s quality is degrading in production?

Set up periodic LLM-as-judge evaluation on sampled production traffic (1-5% sample), compared against a golden set of representative queries with expected characteristics. Track average quality scores over time. Alert when the rolling 7-day average drops below a threshold. Also monitor implicit signals: thumbs-down rate, session abandonment rate after specific response types, regeneration rate.

Q: What is the difference between TTFT and TPOT latency?

TTFT (Time To First Token) is how long until the user sees the first character — driven by prefill compute and request queue depth. TPOT (Time Per Output Token) is the rate at which tokens are generated after the first — driven by decode compute and memory bandwidth. A slow TTFT feels like the app is “thinking”; a slow TPOT feels like the response is “typing slowly.” They have different root causes and different fixes.

Q: How do you attribute LLM costs to specific features or teams?

Tag each API call with a feature label (e.g., “chat”, “search”, “summarize”, “document_extraction”) and team ID. Store cost per request (input_tokens × price/M + output_tokens × price/M) in your logging backend. Aggregate in your data warehouse (BigQuery, Snowflake) for weekly cost reports per feature/team. Set budget alerts when a feature’s daily cost exceeds a threshold. This is how you justify infrastructure decisions and catch runaway costs from prompt changes.

40.8.2 🟡 Mid Level (2–5 years)

Q: Design an LLM-as-judge monitoring system that runs continuously in production.

Architecture: (1) Sampling service — intercept 2% of production requests, write to a monitoring queue. (2) Judge pipeline — pull from queue, call GPT-4o with a rubric prompt scoring on helpfulness/accuracy/safety 0-10. (3) Metrics store — write scores with request metadata to time-series DB (InfluxDB/Prometheus). (4) Dashboard — track rolling 7-day average, p10 score (catches worst cases), per-feature breakdown. (5) Alerting — PagerDuty alert if 7-day average drops > 0.5 points or p10 drops > 1 point.

Calibration step: weekly sample 50 judged examples for human review to catch judge bias drift.

Follow-up: How do you prevent the judge from being biased toward longer responses? Add explicit length-control to the rubric (“score based on accuracy and conciseness, not length”) and validate judge scores against a length-normalized human-labeled test set.

Q: How do you build an A/B testing framework for LLM prompt changes?

Route 10% of traffic to the new prompt variant using a feature flag keyed on hashed user ID (consistent assignment per user). Collect implicit feedback (thumbs, abandonment, regeneration rate) and explicit feedback (ratings). After 7 days (minimum), check statistical significance: use a two-proportion z-test for binary signals (thumbs up rate) or a t-test for continuous scores. Require p < 0.05 and practical significance (effect size > your business threshold — e.g., > 2% thumbs-up improvement). Don’t peek at results before the planned end date.

Q: Walk through how you’d set up observability for a RAG pipeline from scratch.

Set up LangSmith or Langfuse with custom traces: one parent span per user request, child spans for (1) query embedding, (2) vector DB retrieval (log retrieval latency, number of docs, doc IDs), (3) reranking, (4) LLM generation (log TTFT, TPOT, tokens). Log retrieval metrics (recall@k estimated from user feedback). Set up RAGAS evaluation on a 1% sample — log faithfulness and context precision scores. Alert on: retrieval latency > 500ms (vector DB issue), generation latency > 3s, RAGAS faithfulness < 0.7.

Q: How do you detect embedding drift in a production RAG system?

Weekly: embed 500 sampled production queries, compute mean cosine similarity between them and your training/indexing query distribution. If the distribution is shifting (mean pairwise similarity dropping, or centroid distance increasing), your retrieval quality is degrading because users are asking questions your index wasn’t built for. Also track retrieval quality directly: sample (query, retrieved docs) pairs, have LLM-as-judge score relevance. Alert when relevance score drops 5+ points.

Q: What is the feedback loop from production to your eval suite?

Production feedback (thumbs down, corrections, session abandonment) → triage to identify patterns → extract representative examples → human review to label correctly → add to eval dataset → run regression tests on next model/prompt update. Key: distinguish between model failures (wrong answer) and product failures (right answer, wrong format). Model failures go into the eval dataset; product failures go into prompt engineering or UX fixes. Review the feedback weekly, add 10-20 new eval examples per sprint.

40.8.3 🔴 Senior / Lead / Staff Level (5+ years)

Q: Design an observability stack for a production RAG chatbot with 50k daily users. What do you monitor, what alerts do you set, and how do you detect silent quality degradation?

Strong answer:

Instrumentation: LangSmith (or Langfuse self-hosted for privacy) with traces: retrieval span (latency, doc count, doc IDs), generation span (TTFT, TPOT, input/output tokens). Cost tracker: BigQuery table with model, feature, user cohort, cost per request.

Metrics dashboard: TTFT p50/p95/p99, TPOT p50/p99, error rate by error type, cost/day by feature, thumbs-up rate 7-day rolling, retrieval latency p99.

Alerts (PagerDuty): TTFT p99 > 3s, error rate > 1%, cost/day > 2σ from baseline, thumbs-down rate > 2σ.

Silent degradation detection: Daily sampling 0.5% of production (≈250 requests) → LLM-as-judge scoring on helpfulness + accuracy → plot 7-day rolling average per feature. Also run golden set (100 fixed queries) nightly against production model — alert if any score drops > 1 point.

Feedback loop: Weekly triage of thumbs-down and zero-regeneration examples → label 20-30 most representative → add to eval suite → regression test before any prompt/model change ships.

🎯 What great looks like: Candidates who separate infrastructure observability (latency, errors, cost) from quality observability (LLM-as-judge, golden sets, feedback signals) and who have a concrete plan for detecting silent degradation — not just “we’d look at the dashboard.”

Q: How do you build a production feedback loop that continuously improves your LLM system?

Strong answer:

Three feedback channels with different latency: (1) Explicit (thumbs, corrections) — highest signal, 0.5-2% response rate. (2) Implicit behavioral (regeneration, abandonment, downstream task success/failure) — higher volume, noisier. (3) Automated (LLM-as-judge on production sample) — scalable, requires calibration.

Weekly process: collect feedback from all three channels → categorize by failure type (retrieval miss, hallucination, format error, wrong refusal, off-topic) → sample 50 examples per category → human review to confirm label and write correct response → add to eval dataset → update eval suite.

Monthly process: full eval run on updated suite with current production model → compare to prior month → identify degrading categories → prioritize fixes.

Critical discipline: never let the eval dataset get contaminated with examples from the current production model’s training data. Track provenance of every eval example.

⚠️ Common Mistake: Treating user feedback as ground truth without human review. Users often thumb-down correct answers (because the answer wasn’t what they wanted, not because it was wrong). A lawyer telling an AI “that contract clause is wrong” might be wrong themselves. Always human-review before adding to training data.

```python
# Production Gotcha: LLM-as-judge has its own biases (verbosity, recency).
# Calibrate against human labels on a test set before trusting it for monitoring.
```

## Semantic Caching

Cache responses for semantically similar queries — reduces cost and latency:

```python
import numpy as np
import redis
import hashlib
from openai import OpenAI

client = OpenAI()
cache = redis.Redis(host='localhost', port=6379)
SIMILARITY_THRESHOLD = 0.95

def get_embedding(text: str) -> list[float]:
    response = client.embeddings.create(model="text-embedding-3-small", input=text)
    return response.data[0].embedding

def cosine_similarity(a: list[float], b: list[float]) -> float:
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def cached_completion(prompt: str) -> str:
    """Return cached response if semantically similar query exists."""
    query_embedding = get_embedding(prompt)

    # Check all cached embeddings (use a vector DB for scale)
    for key in cache.scan_iter("emb:*"):
        cached_emb = list(map(float, cache.lrange(key, 0, -1)))
        if cosine_similarity(query_embedding, cached_emb) > SIMILARITY_THRESHOLD:
            response_key = key.decode().replace("emb:", "resp:")
            cached_response = cache.get(response_key)
            if cached_response:
                return cached_response.decode()  # Cache hit

    # Cache miss — generate and cache
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )
    answer = response.choices[0].message.content

    cache_key = hashlib.md5(prompt.encode()).hexdigest()
    cache.rpush(f"emb:{cache_key}", *[str(v) for v in query_embedding])
    cache.set(f"resp:{cache_key}", answer, ex=3600)  # 1 hour TTL

    return answer
```

## The Production Feedback Loop

```
User feedback → Evaluation dataset → Regression tests → Model/prompt improvements → Production
       ↑                                                                                  |
       └──────────────────────── New examples added ────────────────────────────────────┘
```

**Feedback signal hierarchy (best to worst):**
1. Explicit corrections ("Actually the answer should be...")
2. Thumbs down + regenerate
3. Thumbs down
4. Session abandonment after a response
5. No feedback (assume OK)

## Cheat Sheet

- Log: request_id, hashed user_id, model+version, prompt, completion, TTFT, latency, tokens, cost, error_type
- Never log: raw PII, passwords, payment info — use hashed/encrypted versions
- Silent degradation: no errors but worse outputs — detect with LLM-as-judge on production samples vs golden set
- Semantic cache: embed queries, cache responses for similar ones (cosine sim > 0.95) — 20-40% cost reduction typical
- Cost attribution: track at user, feature, and team level; set budget alerts
- LangSmith: traces LangChain apps automatically; Helicone: zero-code proxy for any OpenAI API call
- Feedback loop: user feedback → eval dataset → regression tests → improvements → production
- TTFT vs TPOT: separate these — TTFT degrades with prefill load, TPOT degrades with decode load
- Sampling rate for quality monitoring: 1-5% of traffic for LLM-as-judge scoring is sufficient
- Golden set: 50-100 representative queries with expected characteristics — monitor score weekly
- Drift detection: watch embedding distribution of queries (cosine similarity to training distribution)
- A/B testing: run prompt/model changes on 5-10% traffic, measure downstream metrics not just LLM scores
- Anomaly alerts: cost/request spike > 2σ, refusal rate spike > 2σ, latency p99 > threshold
- Trace granularity: separate spans for retrieval, generation, tool calls — trace IDs link them
- Never use synthetic queries for your quality golden set — they don't reflect real user behavior

## Interview Questions

### 🟢 Entry Level (0–2 years)

**Q: What should you always log for an LLM application in production?**

**Weak answer:** "The inputs and outputs."

**Strong answer:** Log: request ID (for tracing), hashed user ID (never raw PII), model name and version, input prompt, completion, time to first token, end-to-end latency, input/output token counts, cost, and any error types. Also log user feedback (thumbs up/down) when available. Version the model explicitly — a model update without a version change is one of the hardest production bugs to diagnose.

---

**Q: What is semantic caching and why does it matter in production?**

Semantic caching stores LLM responses and retrieves them for semantically similar future queries (cosine similarity above a threshold like 0.95). Unlike exact-match caching, it handles paraphrases. Benefits: 20-40% cost reduction on typical workloads, latency improvement for cached queries. Tradeoff: stale responses if the underlying data changes, and the cache itself has memory costs. Use a vector database or Redis with embedding storage.

---

**Q: How do you detect that your LLM application's quality is degrading in production?**

Set up periodic LLM-as-judge evaluation on sampled production traffic (1-5% sample), compared against a golden set of representative queries with expected characteristics. Track average quality scores over time. Alert when the rolling 7-day average drops below a threshold. Also monitor implicit signals: thumbs-down rate, session abandonment rate after specific response types, regeneration rate.

---

**Q: What is the difference between TTFT and TPOT latency?**

TTFT (Time To First Token) is how long until the user sees the first character — driven by prefill compute and request queue depth. TPOT (Time Per Output Token) is the rate at which tokens are generated after the first — driven by decode compute and memory bandwidth. A slow TTFT feels like the app is "thinking"; a slow TPOT feels like the response is "typing slowly." They have different root causes and different fixes.

---

**Q: How do you attribute LLM costs to specific features or teams?**

Tag each API call with a feature label (e.g., "chat", "search", "summarize", "document_extraction") and team ID. Store cost per request (input_tokens × price/M + output_tokens × price/M) in your logging backend. Aggregate in your data warehouse (BigQuery, Snowflake) for weekly cost reports per feature/team. Set budget alerts when a feature's daily cost exceeds a threshold. This is how you justify infrastructure decisions and catch runaway costs from prompt changes.

---

### 🟡 Mid Level (2–5 years)

**Q: Design an LLM-as-judge monitoring system that runs continuously in production.**

Architecture: (1) Sampling service — intercept 2% of production requests, write to a monitoring queue. (2) Judge pipeline — pull from queue, call GPT-4o with a rubric prompt scoring on helpfulness/accuracy/safety 0-10. (3) Metrics store — write scores with request metadata to time-series DB (InfluxDB/Prometheus). (4) Dashboard — track rolling 7-day average, p10 score (catches worst cases), per-feature breakdown. (5) Alerting — PagerDuty alert if 7-day average drops > 0.5 points or p10 drops > 1 point.

Calibration step: weekly sample 50 judged examples for human review to catch judge bias drift.

*Follow-up: How do you prevent the judge from being biased toward longer responses?*
Add explicit length-control to the rubric ("score based on accuracy and conciseness, not length") and validate judge scores against a length-normalized human-labeled test set.

---

**Q: How do you build an A/B testing framework for LLM prompt changes?**

Route 10% of traffic to the new prompt variant using a feature flag keyed on hashed user ID (consistent assignment per user). Collect implicit feedback (thumbs, abandonment, regeneration rate) and explicit feedback (ratings). After 7 days (minimum), check statistical significance: use a two-proportion z-test for binary signals (thumbs up rate) or a t-test for continuous scores. Require p < 0.05 and practical significance (effect size > your business threshold — e.g., > 2% thumbs-up improvement). Don't peek at results before the planned end date.

---

**Q: Walk through how you'd set up observability for a RAG pipeline from scratch.**

Set up LangSmith or Langfuse with custom traces: one parent span per user request, child spans for (1) query embedding, (2) vector DB retrieval (log retrieval latency, number of docs, doc IDs), (3) reranking, (4) LLM generation (log TTFT, TPOT, tokens). Log retrieval metrics (recall@k estimated from user feedback). Set up RAGAS evaluation on a 1% sample — log faithfulness and context precision scores. Alert on: retrieval latency > 500ms (vector DB issue), generation latency > 3s, RAGAS faithfulness < 0.7.

---

**Q: How do you detect embedding drift in a production RAG system?**

Weekly: embed 500 sampled production queries, compute mean cosine similarity between them and your training/indexing query distribution. If the distribution is shifting (mean pairwise similarity dropping, or centroid distance increasing), your retrieval quality is degrading because users are asking questions your index wasn't built for. Also track retrieval quality directly: sample (query, retrieved docs) pairs, have LLM-as-judge score relevance. Alert when relevance score drops 5+ points.

---

**Q: What is the feedback loop from production to your eval suite?**

Production feedback (thumbs down, corrections, session abandonment) → triage to identify patterns → extract representative examples → human review to label correctly → add to eval dataset → run regression tests on next model/prompt update. Key: distinguish between model failures (wrong answer) and product failures (right answer, wrong format). Model failures go into the eval dataset; product failures go into prompt engineering or UX fixes. Review the feedback weekly, add 10-20 new eval examples per sprint.

---

### 🔴 Senior / Lead / Staff Level (5+ years)

**Q: Design an observability stack for a production RAG chatbot with 50k daily users. What do you monitor, what alerts do you set, and how do you detect silent quality degradation?**

**Strong answer:**

*Instrumentation:* LangSmith (or Langfuse self-hosted for privacy) with traces: retrieval span (latency, doc count, doc IDs), generation span (TTFT, TPOT, input/output tokens). Cost tracker: BigQuery table with model, feature, user cohort, cost per request.

*Metrics dashboard:* TTFT p50/p95/p99, TPOT p50/p99, error rate by error type, cost/day by feature, thumbs-up rate 7-day rolling, retrieval latency p99.

*Alerts (PagerDuty):* TTFT p99 > 3s, error rate > 1%, cost/day > 2σ from baseline, thumbs-down rate > 2σ.

*Silent degradation detection:* Daily sampling 0.5% of production (≈250 requests) → LLM-as-judge scoring on helpfulness + accuracy → plot 7-day rolling average per feature. Also run golden set (100 fixed queries) nightly against production model — alert if any score drops > 1 point.

*Feedback loop:* Weekly triage of thumbs-down and zero-regeneration examples → label 20-30 most representative → add to eval suite → regression test before any prompt/model change ships.

> 🎯 **What great looks like:** Candidates who separate infrastructure observability (latency, errors, cost) from quality observability (LLM-as-judge, golden sets, feedback signals) and who have a concrete plan for detecting silent degradation — not just "we'd look at the dashboard."

---

**Q: How do you build a production feedback loop that continuously improves your LLM system?**

**Strong answer:**

Three feedback channels with different latency: (1) Explicit (thumbs, corrections) — highest signal, 0.5-2% response rate. (2) Implicit behavioral (regeneration, abandonment, downstream task success/failure) — higher volume, noisier. (3) Automated (LLM-as-judge on production sample) — scalable, requires calibration.

Weekly process: collect feedback from all three channels → categorize by failure type (retrieval miss, hallucination, format error, wrong refusal, off-topic) → sample 50 examples per category → human review to confirm label and write correct response → add to eval dataset → update eval suite.

Monthly process: full eval run on updated suite with current production model → compare to prior month → identify degrading categories → prioritize fixes.

Critical discipline: never let the eval dataset get contaminated with examples from the current production model's training data. Track provenance of every eval example.

> ⚠️ **Common Mistake:** Treating user feedback as ground truth without human review. Users often thumb-down correct answers (because the answer wasn't what they wanted, not because it was wrong). A lawyer telling an AI "that contract clause is wrong" might be wrong themselves. Always human-review before adding to training data.
