34.1 Why PPO-Based RLHF Fell Out of Favor

To understand modern alignment, start with the problem it is solving. PPO-based RLHF — the canonical alignment approach used in InstructGPT and early ChatGPT — works as follows: train a supervised fine-tuned (SFT) model on demonstrations; train a separate reward model on human preference pairs; use PPO (Proximal Policy Optimization) to update the policy so its responses maximize reward while staying close to the SFT baseline via a KL penalty.

This pipeline works. It is what produced the first generation of well-behaved chat models. But it requires four separate models in memory simultaneously: the actor (policy being trained), the reference model (frozen SFT copy), the reward model, and the critic (value function). For a 70B parameter model at FP16, that is four models of roughly 140GB each — over 500GB of GPU memory just for model weights, before activations or gradients. This is the most practical reason PPO fell out of favor.

Beyond memory, PPO training is sensitive in ways that make it difficult to operate reliably at scale. The value function (critic) must track the actor’s improving policy or advantage estimates become biased, but the critic update is a separate optimization problem that can lag or diverge. The clip ratio, KL coefficient, and GAE parameters interact in ways that produce instability that looks like slow convergence until it suddenly looks like reward hacking or policy collapse. Debugging a PPO run on a 70B model requires specialized RL expertise and weeks of iteration.

Modern alignment is the engineering response to this: achieve equivalent or better alignment quality using simpler, more stable, more memory-efficient methods.

Warning

Common Misconception: “PPO is the theoretically correct algorithm, and DPO-family methods are approximations.”

This is backwards. DPO is not an approximation of PPO — it is an exact derivation of the optimal policy under the KL-constrained RL objective, expressed as a supervised loss. DPO’s limitations are distributional (offline training) not theoretical. For tasks with verifiable rewards (math, code), GRPO with rule-based rewards is strictly stronger than learned-reward PPO.

34.2 DPO: The Implicit Reward Formulation

34.2.1 How DPO Works

Direct Preference Optimization (DPO) derives a supervised training objective directly from the same KL-constrained RL problem that PPO solves. The key insight is that the KL-regularized RL objective has a closed-form optimal policy:

\[\pi^*(y|x) = \frac{1}{Z(x)} \pi_{\text{ref}}(y|x) \exp\left(\frac{r(y,x)}{\beta}\right)\]

where \(Z(x)\) is the partition function (intractable in general). Rearranging for \(r(y,x)\):

\[r(y,x) = \beta \log \frac{\pi^*(y|x)}{\pi_{\text{ref}}(y|x)} + \beta \log Z(x)\]

The \(\log Z(x)\) term cancels when you take the difference between chosen and rejected rewards in a Bradley-Terry model. The final DPO loss is:

\[\mathcal{L}_{\text{DPO}} = -\mathbb{E}_{(x, y_c, y_r) \sim \mathcal{D}} \left[ \log \sigma \left( \beta \log \frac{\pi_\theta(y_c|x)}{\pi_{\text{ref}}(y_c|x)} - \beta \log \frac{\pi_\theta(y_r|x)}{\pi_{\text{ref}}(y_r|x)} \right) \right]\]

This is just binary cross-entropy on a log-ratio difference. No reward model. No value function. No RL loop. The reward is implicit in the policy itself: a model trained with DPO has an implicit reward function equal to \(\beta \log(\pi_\theta / \pi_{\text{ref}})\).

Analogy: DPO is like learning the rules of chess by watching games and noting which moves led to wins — you never need to explicitly encode a scoring function, the preference signal is already in the game records.

34.2.2 DPO’s Three Structural Limitations

1. The Distribution Gap (Offline Training)

DPO is an offline algorithm. The preference pairs \(\{(x, y_c, y_r)\}\) are collected before training starts, from some earlier model version. As training proceeds and the policy improves, the rejected responses in the dataset no longer represent current failure modes — they represent past ones. The learning signal weakens because the training data is increasingly unrepresentative of what the current model does wrong.

2. Length Bias

DPO’s log-likelihood is a sum over tokens. Longer responses contribute more total probability mass. Human annotators, presented with two responses without length controls, systematically prefer longer responses because length correlates with perceived thoroughness. The result: DPO training learns that more tokens = more reward. Models fine-tuned with vanilla DPO produce responses 20–40% longer on average than the SFT baseline. At API scale, this is a direct cost — 30% more tokens means 30% higher inference bills.

3. Implicit KL Regularization

The KL term is controlled indirectly via the \(\beta\) hyperparameter. For prompts not well covered by the preference dataset, the policy can drift arbitrarily far from the reference model without incurring a strong penalty. This causes degenerate behavior on out-of-distribution inputs.

34.3 DPO Variants

34.3.1 IPO: Identity Preference Optimization

What it fixes: Overfitting on small datasets.

How: DPO’s sigmoid loss saturates — when the log-ratio difference grows large, the gradient approaches zero and training effectively stops. The model can overfit to the preference dataset without any signal to stop. IPO replaces the sigmoid loss with a squared error loss anchored to a target log-ratio of \(1/(2\tau)\):

\[\mathcal{L}_{\text{IPO}} = \mathbb{E}\left[\left(\log \frac{\pi_\theta(y_c|x)}{\pi_{\text{ref}}(y_c|x)} - \log \frac{\pi_\theta(y_r|x)}{\pi_{\text{ref}}(y_r|x)} - \frac{1}{2\tau}\right)^2\right]\]

The loss never saturates — there is always a gradient pulling the log-ratio toward the target. This prevents the extreme probability assignments that cause DPO to overfit.

Dataset Size Recommended Method
< 5,000 pairs IPO (prevents overfitting)
5,000–50,000 pairs DPO or IPO equivalent
> 50,000 pairs DPO, SimPO, or online DPO

When to use IPO: Small preference datasets (< 10k pairs), long training runs on the same data, or when you observe DPO loss going to zero suspiciously early.

34.3.2 KTO: Kahneman-Tversky Optimization

What it fixes: Removes the requirement for paired comparisons.

Plain English: DPO requires two responses to the same prompt — one good, one bad — collected together. KTO only needs individual labeled responses: “this was good,” “this was bad.” No pairing required.

Theoretical Basis: Kahneman and Tversky’s prospect theory shows that humans weight losses more than equivalent gains — a loss of $100 hurts roughly twice as much as a gain of $100 feels good. KTO maps this to alignment: the training objective penalizes undesirable outputs more steeply than it rewards desirable ones, using the KL divergence of the current policy from the reference as a reference point.

\[\mathcal{L}_{\text{KTO}} = \mathbb{E}\left[\lambda_D \cdot \sigma\left(\beta \cdot (r_\theta(x,y) - z_0)\right) \cdot \mathbf{1}[y \text{ desirable}] - \lambda_U \cdot \sigma\left(\beta \cdot (z_0 - r_\theta(x,y))\right) \cdot \mathbf{1}[y \text{ undesirable}]\right]\]

where \(\lambda_U > \lambda_D\) encodes the asymmetric weighting, and \(z_0 = \beta \log Z(x)\) is the reference value.

Analogy: KTO is like a teacher who grades work individually — each assignment gets a pass/fail without needing to compare it to another student’s work on the same question.

When to use KTO: You have individual binary-labeled responses (not matched pairs), annotation was collected via thumbs up/down or similar single-response rating, or you want to leverage twice the annotation budget (individual labels are cheaper to collect than paired comparisons).

When NOT to use KTO: You have high-quality paired comparisons already. Paired comparisons provide a stronger per-example signal. Use DPO or SimPO instead.

Tip

Production Note: Many logging pipelines naturally produce KTO-compatible data — if users rate responses in your app via a thumbs up/down, you have individual binary labels. You can start KTO training without any additional annotation infrastructure.

34.3.3 SimPO: Simple Preference Optimization

What it fixes: Length bias and reference model overhead.

How: SimPO removes the reference model entirely (like ORPO) and replaces the DPO log-ratio with the average log-probability of the response under the current policy, normalized by sequence length:

\[r_{\text{SimPO}}(y|x) = \frac{1}{|y|} \sum_{t=1}^{|y|} \log \pi_\theta(y_t | x, y_{<t})\]

Because the reward is per-token average probability rather than total log-probability, longer responses do not automatically have higher reward. A concise accurate response and a verbose padded response of equal per-token quality receive identical reward signals.

SimPO also adds a target margin \(\gamma\): the chosen response must score at least \(\gamma\) higher than the rejected response, not just be higher by any amount. This margin prevents the model from satisfying the objective through trivially small differences.

\[\mathcal{L}_{\text{SimPO}} = -\mathbb{E}\left[\log \sigma\left(\frac{\beta}{|y_c|}\log \pi_\theta(y_c|x) - \frac{\beta}{|y_r|}\log \pi_\theta(y_r|x) - \gamma\right)\right]\]

When to use SimPO: Deployment contexts where response length directly impacts cost or latency (API-facing services, customer support bots), when length-controlled conciseness is a customer requirement, or when you want to eliminate the reference model forward pass to reduce memory.

34.3.4 ORPO: Odds Ratio Preference Optimization

What it fixes: Eliminates the need for a separate SFT stage and a reference model.

How: ORPO fuses SFT and alignment into a single training objective:

\[\mathcal{L}_{\text{ORPO}} = \mathcal{L}_{\text{SFT}} + \lambda \cdot \mathcal{L}_{\text{OR}}\]

where \(\mathcal{L}_{\text{SFT}}\) is the standard next-token cross-entropy on chosen responses, and \(\mathcal{L}_{\text{OR}}\) is an odds ratio penalty that increases the relative likelihood of chosen over rejected:

\[\mathcal{L}_{\text{OR}} = -\log \sigma\left(\log \frac{\text{odds}_\theta(y_c|x)}{\text{odds}_\theta(y_r|x)}\right)\]

The SFT term serves as the regularization anchor that the reference model provides in DPO — it keeps the policy close to the chosen response distribution. No frozen reference model checkpoint is needed.

Compute savings: Eliminating the reference model forward pass reduces peak GPU memory by ~50% for a given batch. A 70B model that requires 8 A100s for DPO can be aligned with 4 A100s using ORPO at the same batch size.

Risk: ORPO’s regularization is weaker on out-of-distribution inputs than DPO’s explicit KL constraint. If your preference data looks very different from the base model’s pretraining distribution, ORPO may develop pathological behavior on inputs not covered by the preference dataset. Use ORPO when adapting within a distribution that is close to pretraining; use DPO when the domain shift is large.

34.5 GRPO: Group Relative Policy Optimization

GRPO is the alignment algorithm in DeepSeek-R1. It is an online RL method that eliminates the critic model by using within-group advantage estimation.

34.5.1 How It Works

For each training prompt \(x\), GRPO samples a group of \(G\) responses \(\{y_1, \ldots, y_G\}\) from the current policy. Each response receives a reward \(r_i\) from a reward function. The advantage of each response is computed as a within-group z-score:

\[\hat{A}_i = \frac{r_i - \text{mean}(\mathbf{r})}{\text{std}(\mathbf{r})}\]

The policy gradient update reinforces responses with positive advantage (better than the group average) and penalizes responses with negative advantage:

\[\mathcal{L}_{\text{GRPO}} = -\mathbb{E}\left[\sum_{i=1}^{G} \hat{A}_i \log \pi_\theta(y_i | x)\right] + \beta \cdot D_{\text{KL}}(\pi_\theta \| \pi_{\text{ref}})\]

34.5.2 Why No Critic Is Needed

In PPO, the advantage is computed as: actual reward minus the value function \(V(s)\), where \(V(s)\) is a learned estimate of expected future reward. Computing \(V(s)\) requires a separate critic model trained in parallel with the actor — doubling model count and introducing a second unstable optimization loop.

GRPO replaces the critic by treating the group mean \(\bar{r}\) as an empirical estimate of \(V(s)\). The intuition: the group of \(G\) responses to the same prompt is a sample from the policy’s distribution for that prompt, so the sample mean is an unbiased estimator of the expected reward — exactly what a value function computes. For \(G \in [8, 16]\), this estimate has sufficient quality for stable policy gradient updates, without any learned parameters.

Analogy: Instead of having a judge who grades you against an absolute scale (the critic), GRPO has you grade yourself against your own peers on the same exam. If everyone in your group scores 70%, and you score 85%, you get positive reinforcement — even without knowing the absolute ideal score.

34.5.3 Rule-Based Rewards

DeepSeek-R1’s GRPO uses rule-based rewards, not a learned reward model: - Correctness: Does the final answer match the ground truth? (For math: numeric equality. For code: test suite pass/fail.) - Format compliance: Does the response use the required <think>...</think><answer>...</answer> structure? - Length penalty: Penalize excessively short or excessively long reasoning traces.

Rule-based rewards are deterministic, do not require training, and cannot be gamed by reward model hacking. For tasks where correctness is verifiable — math, code, structured outputs — rule-based GRPO is both simpler and more reliable than learned reward model approaches.

Warning

Reward Hacking Warning: If you use a learned reward model with GRPO, the policy can learn to exploit reward model weaknesses (e.g., generating formatting patterns the reward model rates highly regardless of content). With rule-based rewards, this failure mode is structurally impossible. Use verifiable rewards wherever the task allows it.

34.6 Constitutional AI and RLAIF

34.6.1 Constitutional AI (Anthropic)

Constitutional AI (CAI) addresses the scalability bottleneck of human annotation: instead of hiring humans to rank responses for safety and helpfulness, a strong model applies a written set of principles (the “constitution”) to critique and revise its own outputs.

The pipeline has two phases:

Phase 1 — Supervised Learning from AI Feedback (SL-CAI): 1. Generate an initial response to a potentially harmful prompt. 2. Ask the model to critique the response against a constitutional principle (“Does this response encourage harmful behavior?”). 3. Ask the model to revise the response to address the critique. 4. Repeat for multiple principles. 5. Fine-tune on the revised (safer) responses.

Phase 2 — RL from AI Feedback (RLAIF): 1. Generate pairs of responses to prompts. 2. Ask a strong model to identify which response better adheres to the constitution. 3. Use these AI-generated preference labels to train a reward model. 4. Run RL (PPO or a DPO variant) using this AI-feedback reward model.

The constitutional principles are explicit and auditable — unlike opaque human annotation guidelines, you can inspect exactly what principles shaped the model’s behavior. This makes CAI more interpretable and more adjustable than standard RLHF.

34.6.2 Scalable Oversight

As models become capable in specialized domains (advanced math, medical reasoning), the human annotators supervising them may lack the expertise to judge response quality. Scalable oversight addresses the question: how do you supervise a model that may know more than the supervisor in some domains?

Debate: Two AI agents argue opposing positions; a human judge evaluates the debate quality, not the underlying facts. The model must produce convincing arguments, and the structure of debate exposes flaws and false claims more readily than single-response evaluation.

Recursive Reward Modeling: Break complex tasks into subtasks humans can evaluate; aggregate subtask evaluations bottom-up. A human may not be able to judge a 500-page legal analysis, but they can judge whether a one-paragraph summary accurately captures a section.

Critiques: Train a model to identify errors in responses, then have humans judge whether the critique is valid — a lower-skill task than evaluating the original response directly.

34.7 Iterative DPO and Online Preference Learning

34.7.1 The Distribution Gap Problem

All offline DPO variants share a structural weakness: the preference data was collected from an earlier model, not the model currently being trained. As training progresses, the model’s distribution shifts, but the training data does not. The rejected responses in the dataset represent past failure modes, not current ones. Learning slows.

34.7.2 Iterative DPO

Iterative DPO bridges offline and fully online training by periodically refreshing the preference dataset:

for iteration in range(N_iterations):
    # Step 1: Generate fresh responses using current policy
    fresh_responses = []
    for prompt in training_prompts:
        y1 = sample(policy_current, prompt)
        y2 = sample(policy_current, prompt)
        fresh_responses.append((prompt, y1, y2))

    # Step 2: Score with reward model or rule-based judge
    preference_pairs = []
    for prompt, y1, y2 in fresh_responses:
        r1 = reward_model(prompt, y1)
        r2 = reward_model(prompt, y2)
        chosen = y1 if r1 > r2 else y2
        rejected = y2 if r1 > r2 else y1
        preference_pairs.append((prompt, chosen, rejected))

    # Step 3: Run one epoch of DPO on fresh pairs
    policy_current = train_dpo(policy_current, preference_pairs, beta=0.1)

Each iteration costs one generation pass + one training pass (~2x offline DPO), but the distribution gap is reset at every iteration. In practice, 3–5 outer iterations provide most of the quality benefit over a single offline run.

34.7.3 Rejection Sampling Fine-Tuning

A simpler variant: for each prompt, generate \(k\) responses (typically \(k \in [10, 32]\)), score all \(k\) with a reward model, keep only the top-1 or top-\(m\), and use these high-reward responses as supervised training targets. This is SFT on filtered generations — no preference pairs required. It is computationally expensive (sampling \(k\) responses per prompt) but very stable. Used as a first-pass alignment step before DPO in several frontier model pipelines.

34.8 Python: DPO Training with TRL

from datasets import Dataset
from trl import DPOConfig, DPOTrainer
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

# Load model and tokenizer
model_name = "meta-llama/Meta-Llama-3-8B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token

# Load policy and reference models
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)
model_ref = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)

# DPO expects: prompt, chosen, rejected fields
preference_data = [
    {
        "prompt": "Explain gradient descent in one sentence.",
        "chosen": "Gradient descent iteratively adjusts model parameters by moving in the direction of steepest loss decrease.",
        "rejected": "Gradient descent is an optimization algorithm used in machine learning to train models and it works by calculating gradients of the loss function with respect to parameters and then updating those parameters repeatedly over many training steps until convergence.",
    },
    # ... more examples
]

dataset = Dataset.from_list(preference_data)

# DPO configuration
training_args = DPOConfig(
    output_dir="./dpo-output",
    num_train_epochs=3,
    per_device_train_batch_size=2,
    gradient_accumulation_steps=8,
    learning_rate=5e-7,          # Lower LR than SFT; DPO is sensitive
    beta=0.1,                    # KL penalty coefficient; higher = more conservative
    max_length=1024,
    max_prompt_length=512,
    fp16=False,
    bf16=True,
    logging_steps=10,
    save_steps=500,
    warmup_ratio=0.1,
    lr_scheduler_type="cosine",
    # For SimPO: use loss_type="simpo" and add simpo_gamma
    loss_type="sigmoid",         # Standard DPO; options: "sigmoid", "ipo", "kto_pair"
)

# Initialize DPO trainer
trainer = DPOTrainer(
    model=model,
    ref_model=model_ref,
    args=training_args,
    train_dataset=dataset,
    tokenizer=tokenizer,
)

# Train
trainer.train()

# Key metrics to monitor during DPO training:
# - rewards/chosen: should increase steadily
# - rewards/rejected: should decrease steadily
# - rewards/margins: (chosen - rejected); target > 0 and increasing
# - logps/chosen, logps/rejected: watch for divergence (sign of overfitting)
# - kl_divergence: if spiking, increase beta or reduce learning rate
# GRPO-style training with rule-based rewards (simplified)
import torch
import torch.nn.functional as F
from typing import List, Tuple

def grpo_loss(
    policy_logprobs: torch.Tensor,   # (G, seq_len) log probs for G responses
    rewards: torch.Tensor,           # (G,) rewards for each response
    ref_logprobs: torch.Tensor,      # (G, seq_len) reference log probs
    beta: float = 0.01,
) -> torch.Tensor:
    """
    Compute GRPO loss for a group of G responses to the same prompt.
    policy_logprobs: summed log probs per response under current policy
    rewards: scalar reward per response (e.g., 1.0 if correct, 0.0 if not)
    ref_logprobs: summed log probs per response under reference policy
    """
    G = rewards.shape[0]

    # Within-group advantage: z-score normalization
    reward_mean = rewards.mean()
    reward_std = rewards.std() + 1e-8   # avoid division by zero
    advantages = (rewards - reward_mean) / reward_std  # (G,)

    # Policy gradient loss
    pg_loss = -(advantages * policy_logprobs).mean()

    # KL penalty against reference policy
    kl_div = (policy_logprobs - ref_logprobs).mean()

    total_loss = pg_loss + beta * kl_div
    return total_loss


def rule_based_reward(response: str, ground_truth: str) -> float:
    """
    Example rule-based reward for math problems.
    Returns 1.0 if answer is correct, 0.0 otherwise.
    Format bonus: +0.1 for using <think> tags.
    """
    import re

    # Check format compliance
    has_think_tags = bool(re.search(r'<think>.*</think>', response, re.DOTALL))
    format_bonus = 0.1 if has_think_tags else 0.0

    # Extract final answer
    answer_match = re.search(r'<answer>(.*?)</answer>', response, re.DOTALL)
    if not answer_match:
        return format_bonus  # no answer found

    predicted = answer_match.group(1).strip()

    # Normalize and compare
    def normalize(s):
        return re.sub(r'\s+', '', s.lower())

    correctness = 1.0 if normalize(predicted) == normalize(ground_truth) else 0.0
    return correctness + format_bonus
Tip

Production Gotcha — DPO Learning Rate: DPO is extremely sensitive to learning rate. The typical SFT learning rate (1e-5 to 5e-5) is too high for DPO and causes reward hacking — the model drives log-ratios to extreme values, the loss saturates, and gradient updates become noisy. Use 1e-7 to 5e-7 for DPO. Monitor rewards/margins and logps/chosen in your training logs. If logps/chosen is decreasing (the model is becoming less likely to generate the chosen response), your beta is too low or your learning rate too high.

34.9 The Production Alignment Stack in 2025

Most frontier model alignment pipelines in 2025 follow a multi-stage approach:

Stage 1 — Supervised Fine-Tuning (SFT): Train on high-quality (instruction, response) pairs. This establishes the model’s instruction-following format, tone, and domain knowledge. Quality matters more than quantity here (see the LIMA paper: 1,000 carefully curated examples outperformed 52,000 lower-quality ones on many benchmarks).

Stage 2 — Rejection Sampling: Generate \(k=32\) responses per prompt on a held-out prompt set. Score with a reward model. Keep the top-1 to top-4. SFT again on the filtered responses. This “lifts” the model toward higher-reward behaviors before DPO.

Stage 3 — Iterative DPO or Online DPO: Run 3–5 iterations of the generate-score-DPO loop. Each iteration the model is confronted with its current failure modes, not historical ones.

Stage 4 (optional) — GRPO for specific capabilities: If you need strong math or coding, add a GRPO stage with rule-based verifiable rewards after the DPO stage.

Base Model
    → SFT (instruction following, format, tone)
    → Rejection Sampling FT (lift quality ceiling)
    → Iterative DPO × 3-5 (preference alignment)
    → GRPO with rule-based rewards (math/code, if needed)
    → Final safety DPO (safety-specific preference pairs)

PPO is now reserved for very specific use cases: continuous action spaces (robotics), real-time feedback loops (game-playing), or pipelines that already have a high-quality learned reward model and the engineering infrastructure to run it stably.

34.10 Cheat Sheet

  • DPO derives alignment from KL-constrained RL by expressing reward as a log-ratio of policy to reference. No explicit reward model needed. Three limitations: offline (distribution gap), length bias, implicit KL regularization.
  • Implicit reward in DPO: \(r(y,x) = \beta \log(\pi_\theta(y|x) / \pi_{\text{ref}}(y|x))\). The policy itself is the reward model.
  • IPO replaces the sigmoid loss with a squared-error loss anchored to a target log-ratio. Prevents saturation/overfitting on small datasets.
  • KTO trains on individual (not paired) binary labels. Based on prospect theory’s asymmetric value function (\(\lambda_U > \lambda_D\)). Best when you have thumbs-up/thumbs-down logs rather than pairwise comparisons.
  • SimPO normalizes reward by sequence length (per-token average log-prob). Directly removes length bias. Adds target margin \(\gamma\). No reference model needed.
  • ORPO fuses SFT + alignment in a single pass. SFT cross-entropy serves as the regularization anchor instead of a reference model. ~50% memory savings vs DPO. Risk: weaker out-of-distribution regularization.
  • GRPO samples \(G\) responses per prompt, uses within-group reward z-scores as advantage estimates. Eliminates the critic model. Rule-based rewards (correctness, format) prevent reward hacking. Used in DeepSeek-R1.
  • Distribution gap is the core weakness of all offline methods. As the policy improves, the rejected responses in the training set no longer represent current failure modes.
  • Iterative DPO refreshes the preference dataset every \(N\) steps using the current policy. Closes the distribution gap at ~2x the compute of a single offline run.
  • Online DPO generates preference pairs continuously during training. Eliminates the distribution gap entirely. Requires careful stability engineering.
  • Rejection sampling FT: Generate \(k\) responses per prompt, keep top-\(m\) by reward score, SFT on them. Stable “pre-alignment” that lifts the model before DPO.
  • Constitutional AI: Self-critique and revision using a written constitution (set of principles). Produces safe responses without human-labeled harm examples. RLAIF extends this to preference label generation.
  • RLAIF: AI-generated preference labels (using a strong judge model) at scale. Quality depends on judge model quality. Produces datasets 100x larger than human annotation allows.
  • Reward hacking occurs when a learned reward model has exploitable weaknesses and the policy learns to score high without genuinely improving. Rule-based rewards (verifiable tasks) make reward hacking structurally impossible.
  • β hyperparameter: Controls KL penalty strength in DPO. Higher β = more conservative (stays close to reference). Typical range: 0.01–0.5. Too low → distribution collapse. Too high → barely moves from SFT.
  • Length normalization: The single most impactful intervention for concise model outputs. SimPO implements it natively. For vanilla DPO: filter training pairs to control for length or add a length penalty to the reward signal.
  • PPO memory requirement at 70B scale: actor + critic + RM + reference = 4 × 140GB = 560GB+ in FP16, before activations. This is why it is impractical without large A100/H100 clusters.
  • GRPO advantage normalization: Within-group z-score \(\hat{A}_i = (r_i - \bar{r}) / \sigma_r\). Responses better than the group average get positive advantage; worse get negative. No critic training needed.
  • SPIN (Self-Play FT): Train the model to prefer human reference responses over its own generations. Zero additional annotation. Useful when no preference pairs are available.
  • Scalable oversight (debate, RRM): Methods to supervise AI on tasks where the AI may outperform the human evaluator in domain expertise.

34.11 Interview Questions

34.11.1 Entry Level

Entry Level

Q1. What is the difference between DPO and RLHF/PPO in plain terms?

Model Answer

RLHF with PPO runs in three stages: SFT on demonstrations, train a separate reward model on human preference pairs, then use PPO to update the policy so it generates responses the reward model scores highly. Four models must be in GPU memory simultaneously during PPO: actor, critic, reward model, and reference model. This is memory-intensive, unstable, and requires RL expertise to tune.

DPO achieves the same goal with a single supervised training step. The mathematical insight: the KL-regularized RL objective used by PPO has a closed-form optimal policy. You can rearrange this to express the reward function entirely in terms of log-probability ratios between the policy and a frozen reference model. The DPO loss is therefore just binary cross-entropy on preference pairs — no RL loop, no reward model, no value function. Training is stable, debuggable with standard tools, and needs only the policy and a frozen reference model.

The tradeoff: DPO is offline and cannot explore new responses during training. PPO can discover new good behaviors through exploration. For tasks with a verifiable reward signal (math, code), GRPO with rule-based rewards is now preferred over both.

Entry Level

Q2. What does KTO offer that DPO doesn’t?

Model Answer

DPO requires matched pairs: for a given prompt, you need both a good response and a bad response collected together from the same annotation session. If you have a dataset of 10,000 individual ratings — “response A was helpful,” “response B was not helpful” — without those responses being paired to the same prompt, DPO cannot use this data.

KTO trains on individual binary-labeled responses. Each example is a (prompt, response, label) triple with a simple desirable/undesirable label. No pairing is required. This matches how many real systems collect feedback: thumbs up/down on individual responses in a chat interface, without any cross-comparison to another response on the same query.

The theoretical grounding is Kahneman-Tversky prospect theory: the loss function weights undesirable examples more heavily than desirable ones, matching the empirical finding that human annotators are more reliable at identifying clearly bad responses than at identifying the best response. KTO effectively doubles your usable annotation budget by enabling individually-rated data rather than requiring the paired annotation workflow DPO demands.

Entry Level

Q3. What is the length bias in DPO and why does it occur?

Model Answer

DPO’s objective increases the log-likelihood ratio between chosen and rejected responses. Log-likelihood is a sum over tokens — longer responses sum over more tokens and contribute more total probability mass to the numerator of the log-ratio.

Human preference annotations, collected without length controls, systematically label longer responses as “chosen.” Annotators perceive length as thoroughness. Since DPO’s gradient is driven by the labeled preference, it learns that more tokens = higher reward. The structural bias amplifies the annotation bias.

The measurable result: models fine-tuned with vanilla DPO are 20–40% more verbose on average than the SFT baseline. For a production API-facing service, that is a 20–40% higher inference bill per query.

SimPO directly addresses this by normalizing the reward signal by sequence length — the reward is the average log-probability per token, not the total. A concise accurate response and a verbose padded response of equal per-token quality receive equal reward. The length incentive is removed at the loss level.

Entry Level

Q4. What is online DPO and why is it better than standard offline DPO?

Model Answer

Offline DPO trains on a fixed dataset of preference pairs collected before training began. As the policy improves, the rejected responses in the dataset — generated by an earlier version — no longer represent the model’s current failure modes. The gradient becomes less informative over time.

Online DPO generates new responses during training using the current policy. For each batch: generate two responses, score them with a reward model, label the better one as chosen and the worse as rejected, train on this fresh pair immediately. Because the rejected responses come from the current policy, the gradient always shows the model examples of mistakes it is currently making.

The practical tradeoff: online DPO is ~2x more compute-intensive per step (generation + training vs. training only) but achieves higher final alignment quality for the same number of training steps, especially in later training stages where offline DPO stagnates. Iterative DPO is a middle ground — regenerate the preference dataset every few hundred steps rather than continuously.

Entry Level

Q5. What is Constitutional AI and why did Anthropic develop it?

Model Answer

Constitutional AI is a technique for training safe AI systems without requiring human-labeled harm examples. The core insight: you can train a model to be helpful and harmless by having a strong model apply written principles (the constitution) to critique and revise its own potentially harmful outputs.

Anthropic developed it to address the scalability bottleneck of human annotation for safety: getting humans to label a large enough set of harmful responses and their safe alternatives requires exposing annotators to harmful content at scale, which is both ethically problematic and practically expensive. Constitutional AI replaces this with AI-generated critique-revision pairs using principles that encode the desired safety properties.

The second phase (RLAIF) extends this to preference labeling: instead of humans ranking responses, a constitutional AI judge labels which of two responses better adheres to the principles. This generates preference data at orders-of-magnitude larger scale and lower cost than human annotation, while making the labeling criteria explicit and auditable in the written constitution.

34.11.2 Mid Level

Mid Level

Q1. Explain GRPO and why it doesn’t need a critic model.

Model Answer

In PPO, the advantage is: actual reward minus the value function \(V(s)\), where \(V(s)\) is a learned estimate of expected reward from state \(s\). Training \(V(s)\) requires a critic model — a second copy of the LLM trained in parallel with the actor. This doubles model count in memory and introduces a second optimization problem that must stay synchronized with the actor’s updates. The critic lagging the actor introduces bias in advantage estimates and contributes to PPO’s instability.

GRPO eliminates the critic by computing advantage empirically within a group. For each training prompt, sample \(G\) responses (typically \(G=8\) to \(G=16\)) from the current policy. Compute a reward for each response. The advantage of response \(i\) is its reward minus the group mean, divided by the group standard deviation: \(\hat{A}_i = (r_i - \bar{r}) / \sigma_r\).

This within-group z-score is an unbiased estimator of the advantage without any learned parameters. The intuition: the group of \(G\) responses to the same prompt is a sample from the policy’s output distribution for that prompt, so the sample mean approximates the expected reward — exactly what a value function computes. For \(G=8\) or \(G=16\), the estimate is noisier than a well-trained critic, but sufficient for stable policy gradient updates.

The practical advantage: no second optimization problem, no value loss coefficient to tune, no risk of critic lag. GRPO with rule-based rewards (math correctness, code test pass rates) is the current best practice for training reasoning models where correctness is verifiable.

Mid Level

Q2. Compare IPO vs. DPO — what specific overfitting problem does IPO solve?

Model Answer

DPO’s loss is \(-\log \sigma(\beta \cdot \Delta r)\) where \(\Delta r\) is the log-ratio difference between chosen and rejected. As training progresses, the model can drive \(\Delta r\) to very large values — the sigmoid approaches 1, the gradient approaches 0, and the loss goes to near zero. The model has “memorized” the preference pairs: on these specific examples, it assigns arbitrarily higher probability to chosen over rejected. But on similar examples not in the dataset, behavior is unpredictable.

This is DPO’s overfitting failure mode: the model satisfies the training loss perfectly while generalizing poorly. On small datasets (< 10,000 pairs), this can happen within a single epoch. The saturation makes subsequent training updates noisy and unstable because the gradients are near zero for most examples.

IPO replaces the sigmoid with a squared-error loss anchored to a target value \(1/(2\tau)\). The loss becomes: \((\Delta r - 1/(2\tau))^2\). This loss never saturates — there is always a non-zero gradient pulling \(\Delta r\) toward the target, preventing extreme values. The explicit target acts as a hard bound on how far the preference ratio can grow.

Practical guidance: use IPO when the preference dataset is small (< 10k pairs), when training for multiple epochs on the same data, or when you observe DPO loss hitting near-zero suspiciously early. The \(\tau\) hyperparameter needs tuning — start at \(\tau = 0.1\) and adjust based on the gradient norms during training.

Mid Level

Q3. Compare ORPO and DPO — what does ORPO eliminate and what is the risk?

Model Answer

DPO requires three forward passes per training step: policy on chosen, policy on rejected, and reference model on both (to compute the log-ratio baseline). The reference model is a frozen copy of the SFT checkpoint, kept in memory throughout training. For a 70B model at FP16, this is two 140GB models — the reference alone doubles the memory requirement.

ORPO eliminates the reference model by fusing SFT and alignment into a single loss: \(\mathcal{L}_{\text{ORPO}} = \mathcal{L}_{\text{SFT}} + \lambda \cdot \mathcal{L}_{\text{OR}}\). The SFT cross-entropy on chosen responses serves as the regularization anchor that the reference model provides in DPO — it keeps the policy close to the chosen response distribution. The odds ratio term \(\mathcal{L}_{\text{OR}}\) penalizes the policy for assigning higher probability to rejected over chosen responses. Net result: ~50% memory reduction for a given model size.

The risk: ORPO’s regularization depends on the SFT data distribution closely matching the preferred response distribution. If you are adapting a general model to a narrow domain with preference data that looks very different from pretraining — specialized legal writing, highly technical engineering documentation — the SFT anchor may not prevent the policy from developing pathological behavior on inputs not covered by the preference dataset. DPO’s explicit KL term against a fixed reference model provides stronger out-of-distribution regularization. Use ORPO for in-distribution adaptation with well-curated data; use DPO when the domain shift is large or when coverage of the preference dataset is incomplete.

Mid Level

Q4. What is KTO’s connection to prospect theory, and how does the asymmetric value function manifest in the loss?

Model Answer

Kahneman and Tversky’s prospect theory describes how humans subjectively evaluate outcomes relative to a reference point. The value function is asymmetric: losses feel approximately twice as bad as equivalent gains feel good. The function is concave for gains (diminishing marginal utility) and convex for losses (increasing marginal pain), with a steeper slope below the reference point.

KTO maps this to preference optimization. The reference point is the expected value of the model’s outputs under the current policy — estimated as a KL-penalized term \(z_0\). A desirable output is a “gain” relative to this reference; an undesirable output is a “loss.”

The asymmetry manifests in the loss weights: \(\lambda_U > \lambda_D\). The penalty for an undesirable output is larger in magnitude than the reward for a desirable output at the same quality distance from the reference. Concretely in the KTO loss, the loss function for undesirable examples uses a steeper coefficient than for desirable examples.

The practical motivation: annotators are more consistent and emphatic when rating clearly bad responses than when rating good ones. “This is wrong” is a stronger and more reliable signal than “this is good.” KTO’s asymmetric loss gives more weight to the more reliable signal. Additionally, this formulation enables training on individual labels (each evaluated against the policy distribution) rather than requiring a head-to-head comparison, which is why KTO works on unpaired data in a principled way rather than as a hack.

Mid Level

Q5. Explain the implicit reward in DPO — if there is no explicit reward model, where is the reward?

Model Answer

In the KL-constrained RL objective, the optimal policy satisfies: \(\pi^*(y|x) \propto \pi_{\text{ref}}(y|x) \exp(r(y,x)/\beta)\). Solving for \(r(y,x)\): \(r(y,x) = \beta \log(\pi^*(y|x) / \pi_{\text{ref}}(y|x)) + \beta \log Z(x)\).

This means every policy implicitly defines a reward function through its ratio to the reference model. In DPO, we are training \(\pi_\theta\) to be a good approximation of \(\pi^*\). So the implicit reward of the DPO-trained model is: \(r_\theta(y,x) = \beta \log(\pi_\theta(y|x) / \pi_{\text{ref}}(y|x))\).

The DPO-trained model can itself be used as a reward model without any additional training. You can compute a reward score for any (prompt, response) pair by computing the log-ratio under the trained policy versus the reference policy. This is directly usable for iterative DPO (use the previous DPO checkpoint as the judge for the next round), for reward model cascades, or for preference dataset filtering.

Empirically, DPO-derived implicit rewards have been shown to correlate well with human preferences on standard benchmarks, suggesting that the implicit reward is a meaningful quality signal despite never being explicitly trained on reward prediction.

Senior / Forward Deployed Engineer

Q1. Compare DPO, GRPO, and PPO. If you are training a reasoning model, which would you choose and why?

What great looks like: Understands the theoretical and practical tradeoffs of all three, correctly identifies that verifiable rewards change the calculus, and gives a concrete recommendation with caveats rather than a generic “it depends.”

Common Mistake: Recommending PPO because it is the “theoretically grounded RL algorithm” without acknowledging its practical infeasibility at 70B+ scale and the superiority of rule-based GRPO for verifiable tasks.

Model Answer

PPO is the general policy gradient method: requires actor + critic + reward model + reference model. For a 70B model, you are running 4 model copies of ~140GB each — ~560GB+ in FP16 before activations. PPO training is sensitive to clip ratio, KL coefficient, and GAE parameters, with instability that manifests as reward hacking or policy collapse rather than obvious training failures. Appropriate when: you have an extremely high-quality learned reward model, engineering infrastructure to run 4-model training stably, and a task where exploration genuinely matters (discovering behaviors not in any dataset).

DPO is offline supervised learning with a preference-derived loss. Requires only policy + reference. Stable, debuggable, and memory-efficient. Limitation: offline — the distribution gap means late training stages are less effective. Appropriate for: general preference alignment (helpfulness, tone, safety) where you have paired comparison data and do not need online exploration.

GRPO is online RL without a critic. Samples G responses per prompt, uses within-group advantage estimation. No critic, no separate reward model if using rule-based rewards. Appropriate for: tasks with verifiable correctness — math problems with numeric answers, code with test suites, structured outputs with schema validation. Rule-based rewards prevent reward hacking entirely.

For a reasoning model specifically, I would choose GRPO with rule-based rewards. Here is the reasoning:

  1. Reasoning models need to develop multi-step problem decomposition, verification, and self-correction — capabilities that require online exploration, not just offline preference imitation. GRPO samples multiple approaches per problem and reinforces ones that reach the correct answer.

  2. Mathematical and logical correctness is verifiable. You do not need a learned reward model — correctness against ground truth is deterministic. This eliminates reward hacking, which is the primary failure mode of learned-reward RL methods on reasoning tasks.

  3. The cold-start problem: reasoning in a specific format (chain-of-thought in <think> tags) must be initialized with SFT on a few thousand examples before GRPO training. Without this, GRPO from a base model produces incoherent formatting that the rule-based reward function cannot evaluate.

  4. DPO on reasoning pairs does not work as well because the chosen/rejected distinction at the response level is too coarse — a correct final answer reached through flawed reasoning may be labeled “chosen” if the final answer is right, training the model to value the conclusion without improving the intermediate reasoning. GRPO rewards correctness per response while training on the full reasoning trace.

Implementation recommendation: SFT on 5,000 format-correct reasoning examples (cold start) → GRPO with correctness + format rewards for the bulk of training → DPO on a curated set of reasoning comparison pairs for final calibration and safety.

Senior / Forward Deployed Engineer

Q2. A customer has a 7B model they want to align for a conciseness requirement — responses must be under 100 tokens on average. They have 5,000 preference pairs where shorter responses are always labeled as “chosen.” Which method would you recommend and how would you implement it?

What great looks like: Identifies the length bias problem in vanilla DPO, recommends SimPO with rationale, addresses implementation details, and flags quality risks.

Common Mistake: Recommending vanilla DPO or adding a post-hoc truncation step without addressing the root cause alignment training issue.

Model Answer

Recommendation: SimPO. Here is why the alternatives fail first.

Vanilla DPO has a structural length bias that works against this goal. The DPO loss is driven by total log-probability (sum over tokens). Even with shorter responses labeled as “chosen,” the gradient incentivizes length because longer responses contribute more probability mass. You are fighting the method’s structural bias with your preference labels — the labels will win eventually, but only partially.

IPO addresses overfitting but not length bias. ORPO is memory-efficient but also inherits the length-additive loss from the SFT cross-entropy term (though less severely than DPO). Neither directly addresses the problem.

SimPO normalizes the reward signal by sequence length — the objective is the average log-probability per token. A concise correct response and a verbose padded response of equal per-token quality receive identical reward signals. The length incentive is removed at the loss level, not through post-hoc regularization. The target margin \(\gamma\) (I would set \(\gamma = 1.0\) as a starting point for this use case) ensures the model’s preference for shorter responses is strong, not marginal.

Implementation:

Step 1 — Audit the 5,000 pairs before training. Random-sample 100 and verify: is the shorter response actually complete (same information density, just more concise) or is it truncated (missing necessary content)? Pairs where the shorter response omits necessary information train the model toward unhelpful brevity, not genuine conciseness. Remove those — you want the model to learn concision, not truncation.

Step 2 — Train with SimPO using TRL’s SimPO loss type: loss_type="simpo", beta=2.0, simpo_gamma=1.0. Monitor average response length as a primary training metric alongside reward margins.

Step 3 — Establish a held-out evaluation set of 200 prompts stratified by complexity: 50 simple queries (1-sentence answers are appropriate), 100 medium queries (3–5 sentences reasonable), 50 complex queries (10+ sentences genuinely needed). Track average length per stratum, not just overall. You want the model to be concise on simple queries without truncating complex ones.

Step 4 — Check for over-correction. If complex queries (multi-step troubleshooting, technical explanations) are producing 50-word answers that omit needed steps, add back some preference pairs where the longer response is chosen for genuinely complex queries. This teaches the model that conciseness is context-dependent, not universal.

Deployment monitoring: Log response token counts by query type after deployment. If average drops below 50 tokens overall (too aggressive), increase \(\gamma\) to raise the preference margin threshold and retrain on a 500-example subset. If responses are at 100 tokens but customer satisfaction drops, the model may be truncating valuable information — investigate by reviewing specific cases where users sent follow-up clarification requests.

Senior / Forward Deployed Engineer

Q3. A team wants to run iterative DPO on a model to reach frontier alignment quality. Walk through the full pipeline, engineering tradeoffs, and failure modes.

What great looks like: Covers all 4 stages of the loop (generate, score, build pairs, train), identifies the distribution gap as the motivating problem, discusses reward model quality as the bottleneck, and flags specific failure modes with mitigations.

Common Mistake: Describing only the training step without discussing the generation and scoring infrastructure, or treating iterative DPO as just “run DPO multiple times on the same dataset.”

Model Answer

Motivating problem: Offline DPO stagnates because the preference dataset reflects the model’s past failure modes, not current ones. After 1–2 epochs of offline DPO, the model has improved beyond what the static dataset can teach. Iterative DPO refreshes the dataset each iteration to stay diagnostic.

Pipeline:

Iteration loop (run 3–5 times):

  1. Generate: Sample 2 responses per prompt from the current policy for each prompt in the training set. Use temperature 0.7–0.9 to get diverse responses — too low and both responses are nearly identical (no preference signal), too high and responses are incoherent.

  2. Score: Run a reward model over all generated responses. This is the highest-variance component: if the reward model has systematic weaknesses, every iteration will reinforce those weaknesses. Options: (a) a separately trained RM on human preference data, (b) an implicit reward model from a previous DPO checkpoint, (c) rule-based scoring for verifiable tasks.

  3. Build pairs: For each prompt, the higher-scoring response becomes “chosen,” the lower-scoring becomes “rejected.” Filter out pairs where the score difference is below a threshold (e.g., 0.1 on a 0–1 scale) — near-tie pairs provide weak signal and can introduce noise.

  4. Train DPO: One epoch of DPO on the fresh pairs. Keep \(\beta\) constant across iterations (typically 0.1). Use a lower learning rate than the first training run (1e-7 vs 5e-7) — the model is closer to optimal and needs smaller steps.

Engineering tradeoffs:

  • Compute: 2x per iteration (generation + training) vs. single offline run. 5 iterations = 10x a single offline run. This is usually worth it for final model quality but requires planning compute budget upfront.
  • Reward model staleness: If you are using a fixed reward model across all iterations, by iteration 4 the model may have learned to score highly on the reward model’s biases rather than genuinely improving. Mitigation: use the DPO checkpoint’s implicit reward as the scoring signal — it updates each iteration and is less hackable.
  • Prompt coverage: The training set must cover the full distribution of intended deployment prompts. If iteration 1 uses a narrow prompt set, the model will overfit to that distribution. Use a diverse held-out evaluation set to detect this.

Failure modes:

  • Reward hacking per iteration: The model learns to game the reward model rather than genuinely improving. Symptom: reward scores increase each iteration but held-out human evaluation scores plateau or decline. Mitigation: use rule-based rewards for verifiable tasks; use diverse human evaluation as the ground truth metric across iterations.
  • Distribution collapse: If the generation temperature is too low, both sampled responses are nearly identical and the preference pairs are trivial. The model sees “chosen” and “rejected” responses that differ in one token — no useful gradient. Monitor average cosine similarity between chosen and rejected responses; it should stay below 0.7.
  • KL explosion: If \(\beta\) is too low, the policy moves too far from the reference model each iteration, and later iterations are operating on a model that has drifted significantly from the reference. Symptoms: logps/chosen decreasing (the model becomes less likely to generate its own preferred responses), incoherent outputs on out-of-distribution prompts. Mitigation: update the reference model every 2 iterations to the current checkpoint.
  • Prompt set staleness: If the training prompt set is fixed, later iterations improve on already-covered failure modes rather than discovering new ones. In production, refresh 20–30% of the prompt set each iteration by sampling from recent deployment logs or adding newly generated adversarial prompts.

## Why PPO-Based RLHF Fell Out of Favor

To understand modern alignment, start with the problem it is solving. PPO-based RLHF — the canonical alignment approach used in InstructGPT and early ChatGPT — works as follows: train a supervised fine-tuned (SFT) model on demonstrations; train a separate reward model on human preference pairs; use PPO (Proximal Policy Optimization) to update the policy so its responses maximize reward while staying close to the SFT baseline via a KL penalty.

This pipeline works. It is what produced the first generation of well-behaved chat models. But it requires four separate models in memory simultaneously: the actor (policy being trained), the reference model (frozen SFT copy), the reward model, and the critic (value function). For a 70B parameter model at FP16, that is four models of roughly 140GB each — over 500GB of GPU memory just for model weights, before activations or gradients. This is the most practical reason PPO fell out of favor.

Beyond memory, PPO training is sensitive in ways that make it difficult to operate reliably at scale. The value function (critic) must track the actor's improving policy or advantage estimates become biased, but the critic update is a separate optimization problem that can lag or diverge. The clip ratio, KL coefficient, and GAE parameters interact in ways that produce instability that looks like slow convergence until it suddenly looks like reward hacking or policy collapse. Debugging a PPO run on a 70B model requires specialized RL expertise and weeks of iteration.

Modern alignment is the engineering response to this: achieve equivalent or better alignment quality using simpler, more stable, more memory-efficient methods.

::: {.callout-warning}
**Common Misconception:** "PPO is the theoretically correct algorithm, and DPO-family methods are approximations."

This is backwards. DPO is not an approximation of PPO — it is an exact derivation of the optimal policy under the KL-constrained RL objective, expressed as a supervised loss. DPO's limitations are distributional (offline training) not theoretical. For tasks with verifiable rewards (math, code), GRPO with rule-based rewards is strictly stronger than learned-reward PPO.
:::

## DPO: The Implicit Reward Formulation

### How DPO Works

Direct Preference Optimization (DPO) derives a supervised training objective directly from the same KL-constrained RL problem that PPO solves. The key insight is that the KL-regularized RL objective has a closed-form optimal policy:

$$\pi^*(y|x) = \frac{1}{Z(x)} \pi_{\text{ref}}(y|x) \exp\left(\frac{r(y,x)}{\beta}\right)$$

where $Z(x)$ is the partition function (intractable in general). Rearranging for $r(y,x)$:

$$r(y,x) = \beta \log \frac{\pi^*(y|x)}{\pi_{\text{ref}}(y|x)} + \beta \log Z(x)$$

The $\log Z(x)$ term cancels when you take the difference between chosen and rejected rewards in a Bradley-Terry model. The final DPO loss is:

$$\mathcal{L}_{\text{DPO}} = -\mathbb{E}_{(x, y_c, y_r) \sim \mathcal{D}} \left[ \log \sigma \left( \beta \log \frac{\pi_\theta(y_c|x)}{\pi_{\text{ref}}(y_c|x)} - \beta \log \frac{\pi_\theta(y_r|x)}{\pi_{\text{ref}}(y_r|x)} \right) \right]$$

This is just binary cross-entropy on a log-ratio difference. No reward model. No value function. No RL loop. The reward is implicit in the policy itself: a model trained with DPO has an implicit reward function equal to $\beta \log(\pi_\theta / \pi_{\text{ref}})$.

**Analogy:** DPO is like learning the rules of chess by watching games and noting which moves led to wins — you never need to explicitly encode a scoring function, the preference signal is already in the game records.

### DPO's Three Structural Limitations

**1. The Distribution Gap (Offline Training)**

DPO is an offline algorithm. The preference pairs $\{(x, y_c, y_r)\}$ are collected before training starts, from some earlier model version. As training proceeds and the policy improves, the rejected responses in the dataset no longer represent current failure modes — they represent past ones. The learning signal weakens because the training data is increasingly unrepresentative of what the current model does wrong.

**2. Length Bias**

DPO's log-likelihood is a sum over tokens. Longer responses contribute more total probability mass. Human annotators, presented with two responses without length controls, systematically prefer longer responses because length correlates with perceived thoroughness. The result: DPO training learns that more tokens = more reward. Models fine-tuned with vanilla DPO produce responses 20–40% longer on average than the SFT baseline. At API scale, this is a direct cost — 30% more tokens means 30% higher inference bills.

**3. Implicit KL Regularization**

The KL term is controlled indirectly via the $\beta$ hyperparameter. For prompts not well covered by the preference dataset, the policy can drift arbitrarily far from the reference model without incurring a strong penalty. This causes degenerate behavior on out-of-distribution inputs.

## DPO Variants

### IPO: Identity Preference Optimization

**What it fixes:** Overfitting on small datasets.

**How:** DPO's sigmoid loss saturates — when the log-ratio difference grows large, the gradient approaches zero and training effectively stops. The model can overfit to the preference dataset without any signal to stop. IPO replaces the sigmoid loss with a squared error loss anchored to a target log-ratio of $1/(2\tau)$:

$$\mathcal{L}_{\text{IPO}} = \mathbb{E}\left[\left(\log \frac{\pi_\theta(y_c|x)}{\pi_{\text{ref}}(y_c|x)} - \log \frac{\pi_\theta(y_r|x)}{\pi_{\text{ref}}(y_r|x)} - \frac{1}{2\tau}\right)^2\right]$$

The loss never saturates — there is always a gradient pulling the log-ratio toward the target. This prevents the extreme probability assignments that cause DPO to overfit.

| Dataset Size | Recommended Method |
|---|---|
| < 5,000 pairs | IPO (prevents overfitting) |
| 5,000–50,000 pairs | DPO or IPO equivalent |
| > 50,000 pairs | DPO, SimPO, or online DPO |

**When to use IPO:** Small preference datasets (< 10k pairs), long training runs on the same data, or when you observe DPO loss going to zero suspiciously early.

### KTO: Kahneman-Tversky Optimization

**What it fixes:** Removes the requirement for paired comparisons.

**Plain English:** DPO requires two responses to the same prompt — one good, one bad — collected together. KTO only needs individual labeled responses: "this was good," "this was bad." No pairing required.

**Theoretical Basis:** Kahneman and Tversky's prospect theory shows that humans weight losses more than equivalent gains — a loss of $100 hurts roughly twice as much as a gain of $100 feels good. KTO maps this to alignment: the training objective penalizes undesirable outputs more steeply than it rewards desirable ones, using the KL divergence of the current policy from the reference as a reference point.

$$\mathcal{L}_{\text{KTO}} = \mathbb{E}\left[\lambda_D \cdot \sigma\left(\beta \cdot (r_\theta(x,y) - z_0)\right) \cdot \mathbf{1}[y \text{ desirable}] - \lambda_U \cdot \sigma\left(\beta \cdot (z_0 - r_\theta(x,y))\right) \cdot \mathbf{1}[y \text{ undesirable}]\right]$$

where $\lambda_U > \lambda_D$ encodes the asymmetric weighting, and $z_0 = \beta \log Z(x)$ is the reference value.

**Analogy:** KTO is like a teacher who grades work individually — each assignment gets a pass/fail without needing to compare it to another student's work on the same question.

**When to use KTO:** You have individual binary-labeled responses (not matched pairs), annotation was collected via thumbs up/down or similar single-response rating, or you want to leverage twice the annotation budget (individual labels are cheaper to collect than paired comparisons).

**When NOT to use KTO:** You have high-quality paired comparisons already. Paired comparisons provide a stronger per-example signal. Use DPO or SimPO instead.

::: {.callout-tip}
**Production Note:** Many logging pipelines naturally produce KTO-compatible data — if users rate responses in your app via a thumbs up/down, you have individual binary labels. You can start KTO training without any additional annotation infrastructure.
:::

### SimPO: Simple Preference Optimization

**What it fixes:** Length bias and reference model overhead.

**How:** SimPO removes the reference model entirely (like ORPO) and replaces the DPO log-ratio with the average log-probability of the response under the current policy, normalized by sequence length:

$$r_{\text{SimPO}}(y|x) = \frac{1}{|y|} \sum_{t=1}^{|y|} \log \pi_\theta(y_t | x, y_{<t})$$

Because the reward is per-token average probability rather than total log-probability, longer responses do not automatically have higher reward. A concise accurate response and a verbose padded response of equal per-token quality receive identical reward signals.

SimPO also adds a target margin $\gamma$: the chosen response must score at least $\gamma$ higher than the rejected response, not just be higher by any amount. This margin prevents the model from satisfying the objective through trivially small differences.

$$\mathcal{L}_{\text{SimPO}} = -\mathbb{E}\left[\log \sigma\left(\frac{\beta}{|y_c|}\log \pi_\theta(y_c|x) - \frac{\beta}{|y_r|}\log \pi_\theta(y_r|x) - \gamma\right)\right]$$

**When to use SimPO:** Deployment contexts where response length directly impacts cost or latency (API-facing services, customer support bots), when length-controlled conciseness is a customer requirement, or when you want to eliminate the reference model forward pass to reduce memory.

### ORPO: Odds Ratio Preference Optimization

**What it fixes:** Eliminates the need for a separate SFT stage and a reference model.

**How:** ORPO fuses SFT and alignment into a single training objective:

$$\mathcal{L}_{\text{ORPO}} = \mathcal{L}_{\text{SFT}} + \lambda \cdot \mathcal{L}_{\text{OR}}$$

where $\mathcal{L}_{\text{SFT}}$ is the standard next-token cross-entropy on chosen responses, and $\mathcal{L}_{\text{OR}}$ is an odds ratio penalty that increases the relative likelihood of chosen over rejected:

$$\mathcal{L}_{\text{OR}} = -\log \sigma\left(\log \frac{\text{odds}_\theta(y_c|x)}{\text{odds}_\theta(y_r|x)}\right)$$

The SFT term serves as the regularization anchor that the reference model provides in DPO — it keeps the policy close to the chosen response distribution. No frozen reference model checkpoint is needed.

**Compute savings:** Eliminating the reference model forward pass reduces peak GPU memory by ~50% for a given batch. A 70B model that requires 8 A100s for DPO can be aligned with 4 A100s using ORPO at the same batch size.

**Risk:** ORPO's regularization is weaker on out-of-distribution inputs than DPO's explicit KL constraint. If your preference data looks very different from the base model's pretraining distribution, ORPO may develop pathological behavior on inputs not covered by the preference dataset. Use ORPO when adapting within a distribution that is close to pretraining; use DPO when the domain shift is large.

## GRPO: Group Relative Policy Optimization

GRPO is the alignment algorithm in DeepSeek-R1. It is an online RL method that eliminates the critic model by using within-group advantage estimation.

### How It Works

For each training prompt $x$, GRPO samples a group of $G$ responses $\{y_1, \ldots, y_G\}$ from the current policy. Each response receives a reward $r_i$ from a reward function. The advantage of each response is computed as a within-group z-score:

$$\hat{A}_i = \frac{r_i - \text{mean}(\mathbf{r})}{\text{std}(\mathbf{r})}$$

The policy gradient update reinforces responses with positive advantage (better than the group average) and penalizes responses with negative advantage:

$$\mathcal{L}_{\text{GRPO}} = -\mathbb{E}\left[\sum_{i=1}^{G} \hat{A}_i \log \pi_\theta(y_i | x)\right] + \beta \cdot D_{\text{KL}}(\pi_\theta \| \pi_{\text{ref}})$$

### Why No Critic Is Needed

In PPO, the advantage is computed as: actual reward minus the value function $V(s)$, where $V(s)$ is a learned estimate of expected future reward. Computing $V(s)$ requires a separate critic model trained in parallel with the actor — doubling model count and introducing a second unstable optimization loop.

GRPO replaces the critic by treating the group mean $\bar{r}$ as an empirical estimate of $V(s)$. The intuition: the group of $G$ responses to the same prompt is a sample from the policy's distribution for that prompt, so the sample mean is an unbiased estimator of the expected reward — exactly what a value function computes. For $G \in [8, 16]$, this estimate has sufficient quality for stable policy gradient updates, without any learned parameters.

**Analogy:** Instead of having a judge who grades you against an absolute scale (the critic), GRPO has you grade yourself against your own peers on the same exam. If everyone in your group scores 70%, and you score 85%, you get positive reinforcement — even without knowing the absolute ideal score.

### Rule-Based Rewards

DeepSeek-R1's GRPO uses rule-based rewards, not a learned reward model:
- **Correctness:** Does the final answer match the ground truth? (For math: numeric equality. For code: test suite pass/fail.)
- **Format compliance:** Does the response use the required `<think>...</think><answer>...</answer>` structure?
- **Length penalty:** Penalize excessively short or excessively long reasoning traces.

Rule-based rewards are deterministic, do not require training, and cannot be gamed by reward model hacking. For tasks where correctness is verifiable — math, code, structured outputs — rule-based GRPO is both simpler and more reliable than learned reward model approaches.

::: {.callout-warning}
**Reward Hacking Warning:** If you use a learned reward model with GRPO, the policy can learn to exploit reward model weaknesses (e.g., generating formatting patterns the reward model rates highly regardless of content). With rule-based rewards, this failure mode is structurally impossible. Use verifiable rewards wherever the task allows it.
:::

## Constitutional AI and RLAIF

### Constitutional AI (Anthropic)

Constitutional AI (CAI) addresses the scalability bottleneck of human annotation: instead of hiring humans to rank responses for safety and helpfulness, a strong model applies a written set of principles (the "constitution") to critique and revise its own outputs.

The pipeline has two phases:

**Phase 1 — Supervised Learning from AI Feedback (SL-CAI):**
1. Generate an initial response to a potentially harmful prompt.
2. Ask the model to critique the response against a constitutional principle ("Does this response encourage harmful behavior?").
3. Ask the model to revise the response to address the critique.
4. Repeat for multiple principles.
5. Fine-tune on the revised (safer) responses.

**Phase 2 — RL from AI Feedback (RLAIF):**
1. Generate pairs of responses to prompts.
2. Ask a strong model to identify which response better adheres to the constitution.
3. Use these AI-generated preference labels to train a reward model.
4. Run RL (PPO or a DPO variant) using this AI-feedback reward model.

The constitutional principles are explicit and auditable — unlike opaque human annotation guidelines, you can inspect exactly what principles shaped the model's behavior. This makes CAI more interpretable and more adjustable than standard RLHF.

### Scalable Oversight

As models become capable in specialized domains (advanced math, medical reasoning), the human annotators supervising them may lack the expertise to judge response quality. Scalable oversight addresses the question: how do you supervise a model that may know more than the supervisor in some domains?

**Debate:** Two AI agents argue opposing positions; a human judge evaluates the debate quality, not the underlying facts. The model must produce convincing arguments, and the structure of debate exposes flaws and false claims more readily than single-response evaluation.

**Recursive Reward Modeling:** Break complex tasks into subtasks humans can evaluate; aggregate subtask evaluations bottom-up. A human may not be able to judge a 500-page legal analysis, but they can judge whether a one-paragraph summary accurately captures a section.

**Critiques:** Train a model to identify errors in responses, then have humans judge whether the critique is valid — a lower-skill task than evaluating the original response directly.

## Iterative DPO and Online Preference Learning

### The Distribution Gap Problem

All offline DPO variants share a structural weakness: the preference data was collected from an earlier model, not the model currently being trained. As training progresses, the model's distribution shifts, but the training data does not. The rejected responses in the dataset represent past failure modes, not current ones. Learning slows.

### Iterative DPO

Iterative DPO bridges offline and fully online training by periodically refreshing the preference dataset:

```
for iteration in range(N_iterations):
    # Step 1: Generate fresh responses using current policy
    fresh_responses = []
    for prompt in training_prompts:
        y1 = sample(policy_current, prompt)
        y2 = sample(policy_current, prompt)
        fresh_responses.append((prompt, y1, y2))

    # Step 2: Score with reward model or rule-based judge
    preference_pairs = []
    for prompt, y1, y2 in fresh_responses:
        r1 = reward_model(prompt, y1)
        r2 = reward_model(prompt, y2)
        chosen = y1 if r1 > r2 else y2
        rejected = y2 if r1 > r2 else y1
        preference_pairs.append((prompt, chosen, rejected))

    # Step 3: Run one epoch of DPO on fresh pairs
    policy_current = train_dpo(policy_current, preference_pairs, beta=0.1)
```

Each iteration costs one generation pass + one training pass (~2x offline DPO), but the distribution gap is reset at every iteration. In practice, 3–5 outer iterations provide most of the quality benefit over a single offline run.

### Rejection Sampling Fine-Tuning

A simpler variant: for each prompt, generate $k$ responses (typically $k \in [10, 32]$), score all $k$ with a reward model, keep only the top-1 or top-$m$, and use these high-reward responses as supervised training targets. This is SFT on filtered generations — no preference pairs required. It is computationally expensive (sampling $k$ responses per prompt) but very stable. Used as a first-pass alignment step before DPO in several frontier model pipelines.

```python
# GRPO-style training with rule-based rewards (simplified)
import torch
import torch.nn.functional as F
from typing import List, Tuple

def grpo_loss(
    policy_logprobs: torch.Tensor,   # (G, seq_len) log probs for G responses
    rewards: torch.Tensor,           # (G,) rewards for each response
    ref_logprobs: torch.Tensor,      # (G, seq_len) reference log probs
    beta: float = 0.01,
) -> torch.Tensor:
    """
    Compute GRPO loss for a group of G responses to the same prompt.
    policy_logprobs: summed log probs per response under current policy
    rewards: scalar reward per response (e.g., 1.0 if correct, 0.0 if not)
    ref_logprobs: summed log probs per response under reference policy
    """
    G = rewards.shape[0]

    # Within-group advantage: z-score normalization
    reward_mean = rewards.mean()
    reward_std = rewards.std() + 1e-8   # avoid division by zero
    advantages = (rewards - reward_mean) / reward_std  # (G,)

    # Policy gradient loss
    pg_loss = -(advantages * policy_logprobs).mean()

    # KL penalty against reference policy
    kl_div = (policy_logprobs - ref_logprobs).mean()

    total_loss = pg_loss + beta * kl_div
    return total_loss


def rule_based_reward(response: str, ground_truth: str) -> float:
    """
    Example rule-based reward for math problems.
    Returns 1.0 if answer is correct, 0.0 otherwise.
    Format bonus: +0.1 for using <think> tags.
    """
    import re

    # Check format compliance
    has_think_tags = bool(re.search(r'<think>.*</think>', response, re.DOTALL))
    format_bonus = 0.1 if has_think_tags else 0.0

    # Extract final answer
    answer_match = re.search(r'<answer>(.*?)</answer>', response, re.DOTALL)
    if not answer_match:
        return format_bonus  # no answer found

    predicted = answer_match.group(1).strip()

    # Normalize and compare
    def normalize(s):
        return re.sub(r'\s+', '', s.lower())

    correctness = 1.0 if normalize(predicted) == normalize(ground_truth) else 0.0
    return correctness + format_bonus
```

**Production Gotcha — DPO Learning Rate:** DPO is extremely sensitive to learning rate. The typical SFT learning rate (1e-5 to 5e-5) is too high for DPO and causes reward hacking — the model drives log-ratios to extreme values, the loss saturates, and gradient updates become noisy. Use 1e-7 to 5e-7 for DPO. Monitor `rewards/margins` and `logps/chosen` in your training logs. If `logps/chosen` is decreasing (the model is becoming less likely to generate the chosen response), your beta is too low or your learning rate too high.
:::

## The Production Alignment Stack in 2025

Most frontier model alignment pipelines in 2025 follow a multi-stage approach:

**Stage 1 — Supervised Fine-Tuning (SFT):** Train on high-quality (instruction, response) pairs. This establishes the model's instruction-following format, tone, and domain knowledge. Quality matters more than quantity here (see the LIMA paper: 1,000 carefully curated examples outperformed 52,000 lower-quality ones on many benchmarks).

**Stage 2 — Rejection Sampling:** Generate $k=32$ responses per prompt on a held-out prompt set. Score with a reward model. Keep the top-1 to top-4. SFT again on the filtered responses. This "lifts" the model toward higher-reward behaviors before DPO.

**Stage 3 — Iterative DPO or Online DPO:** Run 3–5 iterations of the generate-score-DPO loop. Each iteration the model is confronted with its current failure modes, not historical ones.

**Stage 4 (optional) — GRPO for specific capabilities:** If you need strong math or coding, add a GRPO stage with rule-based verifiable rewards after the DPO stage.

```
Base Model
    → SFT (instruction following, format, tone)
    → Rejection Sampling FT (lift quality ceiling)
    → Iterative DPO × 3-5 (preference alignment)
    → GRPO with rule-based rewards (math/code, if needed)
    → Final safety DPO (safety-specific preference pairs)
```

PPO is now reserved for very specific use cases: continuous action spaces (robotics), real-time feedback loops (game-playing), or pipelines that already have a high-quality learned reward model and the engineering infrastructure to run it stably.

## Cheat Sheet

- **DPO** derives alignment from KL-constrained RL by expressing reward as a log-ratio of policy to reference. No explicit reward model needed. Three limitations: offline (distribution gap), length bias, implicit KL regularization.
- **Implicit reward in DPO:** $r(y,x) = \beta \log(\pi_\theta(y|x) / \pi_{\text{ref}}(y|x))$. The policy itself is the reward model.
- **IPO** replaces the sigmoid loss with a squared-error loss anchored to a target log-ratio. Prevents saturation/overfitting on small datasets.
- **KTO** trains on individual (not paired) binary labels. Based on prospect theory's asymmetric value function ($\lambda_U > \lambda_D$). Best when you have thumbs-up/thumbs-down logs rather than pairwise comparisons.
- **SimPO** normalizes reward by sequence length (per-token average log-prob). Directly removes length bias. Adds target margin $\gamma$. No reference model needed.
- **ORPO** fuses SFT + alignment in a single pass. SFT cross-entropy serves as the regularization anchor instead of a reference model. ~50% memory savings vs DPO. Risk: weaker out-of-distribution regularization.
- **GRPO** samples $G$ responses per prompt, uses within-group reward z-scores as advantage estimates. Eliminates the critic model. Rule-based rewards (correctness, format) prevent reward hacking. Used in DeepSeek-R1.
- **Distribution gap** is the core weakness of all offline methods. As the policy improves, the rejected responses in the training set no longer represent current failure modes.
- **Iterative DPO** refreshes the preference dataset every $N$ steps using the current policy. Closes the distribution gap at ~2x the compute of a single offline run.
- **Online DPO** generates preference pairs continuously during training. Eliminates the distribution gap entirely. Requires careful stability engineering.
- **Rejection sampling FT:** Generate $k$ responses per prompt, keep top-$m$ by reward score, SFT on them. Stable "pre-alignment" that lifts the model before DPO.
- **Constitutional AI:** Self-critique and revision using a written constitution (set of principles). Produces safe responses without human-labeled harm examples. RLAIF extends this to preference label generation.
- **RLAIF:** AI-generated preference labels (using a strong judge model) at scale. Quality depends on judge model quality. Produces datasets 100x larger than human annotation allows.
- **Reward hacking** occurs when a learned reward model has exploitable weaknesses and the policy learns to score high without genuinely improving. Rule-based rewards (verifiable tasks) make reward hacking structurally impossible.
- **β hyperparameter:** Controls KL penalty strength in DPO. Higher β = more conservative (stays close to reference). Typical range: 0.01–0.5. Too low → distribution collapse. Too high → barely moves from SFT.
- **Length normalization:** The single most impactful intervention for concise model outputs. SimPO implements it natively. For vanilla DPO: filter training pairs to control for length or add a length penalty to the reward signal.
- **PPO memory requirement** at 70B scale: actor + critic + RM + reference = 4 × 140GB = 560GB+ in FP16, before activations. This is why it is impractical without large A100/H100 clusters.
- **GRPO advantage normalization:** Within-group z-score $\hat{A}_i = (r_i - \bar{r}) / \sigma_r$. Responses better than the group average get positive advantage; worse get negative. No critic training needed.
- **SPIN (Self-Play FT):** Train the model to prefer human reference responses over its own generations. Zero additional annotation. Useful when no preference pairs are available.
- **Scalable oversight** (debate, RRM): Methods to supervise AI on tasks where the AI may outperform the human evaluator in domain expertise.

## Interview Questions

### Entry Level

::: {.callout-tip title="Entry Level"}
**Q1. What is the difference between DPO and RLHF/PPO in plain terms?**

::: {.callout-note collapse="true" title="Model Answer"}
RLHF with PPO runs in three stages: SFT on demonstrations, train a separate reward model on human preference pairs, then use PPO to update the policy so it generates responses the reward model scores highly. Four models must be in GPU memory simultaneously during PPO: actor, critic, reward model, and reference model. This is memory-intensive, unstable, and requires RL expertise to tune.

DPO achieves the same goal with a single supervised training step. The mathematical insight: the KL-regularized RL objective used by PPO has a closed-form optimal policy. You can rearrange this to express the reward function entirely in terms of log-probability ratios between the policy and a frozen reference model. The DPO loss is therefore just binary cross-entropy on preference pairs — no RL loop, no reward model, no value function. Training is stable, debuggable with standard tools, and needs only the policy and a frozen reference model.

The tradeoff: DPO is offline and cannot explore new responses during training. PPO can discover new good behaviors through exploration. For tasks with a verifiable reward signal (math, code), GRPO with rule-based rewards is now preferred over both.
:::
:::

::: {.callout-tip title="Entry Level"}
**Q2. What does KTO offer that DPO doesn't?**

::: {.callout-note collapse="true" title="Model Answer"}
DPO requires matched pairs: for a given prompt, you need both a good response and a bad response collected together from the same annotation session. If you have a dataset of 10,000 individual ratings — "response A was helpful," "response B was not helpful" — without those responses being paired to the same prompt, DPO cannot use this data.

KTO trains on individual binary-labeled responses. Each example is a (prompt, response, label) triple with a simple desirable/undesirable label. No pairing is required. This matches how many real systems collect feedback: thumbs up/down on individual responses in a chat interface, without any cross-comparison to another response on the same query.

The theoretical grounding is Kahneman-Tversky prospect theory: the loss function weights undesirable examples more heavily than desirable ones, matching the empirical finding that human annotators are more reliable at identifying clearly bad responses than at identifying the best response. KTO effectively doubles your usable annotation budget by enabling individually-rated data rather than requiring the paired annotation workflow DPO demands.
:::
:::

::: {.callout-tip title="Entry Level"}
**Q3. What is the length bias in DPO and why does it occur?**

::: {.callout-note collapse="true" title="Model Answer"}
DPO's objective increases the log-likelihood ratio between chosen and rejected responses. Log-likelihood is a sum over tokens — longer responses sum over more tokens and contribute more total probability mass to the numerator of the log-ratio.

Human preference annotations, collected without length controls, systematically label longer responses as "chosen." Annotators perceive length as thoroughness. Since DPO's gradient is driven by the labeled preference, it learns that more tokens = higher reward. The structural bias amplifies the annotation bias.

The measurable result: models fine-tuned with vanilla DPO are 20–40% more verbose on average than the SFT baseline. For a production API-facing service, that is a 20–40% higher inference bill per query.

SimPO directly addresses this by normalizing the reward signal by sequence length — the reward is the average log-probability per token, not the total. A concise accurate response and a verbose padded response of equal per-token quality receive equal reward. The length incentive is removed at the loss level.
:::
:::

::: {.callout-tip title="Entry Level"}
**Q4. What is online DPO and why is it better than standard offline DPO?**

::: {.callout-note collapse="true" title="Model Answer"}
Offline DPO trains on a fixed dataset of preference pairs collected before training began. As the policy improves, the rejected responses in the dataset — generated by an earlier version — no longer represent the model's current failure modes. The gradient becomes less informative over time.

Online DPO generates new responses during training using the current policy. For each batch: generate two responses, score them with a reward model, label the better one as chosen and the worse as rejected, train on this fresh pair immediately. Because the rejected responses come from the current policy, the gradient always shows the model examples of mistakes it is currently making.

The practical tradeoff: online DPO is ~2x more compute-intensive per step (generation + training vs. training only) but achieves higher final alignment quality for the same number of training steps, especially in later training stages where offline DPO stagnates. Iterative DPO is a middle ground — regenerate the preference dataset every few hundred steps rather than continuously.
:::
:::

::: {.callout-tip title="Entry Level"}
**Q5. What is Constitutional AI and why did Anthropic develop it?**

::: {.callout-note collapse="true" title="Model Answer"}
Constitutional AI is a technique for training safe AI systems without requiring human-labeled harm examples. The core insight: you can train a model to be helpful and harmless by having a strong model apply written principles (the constitution) to critique and revise its own potentially harmful outputs.

Anthropic developed it to address the scalability bottleneck of human annotation for safety: getting humans to label a large enough set of harmful responses and their safe alternatives requires exposing annotators to harmful content at scale, which is both ethically problematic and practically expensive. Constitutional AI replaces this with AI-generated critique-revision pairs using principles that encode the desired safety properties.

The second phase (RLAIF) extends this to preference labeling: instead of humans ranking responses, a constitutional AI judge labels which of two responses better adheres to the principles. This generates preference data at orders-of-magnitude larger scale and lower cost than human annotation, while making the labeling criteria explicit and auditable in the written constitution.
:::

### Mid Level

::: {.callout-warning title="Mid Level"}
**Q1. Explain GRPO and why it doesn't need a critic model.**

::: {.callout-note collapse="true" title="Model Answer"}
In PPO, the advantage is: actual reward minus the value function $V(s)$, where $V(s)$ is a learned estimate of expected reward from state $s$. Training $V(s)$ requires a critic model — a second copy of the LLM trained in parallel with the actor. This doubles model count in memory and introduces a second optimization problem that must stay synchronized with the actor's updates. The critic lagging the actor introduces bias in advantage estimates and contributes to PPO's instability.

GRPO eliminates the critic by computing advantage empirically within a group. For each training prompt, sample $G$ responses (typically $G=8$ to $G=16$) from the current policy. Compute a reward for each response. The advantage of response $i$ is its reward minus the group mean, divided by the group standard deviation: $\hat{A}_i = (r_i - \bar{r}) / \sigma_r$.

This within-group z-score is an unbiased estimator of the advantage without any learned parameters. The intuition: the group of $G$ responses to the same prompt is a sample from the policy's output distribution for that prompt, so the sample mean approximates the expected reward — exactly what a value function computes. For $G=8$ or $G=16$, the estimate is noisier than a well-trained critic, but sufficient for stable policy gradient updates.

The practical advantage: no second optimization problem, no value loss coefficient to tune, no risk of critic lag. GRPO with rule-based rewards (math correctness, code test pass rates) is the current best practice for training reasoning models where correctness is verifiable.
:::
:::

::: {.callout-warning title="Mid Level"}
**Q2. Compare IPO vs. DPO — what specific overfitting problem does IPO solve?**

::: {.callout-note collapse="true" title="Model Answer"}
DPO's loss is $-\log \sigma(\beta \cdot \Delta r)$ where $\Delta r$ is the log-ratio difference between chosen and rejected. As training progresses, the model can drive $\Delta r$ to very large values — the sigmoid approaches 1, the gradient approaches 0, and the loss goes to near zero. The model has "memorized" the preference pairs: on these specific examples, it assigns arbitrarily higher probability to chosen over rejected. But on similar examples not in the dataset, behavior is unpredictable.

This is DPO's overfitting failure mode: the model satisfies the training loss perfectly while generalizing poorly. On small datasets (< 10,000 pairs), this can happen within a single epoch. The saturation makes subsequent training updates noisy and unstable because the gradients are near zero for most examples.

IPO replaces the sigmoid with a squared-error loss anchored to a target value $1/(2\tau)$. The loss becomes: $(\Delta r - 1/(2\tau))^2$. This loss never saturates — there is always a non-zero gradient pulling $\Delta r$ toward the target, preventing extreme values. The explicit target acts as a hard bound on how far the preference ratio can grow.

Practical guidance: use IPO when the preference dataset is small (< 10k pairs), when training for multiple epochs on the same data, or when you observe DPO loss hitting near-zero suspiciously early. The $\tau$ hyperparameter needs tuning — start at $\tau = 0.1$ and adjust based on the gradient norms during training.
:::
:::

::: {.callout-warning title="Mid Level"}
**Q3. Compare ORPO and DPO — what does ORPO eliminate and what is the risk?**

::: {.callout-note collapse="true" title="Model Answer"}
DPO requires three forward passes per training step: policy on chosen, policy on rejected, and reference model on both (to compute the log-ratio baseline). The reference model is a frozen copy of the SFT checkpoint, kept in memory throughout training. For a 70B model at FP16, this is two 140GB models — the reference alone doubles the memory requirement.

ORPO eliminates the reference model by fusing SFT and alignment into a single loss: $\mathcal{L}_{\text{ORPO}} = \mathcal{L}_{\text{SFT}} + \lambda \cdot \mathcal{L}_{\text{OR}}$. The SFT cross-entropy on chosen responses serves as the regularization anchor that the reference model provides in DPO — it keeps the policy close to the chosen response distribution. The odds ratio term $\mathcal{L}_{\text{OR}}$ penalizes the policy for assigning higher probability to rejected over chosen responses. Net result: ~50% memory reduction for a given model size.

The risk: ORPO's regularization depends on the SFT data distribution closely matching the preferred response distribution. If you are adapting a general model to a narrow domain with preference data that looks very different from pretraining — specialized legal writing, highly technical engineering documentation — the SFT anchor may not prevent the policy from developing pathological behavior on inputs not covered by the preference dataset. DPO's explicit KL term against a fixed reference model provides stronger out-of-distribution regularization. Use ORPO for in-distribution adaptation with well-curated data; use DPO when the domain shift is large or when coverage of the preference dataset is incomplete.
:::
:::

::: {.callout-warning title="Mid Level"}
**Q4. What is KTO's connection to prospect theory, and how does the asymmetric value function manifest in the loss?**

::: {.callout-note collapse="true" title="Model Answer"}
Kahneman and Tversky's prospect theory describes how humans subjectively evaluate outcomes relative to a reference point. The value function is asymmetric: losses feel approximately twice as bad as equivalent gains feel good. The function is concave for gains (diminishing marginal utility) and convex for losses (increasing marginal pain), with a steeper slope below the reference point.

KTO maps this to preference optimization. The reference point is the expected value of the model's outputs under the current policy — estimated as a KL-penalized term $z_0$. A desirable output is a "gain" relative to this reference; an undesirable output is a "loss."

The asymmetry manifests in the loss weights: $\lambda_U > \lambda_D$. The penalty for an undesirable output is larger in magnitude than the reward for a desirable output at the same quality distance from the reference. Concretely in the KTO loss, the loss function for undesirable examples uses a steeper coefficient than for desirable examples.

The practical motivation: annotators are more consistent and emphatic when rating clearly bad responses than when rating good ones. "This is wrong" is a stronger and more reliable signal than "this is good." KTO's asymmetric loss gives more weight to the more reliable signal. Additionally, this formulation enables training on individual labels (each evaluated against the policy distribution) rather than requiring a head-to-head comparison, which is why KTO works on unpaired data in a principled way rather than as a hack.
:::
:::

::: {.callout-warning title="Mid Level"}
**Q5. Explain the implicit reward in DPO — if there is no explicit reward model, where is the reward?**

::: {.callout-note collapse="true" title="Model Answer"}
In the KL-constrained RL objective, the optimal policy satisfies: $\pi^*(y|x) \propto \pi_{\text{ref}}(y|x) \exp(r(y,x)/\beta)$. Solving for $r(y,x)$: $r(y,x) = \beta \log(\pi^*(y|x) / \pi_{\text{ref}}(y|x)) + \beta \log Z(x)$.

This means every policy implicitly defines a reward function through its ratio to the reference model. In DPO, we are training $\pi_\theta$ to be a good approximation of $\pi^*$. So the implicit reward of the DPO-trained model is: $r_\theta(y,x) = \beta \log(\pi_\theta(y|x) / \pi_{\text{ref}}(y|x))$.

The DPO-trained model can itself be used as a reward model without any additional training. You can compute a reward score for any (prompt, response) pair by computing the log-ratio under the trained policy versus the reference policy. This is directly usable for iterative DPO (use the previous DPO checkpoint as the judge for the next round), for reward model cascades, or for preference dataset filtering.

Empirically, DPO-derived implicit rewards have been shown to correlate well with human preferences on standard benchmarks, suggesting that the implicit reward is a meaningful quality signal despite never being explicitly trained on reward prediction.
:::

### Senior / Forward Deployed Engineer

::: {.callout-important title="Senior / Forward Deployed Engineer"}
**Q1. Compare DPO, GRPO, and PPO. If you are training a reasoning model, which would you choose and why?**

> **What great looks like:** Understands the theoretical and practical tradeoffs of all three, correctly identifies that verifiable rewards change the calculus, and gives a concrete recommendation with caveats rather than a generic "it depends."

> **Common Mistake:** Recommending PPO because it is the "theoretically grounded RL algorithm" without acknowledging its practical infeasibility at 70B+ scale and the superiority of rule-based GRPO for verifiable tasks.

::: {.callout-note collapse="true" title="Model Answer"}
**PPO** is the general policy gradient method: requires actor + critic + reward model + reference model. For a 70B model, you are running 4 model copies of ~140GB each — ~560GB+ in FP16 before activations. PPO training is sensitive to clip ratio, KL coefficient, and GAE parameters, with instability that manifests as reward hacking or policy collapse rather than obvious training failures. Appropriate when: you have an extremely high-quality learned reward model, engineering infrastructure to run 4-model training stably, and a task where exploration genuinely matters (discovering behaviors not in any dataset).

**DPO** is offline supervised learning with a preference-derived loss. Requires only policy + reference. Stable, debuggable, and memory-efficient. Limitation: offline — the distribution gap means late training stages are less effective. Appropriate for: general preference alignment (helpfulness, tone, safety) where you have paired comparison data and do not need online exploration.

**GRPO** is online RL without a critic. Samples G responses per prompt, uses within-group advantage estimation. No critic, no separate reward model if using rule-based rewards. Appropriate for: tasks with verifiable correctness — math problems with numeric answers, code with test suites, structured outputs with schema validation. Rule-based rewards prevent reward hacking entirely.

**For a reasoning model specifically, I would choose GRPO with rule-based rewards.** Here is the reasoning:

1. Reasoning models need to develop multi-step problem decomposition, verification, and self-correction — capabilities that require online exploration, not just offline preference imitation. GRPO samples multiple approaches per problem and reinforces ones that reach the correct answer.

2. Mathematical and logical correctness is verifiable. You do not need a learned reward model — correctness against ground truth is deterministic. This eliminates reward hacking, which is the primary failure mode of learned-reward RL methods on reasoning tasks.

3. The cold-start problem: reasoning in a specific format (chain-of-thought in `<think>` tags) must be initialized with SFT on a few thousand examples before GRPO training. Without this, GRPO from a base model produces incoherent formatting that the rule-based reward function cannot evaluate.

4. DPO on reasoning pairs does not work as well because the chosen/rejected distinction at the response level is too coarse — a correct final answer reached through flawed reasoning may be labeled "chosen" if the final answer is right, training the model to value the conclusion without improving the intermediate reasoning. GRPO rewards correctness per response while training on the full reasoning trace.

**Implementation recommendation:** SFT on 5,000 format-correct reasoning examples (cold start) → GRPO with correctness + format rewards for the bulk of training → DPO on a curated set of reasoning comparison pairs for final calibration and safety.
:::

::: {.callout-important title="Senior / Forward Deployed Engineer"}
**Q2. A customer has a 7B model they want to align for a conciseness requirement — responses must be under 100 tokens on average. They have 5,000 preference pairs where shorter responses are always labeled as "chosen." Which method would you recommend and how would you implement it?**

> **What great looks like:** Identifies the length bias problem in vanilla DPO, recommends SimPO with rationale, addresses implementation details, and flags quality risks.

> **Common Mistake:** Recommending vanilla DPO or adding a post-hoc truncation step without addressing the root cause alignment training issue.

::: {.callout-note collapse="true" title="Model Answer"}
**Recommendation: SimPO.** Here is why the alternatives fail first.

Vanilla DPO has a structural length bias that works against this goal. The DPO loss is driven by total log-probability (sum over tokens). Even with shorter responses labeled as "chosen," the gradient incentivizes length because longer responses contribute more probability mass. You are fighting the method's structural bias with your preference labels — the labels will win eventually, but only partially.

IPO addresses overfitting but not length bias. ORPO is memory-efficient but also inherits the length-additive loss from the SFT cross-entropy term (though less severely than DPO). Neither directly addresses the problem.

SimPO normalizes the reward signal by sequence length — the objective is the average log-probability per token. A concise correct response and a verbose padded response of equal per-token quality receive identical reward signals. The length incentive is removed at the loss level, not through post-hoc regularization. The target margin $\gamma$ (I would set $\gamma = 1.0$ as a starting point for this use case) ensures the model's preference for shorter responses is strong, not marginal.

**Implementation:**

Step 1 — Audit the 5,000 pairs before training. Random-sample 100 and verify: is the shorter response actually complete (same information density, just more concise) or is it truncated (missing necessary content)? Pairs where the shorter response omits necessary information train the model toward unhelpful brevity, not genuine conciseness. Remove those — you want the model to learn concision, not truncation.

Step 2 — Train with SimPO using TRL's SimPO loss type: `loss_type="simpo"`, `beta=2.0`, `simpo_gamma=1.0`. Monitor average response length as a primary training metric alongside reward margins.

Step 3 — Establish a held-out evaluation set of 200 prompts stratified by complexity: 50 simple queries (1-sentence answers are appropriate), 100 medium queries (3–5 sentences reasonable), 50 complex queries (10+ sentences genuinely needed). Track average length per stratum, not just overall. You want the model to be concise on simple queries without truncating complex ones.

Step 4 — Check for over-correction. If complex queries (multi-step troubleshooting, technical explanations) are producing 50-word answers that omit needed steps, add back some preference pairs where the longer response is chosen for genuinely complex queries. This teaches the model that conciseness is context-dependent, not universal.

**Deployment monitoring:** Log response token counts by query type after deployment. If average drops below 50 tokens overall (too aggressive), increase $\gamma$ to raise the preference margin threshold and retrain on a 500-example subset. If responses are at 100 tokens but customer satisfaction drops, the model may be truncating valuable information — investigate by reviewing specific cases where users sent follow-up clarification requests.
:::

::: {.callout-important title="Senior / Forward Deployed Engineer"}
**Q3. A team wants to run iterative DPO on a model to reach frontier alignment quality. Walk through the full pipeline, engineering tradeoffs, and failure modes.**

> **What great looks like:** Covers all 4 stages of the loop (generate, score, build pairs, train), identifies the distribution gap as the motivating problem, discusses reward model quality as the bottleneck, and flags specific failure modes with mitigations.

> **Common Mistake:** Describing only the training step without discussing the generation and scoring infrastructure, or treating iterative DPO as just "run DPO multiple times on the same dataset."

::: {.callout-note collapse="true" title="Model Answer"}
**Motivating problem:** Offline DPO stagnates because the preference dataset reflects the model's past failure modes, not current ones. After 1–2 epochs of offline DPO, the model has improved beyond what the static dataset can teach. Iterative DPO refreshes the dataset each iteration to stay diagnostic.

**Pipeline:**

*Iteration loop (run 3–5 times):*

1. **Generate:** Sample 2 responses per prompt from the current policy for each prompt in the training set. Use temperature 0.7–0.9 to get diverse responses — too low and both responses are nearly identical (no preference signal), too high and responses are incoherent.

2. **Score:** Run a reward model over all generated responses. This is the highest-variance component: if the reward model has systematic weaknesses, every iteration will reinforce those weaknesses. Options: (a) a separately trained RM on human preference data, (b) an implicit reward model from a previous DPO checkpoint, (c) rule-based scoring for verifiable tasks.

3. **Build pairs:** For each prompt, the higher-scoring response becomes "chosen," the lower-scoring becomes "rejected." Filter out pairs where the score difference is below a threshold (e.g., 0.1 on a 0–1 scale) — near-tie pairs provide weak signal and can introduce noise.

4. **Train DPO:** One epoch of DPO on the fresh pairs. Keep $\beta$ constant across iterations (typically 0.1). Use a lower learning rate than the first training run (1e-7 vs 5e-7) — the model is closer to optimal and needs smaller steps.

**Engineering tradeoffs:**

- **Compute:** 2x per iteration (generation + training) vs. single offline run. 5 iterations = 10x a single offline run. This is usually worth it for final model quality but requires planning compute budget upfront.
- **Reward model staleness:** If you are using a fixed reward model across all iterations, by iteration 4 the model may have learned to score highly on the reward model's biases rather than genuinely improving. Mitigation: use the DPO checkpoint's implicit reward as the scoring signal — it updates each iteration and is less hackable.
- **Prompt coverage:** The training set must cover the full distribution of intended deployment prompts. If iteration 1 uses a narrow prompt set, the model will overfit to that distribution. Use a diverse held-out evaluation set to detect this.

**Failure modes:**

- **Reward hacking per iteration:** The model learns to game the reward model rather than genuinely improving. Symptom: reward scores increase each iteration but held-out human evaluation scores plateau or decline. Mitigation: use rule-based rewards for verifiable tasks; use diverse human evaluation as the ground truth metric across iterations.
- **Distribution collapse:** If the generation temperature is too low, both sampled responses are nearly identical and the preference pairs are trivial. The model sees "chosen" and "rejected" responses that differ in one token — no useful gradient. Monitor average cosine similarity between chosen and rejected responses; it should stay below 0.7.
- **KL explosion:** If $\beta$ is too low, the policy moves too far from the reference model each iteration, and later iterations are operating on a model that has drifted significantly from the reference. Symptoms: logps/chosen decreasing (the model becomes less likely to generate its own preferred responses), incoherent outputs on out-of-distribution prompts. Mitigation: update the reference model every 2 iterations to the current checkpoint.
- **Prompt set staleness:** If the training prompt set is fixed, later iterations improve on already-covered failure modes rather than discovering new ones. In production, refresh 20–30% of the prompt set each iteration by sampling from recent deployment logs or adding newly generated adversarial prompts.
