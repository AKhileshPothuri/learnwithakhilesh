22.1 1. API Integration Patterns

22.1.1 The Three Latency Regimes

GenAI APIs have fundamentally different latency characteristics from traditional CRUD endpoints. A Postgres query takes 1-10 ms. An LLM generation for a 500-token response takes 2-30 seconds depending on model size, provider load, and output length. This single fact forces three distinct API patterns, each occupying a latency regime.

Plain-English definition: An API integration pattern is the structural shape of the client-server interaction — how the client sends a request, how it receives data, and what happens when things go wrong.

Analogy: Think of the three patterns like three ways to order coffee. Synchronous is a drive-through — you wait at the window until the cup is in your hand. Streaming is an espresso bar where the barista calls your name as each drink component is ready. Async with a webhook is ordering via a mobile app — you submit, go sit down, and the app buzzes you when the order is ready.

Pattern Latency range Best for Avoid when
Synchronous (blocking) < 3 s Simple classification, embedding, short extraction User is watching, response > 5 s
Streaming (SSE) First token 0.3-1 s User-facing chat, copilot features Client can’t consume streams (legacy systems)
Async + webhook/polling 10 s – 10 min Document analysis, batch summarization, multi-step agents User needs real-time answer
Warning

Common Misconception: “We can just set a longer HTTP timeout and use synchronous for everything.”

HTTP timeouts at load balancers, API gateways, and CDNs are typically 30-60 seconds and not always configurable. A document analysis job that takes 90 seconds will be killed at the network layer before the LLM finishes. Use async for anything that might exceed 25 seconds.

22.1.2 Streaming with Server-Sent Events (SSE)

SSE is the standard mechanism for streaming tokens from an LLM server to a browser or API client. It is unidirectional (server to client), uses a plain HTTP connection, and has native browser support via EventSource. For non-browser clients, SSE is trivial to parse: each event is a text line prefixed with data:.

Why it matters for UX: In user studies, perceived latency drops dramatically when content appears progressively. A 10-second streaming response feels faster than a 3-second synchronous response because the user receives signal within 400 ms that something is happening.

# streaming_client.py — production-grade SSE streaming with retry and error handling
import anthropic
import httpx
from typing import Iterator

def stream_completion(
    prompt: str,
    system: str = "",
    model: str = "claude-sonnet-4-5",
    max_tokens: int = 1024,
) -> Iterator[str]:
    """
    Streams tokens from the Anthropic API.
    Yields text chunks as they arrive.
    Raises on non-retryable errors; caller handles retry logic.
    """
    client = anthropic.Anthropic()

    with client.messages.stream(
        model=model,
        max_tokens=max_tokens,
        system=system,
        messages=[{"role": "user", "content": prompt}],
    ) as stream:
        for text_chunk in stream.text_stream:
            yield text_chunk

        # Final message gives token counts for cost tracking
        final_message = stream.get_final_message()
        usage = final_message.usage
        # Log usage for cost attribution
        _log_usage(model=model, input_tokens=usage.input_tokens,
                   output_tokens=usage.output_tokens)


def _log_usage(model: str, input_tokens: int, output_tokens: int):
    """Emit a structured log entry for cost tracking."""
    import json, logging
    logging.info(json.dumps({
        "event": "llm_usage",
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
    }))


# FastAPI SSE endpoint — sends tokens to the browser as they arrive
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/chat/stream")
async def chat_stream(payload: dict):
    prompt = payload.get("prompt", "")

    def event_generator():
        try:
            for chunk in stream_completion(prompt):
                # SSE format: each line starts with "data: "
                yield f"data: {chunk}\n\n"
            # Signal end of stream
            yield "data: [DONE]\n\n"
        except Exception as e:
            # Errors mid-stream must be sent as a special event type
            yield f"event: error\ndata: {str(e)}\n\n"

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",  # Disable Nginx buffering
        },
    )
Tip

Production gotcha: Nginx and many reverse proxies buffer responses by default. Add X-Accel-Buffering: no (Nginx) or equivalent headers to ensure tokens flow to the client immediately rather than being buffered until the response is complete. Without this, streaming degrades to synchronous from the user’s perspective.

22.1.3 Async Processing with Webhooks

For tasks that take more than 25-30 seconds — multi-document analysis, complex agent runs, batch summarization — the client cannot wait for an HTTP response. The correct pattern is:

  1. Client POSTs job request → server returns HTTP 202 Accepted with a job_id immediately.
  2. Server processes the job asynchronously (Celery worker, Cloud Run job, Lambda).
  3. On completion, server POSTs results to the client’s registered webhook URL.
  4. Client also polls GET /jobs/{job_id} for status (fallback when webhooks fail).
# async_job.py — webhook delivery with retry
import httpx
import asyncio
import json
from dataclasses import dataclass
from enum import Enum

class JobStatus(Enum):
    PENDING = "pending"
    PROCESSING = "processing"
    COMPLETED = "completed"
    FAILED = "failed"

@dataclass
class Job:
    job_id: str
    webhook_url: str
    prompt: str
    status: JobStatus = JobStatus.PENDING
    result: str | None = None
    error: str | None = None

async def deliver_webhook(job: Job, max_attempts: int = 5) -> bool:
    """
    Delivers webhook with exponential backoff.
    Returns True on successful delivery, False after all retries exhausted.
    """
    payload = {
        "job_id": job.job_id,
        "status": job.status.value,
        "result": job.result,
        "error": job.error,
    }
    base_delay = 1.0  # seconds

    async with httpx.AsyncClient(timeout=10.0) as client:
        for attempt in range(max_attempts):
            try:
                response = await client.post(
                    job.webhook_url,
                    json=payload,
                    headers={"Content-Type": "application/json"},
                )
                if response.status_code in (200, 201, 204):
                    return True
                # 4xx errors are not retryable (bad webhook URL)
                if 400 <= response.status_code < 500:
                    return False
            except (httpx.ConnectError, httpx.TimeoutException):
                pass  # Transient; retry

            # Exponential backoff with jitter
            import random
            delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
            await asyncio.sleep(min(delay, 60.0))  # Cap at 60 s

    return False  # All retries exhausted

22.2 2. Retry Strategies: Exponential Backoff with Jitter

Plain-English definition: When an API call fails transiently (rate limit, transient 503), retry after a delay. Make each delay longer than the last (exponential) and add randomness (jitter) to prevent all retrying clients from hammering the provider simultaneously.

Analogy: Imagine 100 people all trying to call the same busy phone number. If they all hang up and immediately redial at the same time, the line stays busy. If each person waits a random amount of time before retrying, calls spread out and the line clears.

The formula: delay = min(base * 2^attempt + random(0, 1), max_delay)

# retry.py — production retry decorator with jitter and provider error classification
import time
import random
import functools
import logging
from typing import Callable, TypeVar, Type

logger = logging.getLogger(__name__)
T = TypeVar("T")

# Errors that should be retried (transient)
RETRYABLE_STATUS_CODES = {429, 500, 502, 503, 504}

class RetryExhausted(Exception):
    """Raised when all retry attempts fail."""
    pass

def with_retry(
    max_attempts: int = 5,
    base_delay: float = 1.0,
    max_delay: float = 60.0,
    retryable_exceptions: tuple[Type[Exception], ...] = (Exception,),
):
    """
    Decorator: retry with exponential backoff + full jitter.
    Full jitter: delay = random(0, min(base * 2^attempt, max_delay))
    This distributes retries evenly across the range [0, cap].
    """
    def decorator(func: Callable) -> Callable:
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_exception = None
            for attempt in range(max_attempts):
                try:
                    return func(*args, **kwargs)
                except retryable_exceptions as exc:
                    last_exception = exc
                    if attempt == max_attempts - 1:
                        break  # No more retries

                    # Full jitter: uniform random in [0, cap]
                    cap = min(base_delay * (2 ** attempt), max_delay)
                    delay = random.uniform(0, cap)

                    logger.warning(
                        "Attempt %d/%d failed: %s. Retrying in %.2fs.",
                        attempt + 1, max_attempts, str(exc), delay,
                    )
                    time.sleep(delay)

            raise RetryExhausted(
                f"All {max_attempts} attempts failed. "
                f"Last error: {last_exception}"
            ) from last_exception
        return wrapper
    return decorator


# Usage with Anthropic SDK
import anthropic

@with_retry(
    max_attempts=5,
    base_delay=1.0,
    max_delay=30.0,
    retryable_exceptions=(anthropic.RateLimitError, anthropic.APIStatusError),
)
def call_llm(prompt: str) -> str:
    client = anthropic.Anthropic()
    message = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=512,
        messages=[{"role": "user", "content": prompt}],
    )
    return message.content[0].text
Warning

Common Mistake: Using uniform retry delays (always wait 2 seconds) instead of exponential backoff. Under sustained provider unavailability, uniform retries maintain high request volume and may cause your account to be rate-limited further. Exponential backoff naturally reduces retry pressure as outage duration increases.

Also: never retry on 4xx client errors (400, 401, 403, 404) — these are not transient. Retrying a malformed request wastes tokens and hides bugs.

22.3 3. LLM Provider Abstraction Layer

When to build one: As soon as you have two requirements: (a) more than one LLM provider in use or planned, OR (b) the need to fail over from a primary provider to a secondary during outages.

When not to build one: If you have exactly one provider and no plans to switch, abstractions add complexity without benefit. YAGNI (You Aren’t Gonna Need It) applies.

Analogy: A power strip with a universal adapter. Your devices (application code) plug into a single standardized interface; the adapter handles the different voltages and plug shapes behind the scenes.

# llm_gateway.py — provider-agnostic LLM gateway with failover and cost tracking
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from typing import Optional
import time
import logging

logger = logging.getLogger(__name__)

@dataclass
class LLMResponse:
    text: str
    model: str
    provider: str
    input_tokens: int
    output_tokens: int
    latency_ms: float
    cost_usd: float

@dataclass
class ProviderConfig:
    name: str
    model: str
    cost_per_1k_input_tokens: float
    cost_per_1k_output_tokens: float
    priority: int = 0  # Lower = higher priority


class LLMProvider(ABC):
    """Abstract base class for LLM provider implementations."""
    def __init__(self, config: ProviderConfig):
        self.config = config

    @abstractmethod
    def complete(self, prompt: str, system: str, max_tokens: int) -> LLMResponse:
        ...

    def _compute_cost(self, input_tokens: int, output_tokens: int) -> float:
        return (
            input_tokens / 1000 * self.config.cost_per_1k_input_tokens
            + output_tokens / 1000 * self.config.cost_per_1k_output_tokens
        )


class AnthropicProvider(LLMProvider):
    def complete(self, prompt: str, system: str = "", max_tokens: int = 1024) -> LLMResponse:
        import anthropic
        client = anthropic.Anthropic()
        start = time.monotonic()

        message = client.messages.create(
            model=self.config.model,
            max_tokens=max_tokens,
            system=system,
            messages=[{"role": "user", "content": prompt}],
        )
        latency_ms = (time.monotonic() - start) * 1000

        return LLMResponse(
            text=message.content[0].text,
            model=self.config.model,
            provider="anthropic",
            input_tokens=message.usage.input_tokens,
            output_tokens=message.usage.output_tokens,
            latency_ms=latency_ms,
            cost_usd=self._compute_cost(
                message.usage.input_tokens, message.usage.output_tokens
            ),
        )


class OpenAIProvider(LLMProvider):
    def complete(self, prompt: str, system: str = "", max_tokens: int = 1024) -> LLMResponse:
        from openai import OpenAI
        client = OpenAI()
        start = time.monotonic()

        response = client.chat.completions.create(
            model=self.config.model,
            max_tokens=max_tokens,
            messages=[
                {"role": "system", "content": system},
                {"role": "user", "content": prompt},
            ],
        )
        latency_ms = (time.monotonic() - start) * 1000
        usage = response.usage

        return LLMResponse(
            text=response.choices[0].message.content,
            model=self.config.model,
            provider="openai",
            input_tokens=usage.prompt_tokens,
            output_tokens=usage.completion_tokens,
            latency_ms=latency_ms,
            cost_usd=self._compute_cost(usage.prompt_tokens, usage.completion_tokens),
        )


class LLMGateway:
    """
    Manages a prioritized list of providers with automatic failover.
    Logs cost to a pluggable cost tracker.
    """
    def __init__(self, providers: list[LLMProvider]):
        # Sort by priority; lower value = tried first
        self.providers = sorted(providers, key=lambda p: p.config.priority)

    def complete(
        self,
        prompt: str,
        system: str = "",
        max_tokens: int = 1024,
    ) -> LLMResponse:
        errors = []
        for provider in self.providers:
            try:
                response = provider.complete(prompt, system, max_tokens)
                self._record_cost(response)
                return response
            except Exception as exc:
                logger.warning(
                    "Provider %s failed: %s. Trying next.",
                    provider.config.name, exc,
                )
                errors.append((provider.config.name, str(exc)))

        raise RuntimeError(
            f"All LLM providers failed: {errors}"
        )

    def _record_cost(self, response: LLMResponse):
        logger.info(
            "llm_cost provider=%s model=%s input_tokens=%d "
            "output_tokens=%d cost_usd=%.6f latency_ms=%.1f",
            response.provider, response.model,
            response.input_tokens, response.output_tokens,
            response.cost_usd, response.latency_ms,
        )

22.4 4. Context Window Management

Plain-English definition: Every LLM call has a maximum number of tokens that can appear in the combined input (system prompt + conversation history + retrieved context + user message). When conversation history grows beyond this limit, you must decide what to discard.

Why it matters: At $0.003/1K tokens for mid-tier models, a 200K-token context window full of conversation history costs $0.60 per request — before output tokens. For a high-volume application with 10K daily active users averaging 5 queries/session, that is $30K/day purely in input token costs.

22.4.1 Strategy 1: Sliding Window

Keep the N most recent turns. Discard the oldest turns as the window fills.

# context_manager.py — three context window strategies
from dataclasses import dataclass, field
from typing import Literal

@dataclass
class Message:
    role: Literal["user", "assistant"]
    content: str

    @property
    def token_estimate(self) -> int:
        # Rough estimate: 1 token ~ 4 characters
        return len(self.content) // 4

@dataclass
class ConversationContext:
    messages: list[Message] = field(default_factory=list)
    max_tokens: int = 4000  # Reserve for system prompt + retrieved context

    def add_message(self, role: str, content: str):
        self.messages.append(Message(role=role, content=content))
        self._trim_to_budget()

    def _trim_to_budget(self):
        """Sliding window: drop oldest messages until within budget."""
        while self._total_tokens() > self.max_tokens and len(self.messages) > 2:
            # Always keep at least the most recent exchange
            self.messages.pop(0)

    def _total_tokens(self) -> int:
        return sum(m.token_estimate for m in self.messages)

    def to_api_messages(self) -> list[dict]:
        return [{"role": m.role, "content": m.content} for m in self.messages]

22.4.2 Strategy 2: Summarization Buffer

When the window fills, call the LLM to summarize the oldest N turns, then replace those turns with the summary. Preserves semantic information at the cost of an extra LLM call.

class SummarizingContext:
    def __init__(self, max_tokens: int = 4000, summarize_threshold: int = 3000):
        self.messages: list[Message] = []
        self.summary: str = ""
        self.max_tokens = max_tokens
        self.summarize_threshold = summarize_threshold

    def add_message(self, role: str, content: str):
        self.messages.append(Message(role=role, content=content))
        if self._total_tokens() > self.summarize_threshold:
            self._summarize_oldest_half()

    def _summarize_oldest_half(self):
        midpoint = len(self.messages) // 2
        to_summarize = self.messages[:midpoint]
        self.messages = self.messages[midpoint:]

        # Call LLM to summarize the dropped turns
        import anthropic
        client = anthropic.Anthropic()
        text = "\n".join(
            f"{m.role}: {m.content}" for m in to_summarize
        )
        response = client.messages.create(
            model="claude-haiku-4-5",  # Use cheapest model for summarization
            max_tokens=256,
            messages=[{
                "role": "user",
                "content": (
                    f"Summarize this conversation segment in 3-4 sentences, "
                    f"preserving key facts and decisions:\n\n{text}"
                ),
            }],
        )
        new_summary = response.content[0].text
        self.summary = (
            f"{self.summary}\n{new_summary}".strip()
            if self.summary else new_summary
        )

    def to_api_messages(self) -> list[dict]:
        messages = []
        if self.summary:
            messages.append({
                "role": "user",
                "content": f"[Conversation summary so far: {self.summary}]",
            })
            messages.append({"role": "assistant", "content": "Understood."})
        messages.extend(
            {"role": m.role, "content": m.content} for m in self.messages
        )
        return messages

    def _total_tokens(self) -> int:
        return sum(m.token_estimate for m in self.messages)

22.4.3 Strategy 3: Hierarchical (RAG over conversation history)

For very long sessions (document editing, code review over a large codebase), index the conversation history in a vector store and retrieve only the relevant portions per turn.

When to use each strategy:

Strategy Best for Avoid when
Sliding window Short chat sessions, < 20 turns Need long-term memory
Summarization Medium sessions, need context continuity Cost-sensitive at scale
Hierarchical (RAG over history) Long sessions, document work Latency is critical

22.5 5. Vector Database Integration Patterns

Plain-English definition: A vector database stores numerical embeddings (dense vector representations of text) and supports approximate nearest-neighbor (ANN) search — finding the stored vectors most similar to a query vector.

22.5.1 Production Integration Pattern

# vector_store.py — production-ready vector store abstraction with metadata filtering
from dataclasses import dataclass
from typing import Any
import hashlib

@dataclass
class Document:
    doc_id: str
    content: str
    metadata: dict[str, Any]
    embedding: list[float] | None = None

@dataclass
class SearchResult:
    doc_id: str
    content: str
    score: float
    metadata: dict[str, Any]

class VectorStore:
    """
    Thin wrapper around a vector DB client.
    Handles: upsert, delete, similarity search with metadata filter.
    """
    def __init__(self, client, namespace: str = "default"):
        self.client = client  # e.g., Pinecone Index, Qdrant Collection
        self.namespace = namespace

    def upsert(self, doc: Document) -> None:
        """
        Idempotent: upserting the same doc_id overwrites the previous entry.
        Use document URL or DB primary key as doc_id for idempotency.
        """
        if doc.embedding is None:
            raise ValueError("Document must have an embedding before upsert.")
        self.client.upsert(
            vectors=[{
                "id": doc.doc_id,
                "values": doc.embedding,
                "metadata": {**doc.metadata, "content": doc.content},
            }],
            namespace=self.namespace,
        )

    def delete(self, doc_id: str) -> None:
        """
        Remove a document by ID. Call this when source document is deleted
        to prevent stale citations.
        """
        self.client.delete(ids=[doc_id], namespace=self.namespace)

    def search(
        self,
        query_embedding: list[float],
        top_k: int = 5,
        metadata_filter: dict | None = None,
    ) -> list[SearchResult]:
        """
        Pre-filter search: apply metadata filter inside the vector DB.
        This is the recommended pattern for access control.
        """
        kwargs = {
            "vector": query_embedding,
            "top_k": top_k,
            "include_metadata": True,
            "namespace": self.namespace,
        }
        if metadata_filter:
            kwargs["filter"] = metadata_filter

        results = self.client.query(**kwargs)
        return [
            SearchResult(
                doc_id=match["id"],
                content=match["metadata"]["content"],
                score=match["score"],
                metadata={k: v for k, v in match["metadata"].items()
                          if k != "content"},
            )
            for match in results["matches"]
        ]


# Usage: pre-filter access control
def rag_query(
    question: str,
    user_groups: list[str],
    vector_store: VectorStore,
    embedder,  # Any embed(text) -> list[float] function
) -> list[SearchResult]:
    query_embedding = embedder(question)
    return vector_store.search(
        query_embedding=query_embedding,

# semantic_cache.py — cosine similarity-based response cache
import numpy as np
from dataclasses import dataclass, field
from datetime import datetime, timedelta
import hashlib

@dataclass
class CacheEntry:
    query_embedding: list[float]
    response: str
    created_at: datetime
    ttl_hours: float = 24.0

    @property
    def is_expired(self) -> bool:
        return datetime.utcnow() > self.created_at + timedelta(hours=self.ttl_hours)

class SemanticCache:
    """
    Cache LLM responses by semantic similarity of the query.
    Hit rate metric: track and alert if it drops below baseline.
    Tune threshold empirically: 0.92-0.95 is typical for Q&A applications.
    """
    def __init__(self, similarity_threshold: float = 0.93, max_size: int = 10_000):
        self.threshold = similarity_threshold
        self.max_size = max_size
        self.entries: list[CacheEntry] = []
        self._hit_count = 0
        self._miss_count = 0

    def get(self, query_embedding: list[float]) -> str | None:
        """Returns cached response if a similar query was seen recently."""
        q = np.array(query_embedding)
        for entry in self.entries:
            if entry.is_expired:
                continue
            cached = np.array(entry.query_embedding)
            # Cosine similarity
            similarity = float(
                np.dot(q, cached) / (np.linalg.norm(q) * np.linalg.norm(cached) + 1e-10)
            )
            if similarity >= self.threshold:
                self._hit_count += 1
                return entry.response
        self._miss_count += 1
        return None

    def put(self, query_embedding: list[float], response: str, ttl_hours: float = 24.0):
        """Add a new entry, evicting expired entries if at capacity."""
        self._evict_expired()
        if len(self.entries) >= self.max_size:
            self.entries.pop(0)  # Evict oldest
        self.entries.append(CacheEntry(
            query_embedding=query_embedding,
            response=response,
            created_at=datetime.utcnow(),
            ttl_hours=ttl_hours,
        ))

    def _evict_expired(self):
        self.entries = [e for e in self.entries if not e.is_expired]

    @property
    def hit_rate(self) -> float:
        total = self._hit_count + self._miss_count
        return self._hit_count / total if total > 0 else 0.0

22.8 8. Observability

LLM observability extends conventional service observability with a quality dimension. A service that returns 200 OK with confident but wrong answers has perfect traditional reliability and terrible LLM reliability.

The RAG triad — three quality metrics to track:

Metric Definition How to measure
Context relevance Did we retrieve the right documents? LLM-as-judge, or embedding similarity between query and retrieved docs
Faithfulness Does the answer contradict the retrieved documents? NLI model or LLM-as-judge
Answer relevance Does the answer address the question? LLM-as-judge on a 1-5 rubric
Tip

Logging strategy at scale: Log 100% of requests to a hot store (7-day retention) for debugging. Sample 2-5% to a cold store for long-term quality trend analysis. Running LLM-as-judge on 100% of traffic doubles your inference costs — sampling is the right tradeoff for most applications.

22.9 Cheat Sheet

  • Streaming (SSE): First token in ~400 ms; perceived latency dramatically lower than synchronous even at same total latency; requires special error event type mid-stream; disable proxy buffering (Nginx: X-Accel-Buffering: no).
  • Async + webhook: Use for any task > 25 s; return HTTP 202 + job_id immediately; implement both webhook push and polling fallback; include progress details in status endpoint.
  • Exponential backoff with full jitter: delay = random(0, min(base * 2^attempt, cap)); never retry on 4xx (client errors); retry on 429 and 5xx only.
  • Provider abstraction layer: Abstract when you have 2+ providers or need failover; add cost tracking and latency logging per provider; don’t over-abstract if you have one provider and no switching plans.
  • LangChain: Good for prototypes and demos; heavy dependency footprint; abstraction overhead hurts debugging in production.
  • LlamaIndex: Purpose-built for RAG pipelines; recommended starting point for document search applications.
  • Custom integration: Best for fine-grained control, thin footprint, easy debugging; preferred by mature production teams.
  • Sliding window context: Simplest context management; always keep the 2 most recent turns; discard oldest first.
  • Summarization buffer: Preserve semantic continuity at cost of extra LLM call; use cheapest model (Claude Haiku, GPT-3.5) for summarization.
  • Pre-filter access control: Inject permission filter into vector DB query; only authorized documents are scored; preferred over post-filter for production.
  • Semantic caching: 0.92-0.95 cosine threshold typical; tie TTL to index freshness; monitor hit rate — target 30-60% for FAQ apps.
  • Cost attribution tags: team_id, app_id, user_id, use_case, request_id on every LLM call; enforce at gateway layer.
  • Model routing: Route simple tasks (classification, short extraction) to cheaper models; 40-60% cost reduction achievable; routing classifier must be cheap.
  • RAG triad: Context relevance + Faithfulness + Answer relevance; monitor all three; faithfulness drop usually precedes complaint wave.
  • Prompt versioning: Every prompt template has a version; log prompt_version with every request; treat prompt changes like code changes (review, deploy, rollback).
  • Index freshness SLA: Define it explicitly (batch: 24 h; event-driven: 5 min; streaming: 60 s); measure and alert on violations.
  • Document deletion: Maintain source_doc_id → [chunk_ids] mapping; delete all chunks when source is deleted; soft-delete if recovery needed.
  • Hardcoded model versions: Never hardcode exact version strings in production; pin to aliases you control; provider deprecations break hardcoded versions silently.
  • Human escalation path: Every user-facing GenAI feature needs a visible path to a human; system should offer it when confidence is low.
  • LLM call idempotency: LLM calls are NOT idempotent; blind infrastructure retries can produce duplicate responses; implement idempotency at application layer where semantically correct.

22.10 Interview Questions

22.10.1 Entry Level

Entry Level

Q1. What is the difference between synchronous and streaming LLM API calls? When would you use each?

Model Answer

A synchronous call blocks until the entire response is generated, then returns it all at once. A streaming call returns tokens progressively as the model generates them.

Synchronous is appropriate when: the calling system is not user-facing (batch processing, backend pipeline), the expected response is very short (< 2 seconds), or the downstream consumer cannot process partial data.

Streaming is appropriate for nearly all user-facing features. When a user asks a question and sees text appearing within 400 ms, the experience feels responsive even if total generation takes 10 seconds. Waiting 10 seconds for a blank screen to suddenly show a full response feels broken.

The implementation difference: synchronous returns a complete Message object; streaming uses a context manager (client.messages.stream(...)) and you iterate over stream.text_stream to receive chunks.

Q2. What is exponential backoff and why does jitter matter?

Model Answer

Exponential backoff is a retry strategy where each successive retry waits longer than the previous: retry 1 waits 1s, retry 2 waits 2s, retry 3 waits 4s, and so on. This reduces pressure on an overloaded provider by spacing retries further apart over time.

Jitter adds randomness to each delay. Without jitter, if 100 clients all hit a rate limit at the same time, they will all retry at the exact same moments (1s, 2s, 4s), creating synchronized waves of retry traffic. The provider stays overloaded. With jitter, each client waits a random amount within a range, spreading the retry load across time and allowing the provider to recover.

The full jitter formula: delay = random(0, min(base * 2^attempt, max_delay)). This distributes retries uniformly across the entire backoff range.

Q3. What is semantic caching? When does it help and when does it not?

Model Answer

Semantic caching stores previous query-response pairs. When a new query arrives, its embedding is compared to cached query embeddings. If a cached query is sufficiently similar (above a cosine similarity threshold, typically 0.92-0.95), the cached response is returned instead of calling the LLM.

It helps when: many users ask similar questions (FAQ apps, documentation chatbots, internal knowledge bases). Cache hit rates of 30-80% are achievable in these contexts, directly reducing LLM costs and latency.

It does not help when: queries are highly personalized (each user’s context is unique), content changes frequently (cached responses cite outdated information — tie TTL to index freshness), or the application requires responses tailored to specific user account state (balances, order history).

The key tuning parameter is the similarity threshold. Too high: cache underutilized. Too low: return cached responses to queries that were similar but meaningfully different.

22.10.2 Mid Level

Mid Level

Q1. Explain the pre-filter vs. post-filter approaches to document-level access control in a RAG system. What are the tradeoffs?

Model Answer

Both approaches address the same problem: a RAG knowledge base contains documents with different permission levels, and different users should see different documents in their answers.

Pre-filter: At indexing time, store each chunk with a metadata field listing which permission groups can access it (allowed_groups: ["finance", "hr"]). At query time, inject this as a filter into the vector search query, so only authorized chunks are scored and returned.

Advantages: no unauthorized content enters the LLM context (defense in depth); recall is correct for the user’s authorized set; computationally efficient for coarse-grained permissions.

Disadvantages: requires the vector database to support metadata filtering alongside ANN search (most production databases do); permission changes require re-indexing affected chunks.

Post-filter: Retrieve top-k without access control, then remove unauthorized chunks before passing context to the LLM.

Advantages: simpler to implement — no changes to the retrieval query.

Disadvantages: unauthorized content is fetched and logged (security concern); if many top-k results are unauthorized, the filtered context is thin and answer quality degrades. A user with narrow permissions in a mixed knowledge base gets poor answers even when the knowledge exists in authorized documents.

Recommendation: Pre-filter for production enterprise deployments. Post-filter only for rapid prototyping. For very fine-grained per-document permissions, consider hybrid: coarse department-level pre-filter, exact document-level post-filter.

Q2. A team says their RAG app has 99.9% uptime but users keep complaining “it’s not working.” What is the observability gap and how do you close it?

Model Answer

This is the classic reliability vs. quality gap in LLM systems. 99.9% uptime means the service is responding — it says nothing about whether responses are useful or accurate.

The observability gap has three layers:

  1. No output quality monitoring. The system tracks request count and latency but not whether responses are correct or helpful. Users who get wrong answers don’t generate HTTP 500 errors — they just report “it’s broken.”

  2. No faithfulness monitoring. The system may be retrieving the wrong documents (low context relevance) or generating answers that contradict the retrieved documents (low faithfulness). Both look like “wrong answers” to users. Neither appears in uptime metrics.

  3. No user feedback loop. Users experiencing failures have no mechanism to flag them at the point of failure. Issues surface only through support tickets — too slow and too aggregated to diagnose root causes.

Closing the gap:

  • Implement the RAG triad metrics: context relevance, faithfulness, answer relevance. Track all three over time; alert on degradation.
  • Add inline feedback (thumbs up/down) at the response level. Route low-rated responses to a review queue.
  • Sample 2-5% of production responses through an LLM-as-judge quality evaluator. Track quality scores in a time-series dashboard.
  • Correlate quality drops with prompt version changes and retrieval changes — most quality regressions have a root cause that is identifiable with proper attribution.

Q3. What are the failure modes of context window management approaches, and how do you choose between sliding window, summarization, and hierarchical retrieval?

Model Answer

Sliding window drops the oldest turns verbatim. Failure mode: any fact established in an early turn is silently lost. If the user stated their name, account number, or a key constraint in turn 2 and the session is now at turn 30, that information is gone. The model may produce inconsistent answers as critical early context falls out. Works well for short sessions where continuity across 20+ turns is not required.

Summarization buffer compresses old turns via an LLM call. Failure mode: the summarizer is lossy — it drops specific details in favor of general trends. A precise number (“my budget is $47,500”) may survive summarization (“the user has a budget around $45K-$50K”) or may be dropped. Each summarization call adds latency and cost (use the cheapest model). Works well for medium-length sessions where semantic continuity matters more than specific detail recall.

Hierarchical retrieval (RAG over conversation history) indexes past turns in a vector store and retrieves relevant history per turn. Failure mode: retrieval may miss relevant context that is not semantically similar to the current query but is logically relevant (a constraint stated at the beginning of the session). Adds retrieval latency to every turn. Works best for very long sessions where the user is working on a specific artifact (document, codebase) and most turns are localized to a small part of the history.

Choosing: Short sessions (< 20 turns) → sliding window. Sessions where continuity matters and length is moderate → summarization buffer. Very long sessions with specific artifacts → hierarchical. In practice, most production chat applications use sliding window with a generous token budget (e.g., 8K context reserved for history), switching to summarization only when window pressure becomes a measurable quality issue.

Senior / Forward Deployed Engineer

Q1. Design an LLM integration layer that supports OpenAI, Anthropic, and a locally-hosted model with automatic failover and per-team cost tracking. What are the key components and tradeoffs?

Model Answer

What great looks like: A systematic architecture answer that covers the abstraction interface, routing logic, failover mechanism, cost tracking, and operational concerns — not just “use LangChain.”

Key components:

  1. Provider interface — An abstract base class with a complete(prompt, system, max_tokens) -> LLMResponse method. LLMResponse carries text, provider, model, input_tokens, output_tokens, latency_ms, cost_usd. Each provider (Anthropic, OpenAI, local Ollama) implements this interface independently.

  2. Gateway — Holds a prioritized list of providers. On each call: try provider 1; on failure (exception, timeout, or 5xx), log the error and try provider 2; continue until success or all providers exhausted. Failover policy can be static (always try Anthropic first) or dynamic (track error rates and deprioritize degraded providers using a circuit breaker).

  3. Cost tracker — Plugged into the gateway. After each successful call, records (team_id, app_id, user_id, provider, model, input_tokens, output_tokens, cost_usd, timestamp) to a time-series database. Budget enforcement middleware checks the team’s remaining budget before forwarding requests and returns HTTP 429 when budget is exhausted.

  4. Request context — Every call carries a CallContext struct with team_id, app_id, user_id, use_case, request_id. This flows through the gateway into cost tracking and logs.

  5. Circuit breaker — Per provider: track error rate over a 60-second window. If error rate > 20%, open the circuit breaker and route all traffic to the next provider for 60 seconds, then half-open (let 10% through to test recovery).

Tradeoffs to articulate: - A thick abstraction layer is good for provider switching but makes debugging harder (errors from provider A look the same as errors from provider B unless the gateway adds rich logging). - Failover improves reliability but increases costs (failed primary calls still consume some provider quota or at minimum incur latency). Budget the failover path explicitly. - Local model failover trades cost for quality — if Anthropic is down and you fail over to a local 7B model, response quality drops significantly for complex tasks. Consider a “degrade gracefully” policy: simple queries fail over to local; complex queries return an error with a user-visible message.

Common Mistake: Designing the gateway as a simple round-robin load balancer rather than a prioritized failover system. Round-robin actively sends traffic to degraded providers rather than routing around them.

Q2. A customer has 50 internal teams sharing a $200K/month LLM budget. Three teams routinely burn 80% of the budget by the 15th of each month, leaving the other 47 teams throttled. How do you design a fair and enforceable cost governance system?

Model Answer

What great looks like: A three-layer answer (allocation, enforcement, visibility) with specific mechanisms, not just “use quotas.”

Allocation: - Allocate based on documented use case: high-volume customer-facing teams (support bots, copilot features) get larger allocations than low-volume internal tool teams. Finance and leadership approve allocations quarterly. - Introduce a 10% reserve pool controlled by a platform team for emergency allocations. No team gets the reserve automatically — they request it with a business justification. - Store allocations in a database: (team_id, period, tokens_allocated, tokens_used, overage_policy). Overage policies are configurable: warn_only (alert but don’t throttle), throttle (reduce rate limit to 10% of normal), block (return 429).

Enforcement: - All LLM calls flow through a central gateway. The gateway looks up the requesting team’s budget before forwarding to the provider. If tokens_used >= tokens_allocated and overage_policy == block, return HTTP 429 with a body that explains the budget status and links to the budget request form. - Token counting is done on response (actual tokens from provider API), not estimated on request. Count atomically and update tokens_used in real time. - Warning alerts at 70% utilization (weekly email to team lead) and 90% utilization (Slack alert to team lead + manager).

Visibility: - A self-serve cost dashboard accessible to every team lead shows: real-time spend, daily trend, projected month-end spend (current rate × days remaining), per-application breakdown, and top-5 most expensive queries. - The dashboard is the most impactful governance tool. Most overspend is accidental — teams that can see their consumption self-regulate.

Addressing the three-team problem specifically: - Audit those three teams’ usage patterns: are they using the most expensive models for tasks where a cheaper model would suffice? Implement model routing (classify queries by complexity; route simple queries to GPT-4o-mini or Claude Haiku; saves 60-80% on simple tasks). - Implement per-user daily token limits within a team’s allocation. If one user or integration is consuming 90% of the team’s budget, a per-user cap surfaces that for the team lead to investigate. - Reserve a “floor allocation” for each team: a guaranteed minimum that cannot be consumed by other teams, even if the big consumers hit their caps.

Common Mistake: Implementing enforcement only at month-end (processing after the fact, sending bills). By then, the damage is done. Enforcement must be real-time with mid-period alerts.

Q3. Design a near-real-time RAG index freshness system that gets from document change to searchable in under 3 minutes. What are the failure modes and how do you handle them?

Model Answer

What great looks like: A full pipeline design with latency budget, idempotency analysis, failure mode enumeration, and a specific approach for each failure mode.

Pipeline architecture:

  1. Change detection (0-10 s): Register webhooks with the source system (SharePoint, Confluence, S3 event notifications). For database sources, use CDC (Debezium on Postgres, DynamoDB Streams). Each event carries: (doc_id, event_type: created|updated|deleted, source_url, timestamp).

  2. Event queue (1-5 s): Route events to a durable message queue (SQS, Pub/Sub). Queue provides retry, ordering guarantee (FIFO queue), and decoupling between ingestion rate and processing speed. Set visibility timeout to 3× the expected processing time.

  3. Document processor (15-60 s): Consumer fetches the full document, runs the ingestion pipeline (text extraction, chunking, embedding generation), and writes to the vector index. Use doc_id as the idempotent key — reprocessing the same document ID converges to the correct state.

  4. Index writer (1-5 s): Delete stale chunks (DELETE WHERE doc_id = X), insert new chunks. Wrap in a transaction where the vector DB supports it; otherwise, soft-delete stale chunks first (mark status=stale), then insert new chunks, then hard-delete stale.

  5. Deletion handler (same pipeline): When event_type == deleted, retrieve all chunk IDs with doc_id = X from the chunk-to-source mapping table, delete them from the vector index, then delete the mapping record.

Latency budget: Webhook delivery 1-10 s + queue wait 1-5 s + embedding generation 10-40 s + index write 1-5 s = 13-60 s total — well within 3 minutes.

Failure modes and mitigations:

Failure Impact Mitigation
Webhook not delivered Event lost; doc not re-indexed Supplemental batch reconciliation job (hourly diff between source and index)
Embedding API timeout Event stuck in queue Retry with exponential backoff; DLQ after 5 failures; alert on DLQ depth
Vector DB write fails Stale index Soft-delete + transactional write; idempotent retry safe
Out-of-order events (update received before create) Incorrect state Idempotent processing by doc_id; last-write-wins semantics
Document deleted from source but event missed Zombie chunks in index Periodic full reconciliation: scan index for chunks whose source_url returns 404

Common Mistake: Building the happy path only and assuming events are delivered exactly once in order. Real-world event systems deliver events at-least-once and occasionally out of order. Idempotent processing with a last-write-wins key is mandatory, not optional.

22.11 Adapter Layer Design: Extending Pipelines Without Touching the Core

One of the most common enterprise integration patterns is the need to add AI capabilities to an existing data pipeline without refactoring the core system. The failure mode: modifying the core pipeline directly, introducing AI-specific failure modes into a system that was previously stable.

The correct pattern is the adapter layer: a thin translation and orchestration component that sits between the existing pipeline and the AI system, translating data formats in both directions without requiring changes to either.

22.11.1 The Adapter Pattern

# adapter.py — wraps the AI extraction system for an existing pipeline
from dataclasses import dataclass
from typing import Optional
import json

@dataclass
class LegacyDocument:
    """Format the existing pipeline produces."""
    document_id: str
    raw_text: str
    source_system: str
    metadata: dict

@dataclass
class EnrichedDocument:
    """Format the downstream system expects."""
    document_id: str
    raw_text: str
    source_system: str
    metadata: dict
    # New AI-extracted fields — defaulted so existing consumers are unaffected
    extracted_entities: list[dict] = None
    confidence_score: float = None
    extraction_status: str = "pending"  # pending | success | failed | skipped

class AIExtractionAdapter:
    """
    Adapter layer: wraps AI extraction so the core pipeline never changes.
    Transforms LegacyDocument → EnrichedDocument.
    If AI extraction fails, returns the document with extraction_status=failed
    rather than raising — never lets AI failure break the core pipeline.
    """

    def __init__(self, extractor, confidence_threshold: float = 0.75):
        self.extractor = extractor
        self.confidence_threshold = confidence_threshold

    def enrich(self, doc: LegacyDocument) -> EnrichedDocument:
        enriched = EnrichedDocument(
            document_id=doc.document_id,
            raw_text=doc.raw_text,
            source_system=doc.source_system,
            metadata=doc.metadata,
        )
        try:
            result = self.extractor.extract(doc.raw_text)
            enriched.extracted_entities = result.entities
            enriched.confidence_score = result.confidence
            enriched.extraction_status = (
                "success" if result.confidence >= self.confidence_threshold
                else "low_confidence"
            )
        except Exception as e:
            # AI failure is never a pipeline failure
            enriched.extraction_status = "failed"
            enriched.metadata["extraction_error"] = str(e)
        return enriched

# Production Gotcha: The adapter must never raise. Any exception from the AI
# system is caught here and recorded in the extraction_status field.
# Downstream consumers check extraction_status before using AI fields.

22.11.2 When to Use the Adapter Pattern

  • Adding AI enrichment to an existing ETL pipeline: The adapter runs as a parallel step after ingestion but before storage; the storage layer receives an enriched document with nullable AI fields.
  • Gradual migration: Run the adapter in “shadow mode” first (enrich but don’t write AI fields to the live system). Compare results against manual annotation before activating.
  • Multi-vendor AI: If you want to swap AI providers (or run multiple), the adapter normalizes the output format so downstream consumers are provider-agnostic.

22.12 Rules vs. ML vs. LLM Decision Framework

Every component in an enterprise AI pipeline has a decision point: should this component be a rule, an ML model, or an LLM call? Getting this wrong wastes money, reduces reliability, and creates brittle systems.

DECISION FRAMEWORK FOR COMPONENT TYPE

IF the logic is deterministic and exhaustively listable:
    → Use a rule (regex, lookup table, conditional)
    Examples: format validation, field extraction from structured data,
              routing by document type when document type is reliably detectable

IF the logic requires pattern recognition from labeled examples
   AND training data exists (≥1000 labeled examples)
   AND output is a fixed set of classes or a numeric value:
    → Use a trained ML model (GBT, logistic regression, neural classifier)
    Examples: document priority scoring, spam/not-spam, category classification
              when categories are predefined

IF the logic requires semantic understanding or generation
   AND the output space cannot be fully enumerated
   AND accuracy on edge cases matters more than latency/cost:
    → Use an LLM
    Examples: free-text extraction with semantic understanding,
              summarization, Q&A over documents, anomaly explanation

IF you are unsure:
    → Start with rules, measure where rules fail, train ML for those cases
    → Only introduce LLM where ML accuracy ceiling is insufficient
Component Type Latency Cost Determinism When to Use
Rule / Regex < 1 ms ~$0 100% Fixed format, enumerable logic
Trained ML model 1–100 ms Low High Labeled data exists, fixed output space
LLM (small/fast) 200–800 ms Low-Med Low Semantic understanding, short output
LLM (large) 1–10 s High Low Complex reasoning, long generation

The layered approach: Build the cheapest component that works for the majority case; use the expensive component only for the cases the cheap one fails. A document classifier that handles 70% of cases with a rule (document type is in the filename) and 25% with a GBT model (document type from structural features) and 5% with an LLM (ambiguous documents requiring content understanding) costs a fraction of a pure-LLM approach.

22.13 Config-Driven Output Mapping (Taxonomy Translation Pattern)

Enterprise customers have their own taxonomies, field names, and category structures. A system that hard-codes output field names or category labels becomes a custom build for every customer. The taxonomy translation pattern makes the mapping customer-configurable without code changes.

# taxonomy_mapper.py
from typing import Any
import json

class TaxonomyMapper:
    """
    Maps from canonical AI output schema to customer-specific schema.
    Configuration is loaded from a per-customer config file — no code changes
    required to support a new customer's taxonomy.
    """

    def __init__(self, config_path: str):
        with open(config_path) as f:
            config = json.load(f)
        self.field_mapping = config.get("field_mapping", {})
        self.category_mapping = config.get("category_mapping", {})
        self.default_values = config.get("default_values", {})

    def translate(self, canonical_output: dict) -> dict:
        """Translate canonical schema to customer schema."""
        result = {}
        for canonical_field, value in canonical_output.items():
            # Map field name
            customer_field = self.field_mapping.get(canonical_field, canonical_field)
            # Map categorical value if applicable
            if canonical_field in self.category_mapping:
                value = self.category_mapping[canonical_field].get(value, value)
            result[customer_field] = value

        # Apply defaults for fields not present in canonical output
        for field, default in self.default_values.items():
            if field not in result:
                result[field] = default

        return result

22.14 Human-in-the-Loop Review Queues

Not every AI output should be served directly to downstream systems. For high-stakes extractions (compliance documents, medical records, financial instruments) or low-confidence outputs, a human review step before final ingestion is essential.

# review_queue.py — route low-confidence extractions to human review
from dataclasses import dataclass, field
from enum import Enum

import uuid

class ReviewQueue:
    """Routes AI outputs to human review based on configurable criteria."""

    def __init__(self, storage_backend, confidence_threshold: float = 0.80):
        self.storage = storage_backend
        self.confidence_threshold = confidence_threshold

    def should_review(self, result) -> tuple[bool, str]:
        """Determine if an extraction result needs human review."""
        if result.confidence_score < self.confidence_threshold:
            return True, f"Low confidence: {result.confidence_score:.2f}"
        if result.has_conflicting_fields():
            return True, "Conflicting extracted fields"
        if result.document_type in self.high_stakes_types:
            return True, "High-stakes document type requires review"
        return False, ""

                confidence_score: float, reason: str) -> ReviewItem:

            document_id=document_id,
            ai_output=ai_output,
            confidence_score=confidence_score,
            reason_for_review=reason
        )
        self.storage.save(item)
        return item

    def approve(self, item_id: str, reviewer_id: str,
                edited_output: dict = None) -> ReviewItem:
        item = self.storage.get(item_id)
        item.status = ReviewStatus.APPROVED if not edited_output else ReviewStatus.EDITED
        item.reviewer_id = reviewer_id
        item.reviewed_output = edited_output or item.ai_output
        item.reviewed_at = datetime.utcnow()
        self.storage.save(item)
        return item

22.15 Data Pipeline Design for Multi-Format Inputs

Enterprise data arrives in every format: email bodies, PDF attachments, CSV exports, API payloads, scanned images, Excel files. A pipeline that handles each format independently becomes unmaintainable. The canonical approach is a format-agnostic ingestion layer that normalizes all inputs to a canonical intermediate format before any AI processing.

# ingestion_layer.py — normalize multi-format inputs to canonical text
from pathlib import Path
import mimetypes

class DocumentIngestionPipeline:
    """
    Multi-format ingestion pipeline.
    Normalizes all document types to (text, metadata) pairs.
    """

    def __init__(self):
        self.extractors = {
            "application/pdf": self._extract_pdf,
            "text/plain": self._extract_text,
            "text/html": self._extract_html,
            "application/vnd.openxmlformats-officedocument.wordprocessingml.document":
                self._extract_docx,
            "text/csv": self._extract_csv,
            "message/rfc822": self._extract_email,
        }

    def ingest(self, source: str | bytes,
               mime_type: str = None,
               metadata: dict = None) -> dict:
        """
        Returns canonical document dict:
        {text, pages, source_type, metadata, extraction_quality}
        """
        if mime_type is None:
            mime_type = self._detect_mime_type(source)

        extractor = self.extractors.get(mime_type)
        if extractor is None:
            return {"text": "", "extraction_quality": "unsupported",
                    "source_type": mime_type, "metadata": metadata or {}}

        try:
            text, doc_metadata = extractor(source)
            return {
                "text": text,
                "extraction_quality": self._assess_quality(text),
                "source_type": mime_type,
                "metadata": {**(metadata or {}), **doc_metadata}
            }
        except Exception as e:
            return {
                "text": "",
                "extraction_quality": "failed",
                "source_type": mime_type,
                "error": str(e),
                "metadata": metadata or {}
            }

    def _assess_quality(self, text: str) -> str:
        """Heuristic quality check on extracted text."""
        if not text or len(text) < 50:
            return "empty"
        # Heuristic: high ratio of non-ASCII chars often indicates OCR artifacts
        non_ascii = sum(1 for c in text if ord(c) > 127)
        if non_ascii / len(text) > 0.3:
            return "degraded"
        return "good"

    def _extract_pdf(self, source) -> tuple[str, dict]:
        import pdfplumber
        text_parts = []
        with pdfplumber.open(source) as pdf:
            for page in pdf.pages:
                text_parts.append(page.extract_text() or "")
        return "\n\n".join(text_parts), {"page_count": len(pdf.pages)}

    def _extract_email(self, source) -> tuple[str, dict]:
        import email
        msg = email.message_from_bytes(source if isinstance(source, bytes)
                                       else source.encode())
        parts = []
        if msg.is_multipart():
            for part in msg.walk():
                if part.get_content_type() == "text/plain":
                    parts.append(part.get_payload(decode=True).decode(errors="replace"))
        else:
            parts.append(msg.get_payload(decode=True).decode(errors="replace"))
        return "\n".join(parts), {
            "from": msg.get("From", ""),
            "subject": msg.get("Subject", ""),
            "date": msg.get("Date", "")
        }

# Digitally-native PDFs extract cleanly. Scanned PDFs may need OCR (Tesseract,
# AWS Textract, or similar). Always log extraction_quality and alert on high

22.16 Idempotency Patterns for Submission and Event Ingestion

When a document submission event is processed more than once — due to network retry, queue redelivery, or system restart — the result must be the same as if it had been processed once. Without idempotency, retries cause duplicate records, doubled charges, and inconsistent state.

# idempotency.py — idempotent event processing
import hashlib
import time
from typing import Optional

class IdempotencyStore:
    """Tracks processed event IDs to prevent duplicate processing."""

    def __init__(self, redis_client, ttl_seconds: int = 86400 * 7):
        self.redis = redis_client
        self.ttl = ttl_seconds
        self.key_prefix = "idempotency:"

    def _make_key(self, idempotency_key: str) -> str:
        return f"{self.key_prefix}{idempotency_key}"

    def is_already_processed(self, idempotency_key: str) -> bool:
        return self.redis.exists(self._make_key(idempotency_key)) == 1

    def mark_processing(self, idempotency_key: str) -> bool:
        """
        Atomically set if not exists. Returns True if this process
        acquired the lock, False if another process is already handling it.
        """
        key = self._make_key(idempotency_key)
        # SET NX: only set if key doesn't exist (atomic)
        result = self.redis.set(key, "processing", nx=True, ex=300)  # 5 min lock
        return result is not None

    def mark_complete(self, idempotency_key: str, result_summary: str = ""):
        """Mark as permanently processed with result."""
        key = self._make_key(idempotency_key)
        self.redis.set(key, f"done:{result_summary}", ex=self.ttl)


def make_idempotency_key(doc_id: str, event_type: str, version: str) -> str:
    """Create a deterministic idempotency key from event fields."""
    payload = f"{doc_id}:{event_type}:{version}"
    return hashlib.sha256(payload.encode()).hexdigest()[:32]


class IdempotentEventProcessor:
    """Wraps event processing with idempotency guarantee."""

    def __init__(self, processor_fn, idempotency_store: IdempotencyStore):
        self.process = processor_fn
        self.store = idempotency_store

    def handle(self, event: dict) -> dict:
        idem_key = make_idempotency_key(
            event["doc_id"], event["event_type"], event.get("version", "")
        )

        # Already processed — return early
        if self.store.is_already_processed(idem_key):
            return {"status": "already_processed", "idempotency_key": idem_key}

        # Acquire processing lock
        if not self.store.mark_processing(idem_key):
            return {"status": "being_processed", "idempotency_key": idem_key}

        try:
            result = self.process(event)
            self.store.mark_complete(idem_key, result.get("summary", ""))
            return {"status": "processed", "result": result}
        except Exception as e:
            # Do not mark complete on failure — allow retry
            raise

# Production Gotcha: The idempotency store itself can fail (Redis down).
# When Redis is unavailable, the safest fallback is to process anyway
# (accept occasional duplicates) rather than block all processing.
# Log a warning and proceed — duplicate detection is best-effort.
# The alternative (blocking all events when Redis is down) causes total
# pipeline failure, which is much worse than occasional duplicates.

The Redis-down fallback question comes up in interviews: if your idempotency check depends on Redis, and Redis goes down, what do you do? The answer is: process anyway with a log warning. Occasional duplicate processing is recoverable (downstream deduplication, idempotent downstream writes). A complete pipeline halt while Redis recovers is not recoverable in many SLA contexts.

Q3. Design a near-real-time RAG index freshness system that gets from document change to searchable in under 3 minutes. What are the failure modes and how do you handle them?

Model Answer

What great looks like: A full pipeline design with latency budget, idempotency analysis, failure mode enumeration, and a specific approach for each failure mode.

Pipeline architecture:

  1. Change detection (0-10 s): Register webhooks with the source system (SharePoint, Confluence, S3 event notifications). For database sources, use CDC (Debezium on Postgres, DynamoDB Streams). Each event carries: (doc_id, event_type: created|updated|deleted, source_url, timestamp).

  2. Event queue (1-5 s): Route events to a durable message queue (SQS, Pub/Sub). Queue provides retry, ordering guarantee (FIFO queue), and decoupling between ingestion rate and processing speed. Set visibility timeout to 3× the expected processing time.

  3. Document processor (15-60 s): Consumer fetches the full document, runs the ingestion pipeline (text extraction, chunking, embedding generation), and writes to the vector index. Use doc_id as the idempotent key — reprocessing the same document ID converges to the correct state.

  4. Index writer (1-5 s): Delete stale chunks (DELETE WHERE doc_id = X), insert new chunks. Wrap in a transaction where the vector DB supports it; otherwise, soft-delete stale chunks first (mark status=stale), then insert new chunks, then hard-delete stale.

  5. Deletion handler (same pipeline): When event_type == deleted, retrieve all chunk IDs with doc_id = X from the chunk-to-source mapping table, delete them from the vector index, then delete the mapping record.

Latency budget: Webhook delivery 1-10 s + queue wait 1-5 s + embedding generation 10-40 s + index write 1-5 s = 13-60 s total — well within 3 minutes.

Failure modes and mitigations:

Failure Impact Mitigation
Webhook not delivered Event lost; doc not re-indexed Supplemental batch reconciliation job (hourly diff between source and index)
Embedding API timeout Event stuck in queue Retry with exponential backoff; DLQ after 5 failures; alert on DLQ depth
Vector DB write fails Stale index Soft-delete + transactional write; idempotent retry safe
Out-of-order events (update received before create) Incorrect state Idempotent processing by doc_id; last-write-wins semantics
Document deleted from source but event missed Zombie chunks in index Periodic full reconciliation: scan index for chunks whose source_url returns 404

Common Mistake: Building the happy path only and assuming events are delivered exactly once in order. Real-world event systems deliver events at-least-once and occasionally out of order. Idempotent processing with a last-write-wins key is mandatory, not optional.

## 1. API Integration Patterns

### The Three Latency Regimes

GenAI APIs have fundamentally different latency characteristics from traditional CRUD endpoints. A Postgres query takes 1-10 ms. An LLM generation for a 500-token response takes 2-30 seconds depending on model size, provider load, and output length. This single fact forces three distinct API patterns, each occupying a latency regime.

**Plain-English definition:** An API integration pattern is the structural shape of the client-server interaction — how the client sends a request, how it receives data, and what happens when things go wrong.

**Analogy:** Think of the three patterns like three ways to order coffee. Synchronous is a drive-through — you wait at the window until the cup is in your hand. Streaming is an espresso bar where the barista calls your name as each drink component is ready. Async with a webhook is ordering via a mobile app — you submit, go sit down, and the app buzzes you when the order is ready.

| Pattern | Latency range | Best for | Avoid when |
|---|---|---|---|
| Synchronous (blocking) | < 3 s | Simple classification, embedding, short extraction | User is watching, response > 5 s |
| Streaming (SSE) | First token 0.3-1 s | User-facing chat, copilot features | Client can't consume streams (legacy systems) |
| Async + webhook/polling | 10 s – 10 min | Document analysis, batch summarization, multi-step agents | User needs real-time answer |

::: {.callout-warning}
**Common Misconception:** "We can just set a longer HTTP timeout and use synchronous for everything."

HTTP timeouts at load balancers, API gateways, and CDNs are typically 30-60 seconds and not always configurable. A document analysis job that takes 90 seconds will be killed at the network layer before the LLM finishes. Use async for anything that might exceed 25 seconds.
:::

### Streaming with Server-Sent Events (SSE)

SSE is the standard mechanism for streaming tokens from an LLM server to a browser or API client. It is unidirectional (server to client), uses a plain HTTP connection, and has native browser support via `EventSource`. For non-browser clients, SSE is trivial to parse: each event is a text line prefixed with `data:`.

**Why it matters for UX:** In user studies, perceived latency drops dramatically when content appears progressively. A 10-second streaming response feels faster than a 3-second synchronous response because the user receives signal within 400 ms that something is happening.

```python
# streaming_client.py — production-grade SSE streaming with retry and error handling
import anthropic
import httpx
from typing import Iterator

def stream_completion(
    prompt: str,
    system: str = "",
    model: str = "claude-sonnet-4-5",
    max_tokens: int = 1024,
) -> Iterator[str]:
    """
    Streams tokens from the Anthropic API.
    Yields text chunks as they arrive.
    Raises on non-retryable errors; caller handles retry logic.
    """
    client = anthropic.Anthropic()

    with client.messages.stream(
        model=model,
        max_tokens=max_tokens,
        system=system,
        messages=[{"role": "user", "content": prompt}],
    ) as stream:
        for text_chunk in stream.text_stream:
            yield text_chunk

        # Final message gives token counts for cost tracking
        final_message = stream.get_final_message()
        usage = final_message.usage
        # Log usage for cost attribution
        _log_usage(model=model, input_tokens=usage.input_tokens,
                   output_tokens=usage.output_tokens)


def _log_usage(model: str, input_tokens: int, output_tokens: int):
    """Emit a structured log entry for cost tracking."""
    import json, logging
    logging.info(json.dumps({
        "event": "llm_usage",
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
    }))


# FastAPI SSE endpoint — sends tokens to the browser as they arrive
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/chat/stream")
async def chat_stream(payload: dict):
    prompt = payload.get("prompt", "")

    def event_generator():
        try:
            for chunk in stream_completion(prompt):
                # SSE format: each line starts with "data: "
                yield f"data: {chunk}\n\n"
            # Signal end of stream
            yield "data: [DONE]\n\n"
        except Exception as e:
            # Errors mid-stream must be sent as a special event type
            yield f"event: error\ndata: {str(e)}\n\n"

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",  # Disable Nginx buffering
        },
    )
```

**Production gotcha:** Nginx and many reverse proxies buffer responses by default. Add `X-Accel-Buffering: no` (Nginx) or equivalent headers to ensure tokens flow to the client immediately rather than being buffered until the response is complete. Without this, streaming degrades to synchronous from the user's perspective.

### Async Processing with Webhooks

For tasks that take more than 25-30 seconds — multi-document analysis, complex agent runs, batch summarization — the client cannot wait for an HTTP response. The correct pattern is:

1. Client POSTs job request → server returns `HTTP 202 Accepted` with a `job_id` immediately.
2. Server processes the job asynchronously (Celery worker, Cloud Run job, Lambda).
3. On completion, server POSTs results to the client's registered webhook URL.
4. Client also polls `GET /jobs/{job_id}` for status (fallback when webhooks fail).

```python
# async_job.py — webhook delivery with retry
import httpx
import asyncio
import json
from dataclasses import dataclass
from enum import Enum

class JobStatus(Enum):
    PENDING = "pending"
    PROCESSING = "processing"
    COMPLETED = "completed"
    FAILED = "failed"

@dataclass
class Job:
    job_id: str
    webhook_url: str
    prompt: str
    status: JobStatus = JobStatus.PENDING
    result: str | None = None
    error: str | None = None

async def deliver_webhook(job: Job, max_attempts: int = 5) -> bool:
    """
    Delivers webhook with exponential backoff.
    Returns True on successful delivery, False after all retries exhausted.
    """
    payload = {
        "job_id": job.job_id,
        "status": job.status.value,
        "result": job.result,
        "error": job.error,
    }
    base_delay = 1.0  # seconds

    async with httpx.AsyncClient(timeout=10.0) as client:
        for attempt in range(max_attempts):
            try:
                response = await client.post(
                    job.webhook_url,
                    json=payload,
                    headers={"Content-Type": "application/json"},
                )
                if response.status_code in (200, 201, 204):
                    return True
                # 4xx errors are not retryable (bad webhook URL)
                if 400 <= response.status_code < 500:
                    return False
            except (httpx.ConnectError, httpx.TimeoutException):
                pass  # Transient; retry

            # Exponential backoff with jitter
            import random
            delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
            await asyncio.sleep(min(delay, 60.0))  # Cap at 60 s

    return False  # All retries exhausted
```

## 2. Retry Strategies: Exponential Backoff with Jitter

**Plain-English definition:** When an API call fails transiently (rate limit, transient 503), retry after a delay. Make each delay longer than the last (exponential) and add randomness (jitter) to prevent all retrying clients from hammering the provider simultaneously.

**Analogy:** Imagine 100 people all trying to call the same busy phone number. If they all hang up and immediately redial at the same time, the line stays busy. If each person waits a random amount of time before retrying, calls spread out and the line clears.

**The formula:** `delay = min(base * 2^attempt + random(0, 1), max_delay)`

```python
# retry.py — production retry decorator with jitter and provider error classification
import time
import random
import functools
import logging
from typing import Callable, TypeVar, Type

logger = logging.getLogger(__name__)
T = TypeVar("T")

# Errors that should be retried (transient)
RETRYABLE_STATUS_CODES = {429, 500, 502, 503, 504}

class RetryExhausted(Exception):
    """Raised when all retry attempts fail."""
    pass

def with_retry(
    max_attempts: int = 5,
    base_delay: float = 1.0,
    max_delay: float = 60.0,
    retryable_exceptions: tuple[Type[Exception], ...] = (Exception,),
):
    """
    Decorator: retry with exponential backoff + full jitter.
    Full jitter: delay = random(0, min(base * 2^attempt, max_delay))
    This distributes retries evenly across the range [0, cap].
    """
    def decorator(func: Callable) -> Callable:
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_exception = None
            for attempt in range(max_attempts):
                try:
                    return func(*args, **kwargs)
                except retryable_exceptions as exc:
                    last_exception = exc
                    if attempt == max_attempts - 1:
                        break  # No more retries

                    # Full jitter: uniform random in [0, cap]
                    cap = min(base_delay * (2 ** attempt), max_delay)
                    delay = random.uniform(0, cap)

                    logger.warning(
                        "Attempt %d/%d failed: %s. Retrying in %.2fs.",
                        attempt + 1, max_attempts, str(exc), delay,
                    )
                    time.sleep(delay)

            raise RetryExhausted(
                f"All {max_attempts} attempts failed. "
                f"Last error: {last_exception}"
            ) from last_exception
        return wrapper
    return decorator


# Usage with Anthropic SDK
import anthropic

@with_retry(
    max_attempts=5,
    base_delay=1.0,
    max_delay=30.0,
    retryable_exceptions=(anthropic.RateLimitError, anthropic.APIStatusError),
)
def call_llm(prompt: str) -> str:
    client = anthropic.Anthropic()
    message = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=512,
        messages=[{"role": "user", "content": prompt}],
    )
    return message.content[0].text
```

::: {.callout-warning}
**Common Mistake:** Using uniform retry delays (always wait 2 seconds) instead of exponential backoff. Under sustained provider unavailability, uniform retries maintain high request volume and may cause your account to be rate-limited further. Exponential backoff naturally reduces retry pressure as outage duration increases.

Also: never retry on 4xx client errors (400, 401, 403, 404) — these are not transient. Retrying a malformed request wastes tokens and hides bugs.
:::

## 3. LLM Provider Abstraction Layer

**When to build one:** As soon as you have two requirements: (a) more than one LLM provider in use or planned, OR (b) the need to fail over from a primary provider to a secondary during outages.

**When not to build one:** If you have exactly one provider and no plans to switch, abstractions add complexity without benefit. YAGNI (You Aren't Gonna Need It) applies.

**Analogy:** A power strip with a universal adapter. Your devices (application code) plug into a single standardized interface; the adapter handles the different voltages and plug shapes behind the scenes.

```python
# llm_gateway.py — provider-agnostic LLM gateway with failover and cost tracking
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from typing import Optional
import time
import logging

logger = logging.getLogger(__name__)

@dataclass
class LLMResponse:
    text: str
    model: str
    provider: str
    input_tokens: int
    output_tokens: int
    latency_ms: float
    cost_usd: float

@dataclass
class ProviderConfig:
    name: str
    model: str
    cost_per_1k_input_tokens: float
    cost_per_1k_output_tokens: float
    priority: int = 0  # Lower = higher priority


class LLMProvider(ABC):
    """Abstract base class for LLM provider implementations."""
    def __init__(self, config: ProviderConfig):
        self.config = config

    @abstractmethod
    def complete(self, prompt: str, system: str, max_tokens: int) -> LLMResponse:
        ...

    def _compute_cost(self, input_tokens: int, output_tokens: int) -> float:
        return (
            input_tokens / 1000 * self.config.cost_per_1k_input_tokens
            + output_tokens / 1000 * self.config.cost_per_1k_output_tokens
        )


class AnthropicProvider(LLMProvider):
    def complete(self, prompt: str, system: str = "", max_tokens: int = 1024) -> LLMResponse:
        import anthropic
        client = anthropic.Anthropic()
        start = time.monotonic()

        message = client.messages.create(
            model=self.config.model,
            max_tokens=max_tokens,
            system=system,
            messages=[{"role": "user", "content": prompt}],
        )
        latency_ms = (time.monotonic() - start) * 1000

        return LLMResponse(
            text=message.content[0].text,
            model=self.config.model,
            provider="anthropic",
            input_tokens=message.usage.input_tokens,
            output_tokens=message.usage.output_tokens,
            latency_ms=latency_ms,
            cost_usd=self._compute_cost(
                message.usage.input_tokens, message.usage.output_tokens
            ),
        )


class OpenAIProvider(LLMProvider):
    def complete(self, prompt: str, system: str = "", max_tokens: int = 1024) -> LLMResponse:
        from openai import OpenAI
        client = OpenAI()
        start = time.monotonic()

        response = client.chat.completions.create(
            model=self.config.model,
            max_tokens=max_tokens,
            messages=[
                {"role": "system", "content": system},
                {"role": "user", "content": prompt},
            ],
        )
        latency_ms = (time.monotonic() - start) * 1000
        usage = response.usage

        return LLMResponse(
            text=response.choices[0].message.content,
            model=self.config.model,
            provider="openai",
            input_tokens=usage.prompt_tokens,
            output_tokens=usage.completion_tokens,
            latency_ms=latency_ms,
            cost_usd=self._compute_cost(usage.prompt_tokens, usage.completion_tokens),
        )


class LLMGateway:
    """
    Manages a prioritized list of providers with automatic failover.
    Logs cost to a pluggable cost tracker.
    """
    def __init__(self, providers: list[LLMProvider]):
        # Sort by priority; lower value = tried first
        self.providers = sorted(providers, key=lambda p: p.config.priority)

    def complete(
        self,
        prompt: str,
        system: str = "",
        max_tokens: int = 1024,
    ) -> LLMResponse:
        errors = []
        for provider in self.providers:
            try:
                response = provider.complete(prompt, system, max_tokens)
                self._record_cost(response)
                return response
            except Exception as exc:
                logger.warning(
                    "Provider %s failed: %s. Trying next.",
                    provider.config.name, exc,
                )
                errors.append((provider.config.name, str(exc)))

        raise RuntimeError(
            f"All LLM providers failed: {errors}"
        )

    def _record_cost(self, response: LLMResponse):
        logger.info(
            "llm_cost provider=%s model=%s input_tokens=%d "
            "output_tokens=%d cost_usd=%.6f latency_ms=%.1f",
            response.provider, response.model,
            response.input_tokens, response.output_tokens,
            response.cost_usd, response.latency_ms,
        )
```

## 4. Context Window Management

**Plain-English definition:** Every LLM call has a maximum number of tokens that can appear in the combined input (system prompt + conversation history + retrieved context + user message). When conversation history grows beyond this limit, you must decide what to discard.

**Why it matters:** At $0.003/1K tokens for mid-tier models, a 200K-token context window full of conversation history costs $0.60 per request — before output tokens. For a high-volume application with 10K daily active users averaging 5 queries/session, that is $30K/day purely in input token costs.

### Strategy 1: Sliding Window

Keep the N most recent turns. Discard the oldest turns as the window fills.

```python
# context_manager.py — three context window strategies
from dataclasses import dataclass, field
from typing import Literal

@dataclass
class Message:
    role: Literal["user", "assistant"]
    content: str

    @property
    def token_estimate(self) -> int:
        # Rough estimate: 1 token ~ 4 characters
        return len(self.content) // 4

@dataclass
class ConversationContext:
    messages: list[Message] = field(default_factory=list)
    max_tokens: int = 4000  # Reserve for system prompt + retrieved context

    def add_message(self, role: str, content: str):
        self.messages.append(Message(role=role, content=content))
        self._trim_to_budget()

    def _trim_to_budget(self):
        """Sliding window: drop oldest messages until within budget."""
        while self._total_tokens() > self.max_tokens and len(self.messages) > 2:
            # Always keep at least the most recent exchange
            self.messages.pop(0)

    def _total_tokens(self) -> int:
        return sum(m.token_estimate for m in self.messages)

    def to_api_messages(self) -> list[dict]:
        return [{"role": m.role, "content": m.content} for m in self.messages]
```

### Strategy 2: Summarization Buffer

When the window fills, call the LLM to summarize the oldest N turns, then replace those turns with the summary. Preserves semantic information at the cost of an extra LLM call.

```python
class SummarizingContext:
    def __init__(self, max_tokens: int = 4000, summarize_threshold: int = 3000):
        self.messages: list[Message] = []
        self.summary: str = ""
        self.max_tokens = max_tokens
        self.summarize_threshold = summarize_threshold

    def add_message(self, role: str, content: str):
        self.messages.append(Message(role=role, content=content))
        if self._total_tokens() > self.summarize_threshold:
            self._summarize_oldest_half()

    def _summarize_oldest_half(self):
        midpoint = len(self.messages) // 2
        to_summarize = self.messages[:midpoint]
        self.messages = self.messages[midpoint:]

        # Call LLM to summarize the dropped turns
        import anthropic
        client = anthropic.Anthropic()
        text = "\n".join(
            f"{m.role}: {m.content}" for m in to_summarize
        )
        response = client.messages.create(
            model="claude-haiku-4-5",  # Use cheapest model for summarization
            max_tokens=256,
            messages=[{
                "role": "user",
                "content": (
                    f"Summarize this conversation segment in 3-4 sentences, "
                    f"preserving key facts and decisions:\n\n{text}"
                ),
            }],
        )
        new_summary = response.content[0].text
        self.summary = (
            f"{self.summary}\n{new_summary}".strip()
            if self.summary else new_summary
        )

    def to_api_messages(self) -> list[dict]:
        messages = []
        if self.summary:
            messages.append({
                "role": "user",
                "content": f"[Conversation summary so far: {self.summary}]",
            })
            messages.append({"role": "assistant", "content": "Understood."})
        messages.extend(
            {"role": m.role, "content": m.content} for m in self.messages
        )
        return messages

    def _total_tokens(self) -> int:
        return sum(m.token_estimate for m in self.messages)
```

### Strategy 3: Hierarchical (RAG over conversation history)

For very long sessions (document editing, code review over a large codebase), index the conversation history in a vector store and retrieve only the relevant portions per turn.

**When to use each strategy:**

| Strategy | Best for | Avoid when |
|---|---|---|
| Sliding window | Short chat sessions, < 20 turns | Need long-term memory |
| Summarization | Medium sessions, need context continuity | Cost-sensitive at scale |
| Hierarchical (RAG over history) | Long sessions, document work | Latency is critical |

## 5. Vector Database Integration Patterns

**Plain-English definition:** A vector database stores numerical embeddings (dense vector representations of text) and supports approximate nearest-neighbor (ANN) search — finding the stored vectors most similar to a query vector.

### Production Integration Pattern

```python
# vector_store.py — production-ready vector store abstraction with metadata filtering
from dataclasses import dataclass
from typing import Any
import hashlib

@dataclass
class Document:
    doc_id: str
    content: str
    metadata: dict[str, Any]
    embedding: list[float] | None = None

@dataclass
class SearchResult:
    doc_id: str
    content: str
    score: float
    metadata: dict[str, Any]

class VectorStore:
    """
    Thin wrapper around a vector DB client.
    Handles: upsert, delete, similarity search with metadata filter.
    """
    def __init__(self, client, namespace: str = "default"):
        self.client = client  # e.g., Pinecone Index, Qdrant Collection
        self.namespace = namespace

    def upsert(self, doc: Document) -> None:
        """
        Idempotent: upserting the same doc_id overwrites the previous entry.
        Use document URL or DB primary key as doc_id for idempotency.
        """
        if doc.embedding is None:
            raise ValueError("Document must have an embedding before upsert.")
        self.client.upsert(
            vectors=[{
                "id": doc.doc_id,
                "values": doc.embedding,
                "metadata": {**doc.metadata, "content": doc.content},
            }],
            namespace=self.namespace,
        )

    def delete(self, doc_id: str) -> None:
        """
        Remove a document by ID. Call this when source document is deleted
        to prevent stale citations.
        """
        self.client.delete(ids=[doc_id], namespace=self.namespace)

    def search(
        self,
        query_embedding: list[float],
        top_k: int = 5,
        metadata_filter: dict | None = None,
    ) -> list[SearchResult]:
        """
        Pre-filter search: apply metadata filter inside the vector DB.
        This is the recommended pattern for access control.
        """
        kwargs = {
            "vector": query_embedding,
            "top_k": top_k,
            "include_metadata": True,
            "namespace": self.namespace,
        }
        if metadata_filter:
            kwargs["filter"] = metadata_filter

        results = self.client.query(**kwargs)
        return [
            SearchResult(
                doc_id=match["id"],
                content=match["metadata"]["content"],
                score=match["score"],
                metadata={k: v for k, v in match["metadata"].items()
                          if k != "content"},
            )
            for match in results["matches"]
        ]


# Usage: pre-filter access control
def rag_query(
    question: str,
    user_groups: list[str],
    vector_store: VectorStore,
    embedder,  # Any embed(text) -> list[float] function
) -> list[SearchResult]:
    query_embedding = embedder(question)
    return vector_store.search(
        query_embedding=query_embedding,
        top_k=5,
        # Only return documents accessible to this user's groups
        metadata_filter={"allowed_groups": {"$in": user_groups}},
    )
```

::: {.callout-tip}
**Production gotcha:** Most vector databases support metadata filtering but with performance caveats. Filtering reduces the effective index size before ANN search, which can significantly degrade recall when a user's permission set covers < 10% of the total index. Benchmark with realistic permission distributions before committing to a pre-filter strategy on a large index.
:::

### Semantic Caching

```python
# semantic_cache.py — cosine similarity-based response cache
import numpy as np
from dataclasses import dataclass, field
from datetime import datetime, timedelta
import hashlib

@dataclass
class CacheEntry:
    query_embedding: list[float]
    response: str
    created_at: datetime
    ttl_hours: float = 24.0

    @property
    def is_expired(self) -> bool:
        return datetime.utcnow() > self.created_at + timedelta(hours=self.ttl_hours)

class SemanticCache:
    """
    Cache LLM responses by semantic similarity of the query.
    Hit rate metric: track and alert if it drops below baseline.
    Tune threshold empirically: 0.92-0.95 is typical for Q&A applications.
    """
    def __init__(self, similarity_threshold: float = 0.93, max_size: int = 10_000):
        self.threshold = similarity_threshold
        self.max_size = max_size
        self.entries: list[CacheEntry] = []
        self._hit_count = 0
        self._miss_count = 0

    def get(self, query_embedding: list[float]) -> str | None:
        """Returns cached response if a similar query was seen recently."""
        q = np.array(query_embedding)
        for entry in self.entries:
            if entry.is_expired:
                continue
            cached = np.array(entry.query_embedding)
            # Cosine similarity
            similarity = float(
                np.dot(q, cached) / (np.linalg.norm(q) * np.linalg.norm(cached) + 1e-10)
            )
            if similarity >= self.threshold:
                self._hit_count += 1
                return entry.response
        self._miss_count += 1
        return None

    def put(self, query_embedding: list[float], response: str, ttl_hours: float = 24.0):
        """Add a new entry, evicting expired entries if at capacity."""
        self._evict_expired()
        if len(self.entries) >= self.max_size:
            self.entries.pop(0)  # Evict oldest
        self.entries.append(CacheEntry(
            query_embedding=query_embedding,
            response=response,
            created_at=datetime.utcnow(),
            ttl_hours=ttl_hours,
        ))

    def _evict_expired(self):
        self.entries = [e for e in self.entries if not e.is_expired]

    @property
    def hit_rate(self) -> float:
        total = self._hit_count + self._miss_count
        return self._hit_count / total if total > 0 else 0.0
```

## 8. Observability

LLM observability extends conventional service observability with a quality dimension. A service that returns 200 OK with confident but wrong answers has perfect traditional reliability and terrible LLM reliability.

**The RAG triad — three quality metrics to track:**

| Metric | Definition | How to measure |
|---|---|---|
| Context relevance | Did we retrieve the right documents? | LLM-as-judge, or embedding similarity between query and retrieved docs |
| Faithfulness | Does the answer contradict the retrieved documents? | NLI model or LLM-as-judge |
| Answer relevance | Does the answer address the question? | LLM-as-judge on a 1-5 rubric |

::: {.callout-tip}
**Logging strategy at scale:** Log 100% of requests to a hot store (7-day retention) for debugging. Sample 2-5% to a cold store for long-term quality trend analysis. Running LLM-as-judge on 100% of traffic doubles your inference costs — sampling is the right tradeoff for most applications.
:::

## Cheat Sheet

- **Streaming (SSE):** First token in ~400 ms; perceived latency dramatically lower than synchronous even at same total latency; requires special error event type mid-stream; disable proxy buffering (Nginx: `X-Accel-Buffering: no`).
- **Async + webhook:** Use for any task > 25 s; return HTTP 202 + `job_id` immediately; implement both webhook push and polling fallback; include progress details in status endpoint.
- **Exponential backoff with full jitter:** `delay = random(0, min(base * 2^attempt, cap))`; never retry on 4xx (client errors); retry on 429 and 5xx only.
- **Provider abstraction layer:** Abstract when you have 2+ providers or need failover; add cost tracking and latency logging per provider; don't over-abstract if you have one provider and no switching plans.
- **LangChain:** Good for prototypes and demos; heavy dependency footprint; abstraction overhead hurts debugging in production.
- **LlamaIndex:** Purpose-built for RAG pipelines; recommended starting point for document search applications.
- **Custom integration:** Best for fine-grained control, thin footprint, easy debugging; preferred by mature production teams.
- **Sliding window context:** Simplest context management; always keep the 2 most recent turns; discard oldest first.
- **Summarization buffer:** Preserve semantic continuity at cost of extra LLM call; use cheapest model (Claude Haiku, GPT-3.5) for summarization.
- **Pre-filter access control:** Inject permission filter into vector DB query; only authorized documents are scored; preferred over post-filter for production.
- **Semantic caching:** 0.92-0.95 cosine threshold typical; tie TTL to index freshness; monitor hit rate — target 30-60% for FAQ apps.
- **Cost attribution tags:** `team_id`, `app_id`, `user_id`, `use_case`, `request_id` on every LLM call; enforce at gateway layer.
- **Model routing:** Route simple tasks (classification, short extraction) to cheaper models; 40-60% cost reduction achievable; routing classifier must be cheap.
- **RAG triad:** Context relevance + Faithfulness + Answer relevance; monitor all three; faithfulness drop usually precedes complaint wave.
- **Prompt versioning:** Every prompt template has a version; log `prompt_version` with every request; treat prompt changes like code changes (review, deploy, rollback).
- **Index freshness SLA:** Define it explicitly (batch: 24 h; event-driven: 5 min; streaming: 60 s); measure and alert on violations.
- **Document deletion:** Maintain `source_doc_id → [chunk_ids]` mapping; delete all chunks when source is deleted; soft-delete if recovery needed.
- **Hardcoded model versions:** Never hardcode exact version strings in production; pin to aliases you control; provider deprecations break hardcoded versions silently.
- **Human escalation path:** Every user-facing GenAI feature needs a visible path to a human; system should offer it when confidence is low.
- **LLM call idempotency:** LLM calls are NOT idempotent; blind infrastructure retries can produce duplicate responses; implement idempotency at application layer where semantically correct.

## Interview Questions

### Entry Level

::: {.callout-tip title="Entry Level"}

**Q1. What is the difference between synchronous and streaming LLM API calls? When would you use each?**

::: {.callout-note collapse="true" title="Model Answer"}
A synchronous call blocks until the entire response is generated, then returns it all at once. A streaming call returns tokens progressively as the model generates them.

Synchronous is appropriate when: the calling system is not user-facing (batch processing, backend pipeline), the expected response is very short (< 2 seconds), or the downstream consumer cannot process partial data.

Streaming is appropriate for nearly all user-facing features. When a user asks a question and sees text appearing within 400 ms, the experience feels responsive even if total generation takes 10 seconds. Waiting 10 seconds for a blank screen to suddenly show a full response feels broken.

The implementation difference: synchronous returns a complete `Message` object; streaming uses a context manager (`client.messages.stream(...)`) and you iterate over `stream.text_stream` to receive chunks.
:::

**Q2. What is exponential backoff and why does jitter matter?**

::: {.callout-note collapse="true" title="Model Answer"}
Exponential backoff is a retry strategy where each successive retry waits longer than the previous: retry 1 waits 1s, retry 2 waits 2s, retry 3 waits 4s, and so on. This reduces pressure on an overloaded provider by spacing retries further apart over time.

Jitter adds randomness to each delay. Without jitter, if 100 clients all hit a rate limit at the same time, they will all retry at the exact same moments (1s, 2s, 4s), creating synchronized waves of retry traffic. The provider stays overloaded. With jitter, each client waits a random amount within a range, spreading the retry load across time and allowing the provider to recover.

The full jitter formula: `delay = random(0, min(base * 2^attempt, max_delay))`. This distributes retries uniformly across the entire backoff range.
:::

**Q3. What is semantic caching? When does it help and when does it not?**

::: {.callout-note collapse="true" title="Model Answer"}
Semantic caching stores previous query-response pairs. When a new query arrives, its embedding is compared to cached query embeddings. If a cached query is sufficiently similar (above a cosine similarity threshold, typically 0.92-0.95), the cached response is returned instead of calling the LLM.

It helps when: many users ask similar questions (FAQ apps, documentation chatbots, internal knowledge bases). Cache hit rates of 30-80% are achievable in these contexts, directly reducing LLM costs and latency.

It does not help when: queries are highly personalized (each user's context is unique), content changes frequently (cached responses cite outdated information — tie TTL to index freshness), or the application requires responses tailored to specific user account state (balances, order history).

The key tuning parameter is the similarity threshold. Too high: cache underutilized. Too low: return cached responses to queries that were similar but meaningfully different.
:::

:::

### Mid Level

::: {.callout-warning title="Mid Level"}

**Q1. Explain the pre-filter vs. post-filter approaches to document-level access control in a RAG system. What are the tradeoffs?**

::: {.callout-note collapse="true" title="Model Answer"}
Both approaches address the same problem: a RAG knowledge base contains documents with different permission levels, and different users should see different documents in their answers.

**Pre-filter:** At indexing time, store each chunk with a metadata field listing which permission groups can access it (`allowed_groups: ["finance", "hr"]`). At query time, inject this as a filter into the vector search query, so only authorized chunks are scored and returned.

Advantages: no unauthorized content enters the LLM context (defense in depth); recall is correct for the user's authorized set; computationally efficient for coarse-grained permissions.

Disadvantages: requires the vector database to support metadata filtering alongside ANN search (most production databases do); permission changes require re-indexing affected chunks.

**Post-filter:** Retrieve top-k without access control, then remove unauthorized chunks before passing context to the LLM.

Advantages: simpler to implement — no changes to the retrieval query.

Disadvantages: unauthorized content is fetched and logged (security concern); if many top-k results are unauthorized, the filtered context is thin and answer quality degrades. A user with narrow permissions in a mixed knowledge base gets poor answers even when the knowledge exists in authorized documents.

**Recommendation:** Pre-filter for production enterprise deployments. Post-filter only for rapid prototyping. For very fine-grained per-document permissions, consider hybrid: coarse department-level pre-filter, exact document-level post-filter.
:::

**Q2. A team says their RAG app has 99.9% uptime but users keep complaining "it's not working." What is the observability gap and how do you close it?**

::: {.callout-note collapse="true" title="Model Answer"}
This is the classic reliability vs. quality gap in LLM systems. 99.9% uptime means the service is responding — it says nothing about whether responses are useful or accurate.

**The observability gap has three layers:**

1. No output quality monitoring. The system tracks request count and latency but not whether responses are correct or helpful. Users who get wrong answers don't generate HTTP 500 errors — they just report "it's broken."

2. No faithfulness monitoring. The system may be retrieving the wrong documents (low context relevance) or generating answers that contradict the retrieved documents (low faithfulness). Both look like "wrong answers" to users. Neither appears in uptime metrics.

3. No user feedback loop. Users experiencing failures have no mechanism to flag them at the point of failure. Issues surface only through support tickets — too slow and too aggregated to diagnose root causes.

**Closing the gap:**

- Implement the RAG triad metrics: context relevance, faithfulness, answer relevance. Track all three over time; alert on degradation.
- Add inline feedback (thumbs up/down) at the response level. Route low-rated responses to a review queue.
- Sample 2-5% of production responses through an LLM-as-judge quality evaluator. Track quality scores in a time-series dashboard.
- Correlate quality drops with prompt version changes and retrieval changes — most quality regressions have a root cause that is identifiable with proper attribution.
:::

**Q3. What are the failure modes of context window management approaches, and how do you choose between sliding window, summarization, and hierarchical retrieval?**

::: {.callout-note collapse="true" title="Model Answer"}
**Sliding window** drops the oldest turns verbatim. Failure mode: any fact established in an early turn is silently lost. If the user stated their name, account number, or a key constraint in turn 2 and the session is now at turn 30, that information is gone. The model may produce inconsistent answers as critical early context falls out. Works well for short sessions where continuity across 20+ turns is not required.

**Summarization buffer** compresses old turns via an LLM call. Failure mode: the summarizer is lossy — it drops specific details in favor of general trends. A precise number ("my budget is $47,500") may survive summarization ("the user has a budget around $45K-$50K") or may be dropped. Each summarization call adds latency and cost (use the cheapest model). Works well for medium-length sessions where semantic continuity matters more than specific detail recall.

**Hierarchical retrieval** (RAG over conversation history) indexes past turns in a vector store and retrieves relevant history per turn. Failure mode: retrieval may miss relevant context that is not semantically similar to the current query but is logically relevant (a constraint stated at the beginning of the session). Adds retrieval latency to every turn. Works best for very long sessions where the user is working on a specific artifact (document, codebase) and most turns are localized to a small part of the history.

**Choosing:** Short sessions (< 20 turns) → sliding window. Sessions where continuity matters and length is moderate → summarization buffer. Very long sessions with specific artifacts → hierarchical. In practice, most production chat applications use sliding window with a generous token budget (e.g., 8K context reserved for history), switching to summarization only when window pressure becomes a measurable quality issue.
:::

### Senior / FDE Level

::: {.callout-important title="Senior / Forward Deployed Engineer"}

**Q1. Design an LLM integration layer that supports OpenAI, Anthropic, and a locally-hosted model with automatic failover and per-team cost tracking. What are the key components and tradeoffs?**

::: {.callout-note collapse="true" title="Model Answer"}
> **What great looks like:** A systematic architecture answer that covers the abstraction interface, routing logic, failover mechanism, cost tracking, and operational concerns — not just "use LangChain."

**Key components:**

1. **Provider interface** — An abstract base class with a `complete(prompt, system, max_tokens) -> LLMResponse` method. `LLMResponse` carries `text`, `provider`, `model`, `input_tokens`, `output_tokens`, `latency_ms`, `cost_usd`. Each provider (Anthropic, OpenAI, local Ollama) implements this interface independently.

2. **Gateway** — Holds a prioritized list of providers. On each call: try provider 1; on failure (exception, timeout, or 5xx), log the error and try provider 2; continue until success or all providers exhausted. Failover policy can be static (always try Anthropic first) or dynamic (track error rates and deprioritize degraded providers using a circuit breaker).

3. **Cost tracker** — Plugged into the gateway. After each successful call, records `(team_id, app_id, user_id, provider, model, input_tokens, output_tokens, cost_usd, timestamp)` to a time-series database. Budget enforcement middleware checks the team's remaining budget before forwarding requests and returns HTTP 429 when budget is exhausted.

4. **Request context** — Every call carries a `CallContext` struct with `team_id`, `app_id`, `user_id`, `use_case`, `request_id`. This flows through the gateway into cost tracking and logs.

5. **Circuit breaker** — Per provider: track error rate over a 60-second window. If error rate > 20%, open the circuit breaker and route all traffic to the next provider for 60 seconds, then half-open (let 10% through to test recovery).

**Tradeoffs to articulate:**
- A thick abstraction layer is good for provider switching but makes debugging harder (errors from provider A look the same as errors from provider B unless the gateway adds rich logging).
- Failover improves reliability but increases costs (failed primary calls still consume some provider quota or at minimum incur latency). Budget the failover path explicitly.
- Local model failover trades cost for quality — if Anthropic is down and you fail over to a local 7B model, response quality drops significantly for complex tasks. Consider a "degrade gracefully" policy: simple queries fail over to local; complex queries return an error with a user-visible message.

> **Common Mistake:** Designing the gateway as a simple round-robin load balancer rather than a prioritized failover system. Round-robin actively sends traffic to degraded providers rather than routing around them.
:::

**Q2. A customer has 50 internal teams sharing a $200K/month LLM budget. Three teams routinely burn 80% of the budget by the 15th of each month, leaving the other 47 teams throttled. How do you design a fair and enforceable cost governance system?**

::: {.callout-note collapse="true" title="Model Answer"}

**Allocation:**

- Token counting is done on response (actual tokens from provider API), not estimated on request. Count atomically and update `tokens_used` in real time.
- Warning alerts at 70% utilization (weekly email to team lead) and 90% utilization (Slack alert to team lead + manager).

**Visibility:**
- A self-serve cost dashboard accessible to every team lead shows: real-time spend, daily trend, projected month-end spend (current rate × days remaining), per-application breakdown, and top-5 most expensive queries.
- The dashboard is the most impactful governance tool. Most overspend is accidental — teams that can see their consumption self-regulate.

**Addressing the three-team problem specifically:**

- Implement per-user daily token limits within a team's allocation. If one user or integration is consuming 90% of the team's budget, a per-user cap surfaces that for the team lead to investigate.
- Reserve a "floor allocation" for each team: a guaranteed minimum that cannot be consumed by other teams, even if the big consumers hit their caps.

**Q3. Design a near-real-time RAG index freshness system that gets from document change to searchable in under 3 minutes. What are the failure modes and how do you handle them?**

::: {.callout-note collapse="true" title="Model Answer"}
> **What great looks like:** A full pipeline design with latency budget, idempotency analysis, failure mode enumeration, and a specific approach for each failure mode.

**Pipeline architecture:**

1. **Change detection** (0-10 s): Register webhooks with the source system (SharePoint, Confluence, S3 event notifications). For database sources, use CDC (Debezium on Postgres, DynamoDB Streams). Each event carries: `(doc_id, event_type: created|updated|deleted, source_url, timestamp)`.

2. **Event queue** (1-5 s): Route events to a durable message queue (SQS, Pub/Sub). Queue provides retry, ordering guarantee (FIFO queue), and decoupling between ingestion rate and processing speed. Set visibility timeout to 3× the expected processing time.

3. **Document processor** (15-60 s): Consumer fetches the full document, runs the ingestion pipeline (text extraction, chunking, embedding generation), and writes to the vector index. Use `doc_id` as the idempotent key — reprocessing the same document ID converges to the correct state.

4. **Index writer** (1-5 s): Delete stale chunks (`DELETE WHERE doc_id = X`), insert new chunks. Wrap in a transaction where the vector DB supports it; otherwise, soft-delete stale chunks first (mark `status=stale`), then insert new chunks, then hard-delete stale.

5. **Deletion handler** (same pipeline): When `event_type == deleted`, retrieve all chunk IDs with `doc_id = X` from the chunk-to-source mapping table, delete them from the vector index, then delete the mapping record.

**Latency budget:** Webhook delivery 1-10 s + queue wait 1-5 s + embedding generation 10-40 s + index write 1-5 s = **13-60 s total** — well within 3 minutes.

**Failure modes and mitigations:**

| Failure | Impact | Mitigation |
|---|---|---|
| Webhook not delivered | Event lost; doc not re-indexed | Supplemental batch reconciliation job (hourly diff between source and index) |
| Embedding API timeout | Event stuck in queue | Retry with exponential backoff; DLQ after 5 failures; alert on DLQ depth |
| Vector DB write fails | Stale index | Soft-delete + transactional write; idempotent retry safe |
| Out-of-order events (update received before create) | Incorrect state | Idempotent processing by doc_id; last-write-wins semantics |
| Document deleted from source but event missed | Zombie chunks in index | Periodic full reconciliation: scan index for chunks whose `source_url` returns 404 |

> **Common Mistake:** Building the happy path only and assuming events are delivered exactly once in order. Real-world event systems deliver events at-least-once and occasionally out of order. Idempotent processing with a last-write-wins key is mandatory, not optional.

## Adapter Layer Design: Extending Pipelines Without Touching the Core

One of the most common enterprise integration patterns is the need to add AI capabilities to an existing data pipeline without refactoring the core system. The failure mode: modifying the core pipeline directly, introducing AI-specific failure modes into a system that was previously stable.

The correct pattern is the **adapter layer**: a thin translation and orchestration component that sits between the existing pipeline and the AI system, translating data formats in both directions without requiring changes to either.

### The Adapter Pattern

```python
# adapter.py — wraps the AI extraction system for an existing pipeline
from dataclasses import dataclass
from typing import Optional
import json

@dataclass
class LegacyDocument:
    """Format the existing pipeline produces."""
    document_id: str
    raw_text: str
    source_system: str
    metadata: dict

@dataclass
class EnrichedDocument:
    """Format the downstream system expects."""
    document_id: str
    raw_text: str
    source_system: str
    metadata: dict
    # New AI-extracted fields — defaulted so existing consumers are unaffected
    extracted_entities: list[dict] = None
    confidence_score: float = None
    extraction_status: str = "pending"  # pending | success | failed | skipped

class AIExtractionAdapter:
    """
    Adapter layer: wraps AI extraction so the core pipeline never changes.
    Transforms LegacyDocument → EnrichedDocument.
    If AI extraction fails, returns the document with extraction_status=failed
    rather than raising — never lets AI failure break the core pipeline.
    """

    def __init__(self, extractor, confidence_threshold: float = 0.75):
        self.extractor = extractor
        self.confidence_threshold = confidence_threshold

    def enrich(self, doc: LegacyDocument) -> EnrichedDocument:
        enriched = EnrichedDocument(
            document_id=doc.document_id,
            raw_text=doc.raw_text,
            source_system=doc.source_system,
            metadata=doc.metadata,
        )
        try:
            result = self.extractor.extract(doc.raw_text)
            enriched.extracted_entities = result.entities
            enriched.confidence_score = result.confidence
            enriched.extraction_status = (
                "success" if result.confidence >= self.confidence_threshold
                else "low_confidence"
            )
        except Exception as e:
            # AI failure is never a pipeline failure
            enriched.extraction_status = "failed"
            enriched.metadata["extraction_error"] = str(e)
        return enriched

# Production Gotcha: The adapter must never raise. Any exception from the AI
# system is caught here and recorded in the extraction_status field.
# Downstream consumers check extraction_status before using AI fields.
```

### When to Use the Adapter Pattern

- **Adding AI enrichment to an existing ETL pipeline:** The adapter runs as a parallel step after ingestion but before storage; the storage layer receives an enriched document with nullable AI fields.
- **Gradual migration:** Run the adapter in "shadow mode" first (enrich but don't write AI fields to the live system). Compare results against manual annotation before activating.
- **Multi-vendor AI:** If you want to swap AI providers (or run multiple), the adapter normalizes the output format so downstream consumers are provider-agnostic.

## Rules vs. ML vs. LLM Decision Framework

Every component in an enterprise AI pipeline has a decision point: should this component be a rule, an ML model, or an LLM call? Getting this wrong wastes money, reduces reliability, and creates brittle systems.

```
DECISION FRAMEWORK FOR COMPONENT TYPE

IF the logic is deterministic and exhaustively listable:
    → Use a rule (regex, lookup table, conditional)
    Examples: format validation, field extraction from structured data,
              routing by document type when document type is reliably detectable

IF the logic requires pattern recognition from labeled examples
   AND training data exists (≥1000 labeled examples)
   AND output is a fixed set of classes or a numeric value:
    → Use a trained ML model (GBT, logistic regression, neural classifier)
    Examples: document priority scoring, spam/not-spam, category classification
              when categories are predefined

IF the logic requires semantic understanding or generation
   AND the output space cannot be fully enumerated
   AND accuracy on edge cases matters more than latency/cost:
    → Use an LLM
    Examples: free-text extraction with semantic understanding,
              summarization, Q&A over documents, anomaly explanation

IF you are unsure:
    → Start with rules, measure where rules fail, train ML for those cases
    → Only introduce LLM where ML accuracy ceiling is insufficient
```

| Component Type | Latency | Cost | Determinism | When to Use |
|---|---|---|---|---|
| Rule / Regex | < 1 ms | ~\$0 | 100% | Fixed format, enumerable logic |
| Trained ML model | 1–100 ms | Low | High | Labeled data exists, fixed output space |
| LLM (small/fast) | 200–800 ms | Low-Med | Low | Semantic understanding, short output |
| LLM (large) | 1–10 s | High | Low | Complex reasoning, long generation |

**The layered approach:** Build the cheapest component that works for the majority case; use the expensive component only for the cases the cheap one fails. A document classifier that handles 70% of cases with a rule (document type is in the filename) and 25% with a GBT model (document type from structural features) and 5% with an LLM (ambiguous documents requiring content understanding) costs a fraction of a pure-LLM approach.

## Config-Driven Output Mapping (Taxonomy Translation Pattern)

Enterprise customers have their own taxonomies, field names, and category structures. A system that hard-codes output field names or category labels becomes a custom build for every customer. The taxonomy translation pattern makes the mapping customer-configurable without code changes.

```python
# taxonomy_mapper.py
from typing import Any
import json

class TaxonomyMapper:
    """
    Maps from canonical AI output schema to customer-specific schema.
    Configuration is loaded from a per-customer config file — no code changes
    required to support a new customer's taxonomy.
    """

    def __init__(self, config_path: str):
        with open(config_path) as f:
            config = json.load(f)
        self.field_mapping = config.get("field_mapping", {})
        self.category_mapping = config.get("category_mapping", {})
        self.default_values = config.get("default_values", {})

    def translate(self, canonical_output: dict) -> dict:
        """Translate canonical schema to customer schema."""
        result = {}
        for canonical_field, value in canonical_output.items():
            # Map field name
            customer_field = self.field_mapping.get(canonical_field, canonical_field)
            # Map categorical value if applicable
            if canonical_field in self.category_mapping:
                value = self.category_mapping[canonical_field].get(value, value)
            result[customer_field] = value

        # Apply defaults for fields not present in canonical output
        for field, default in self.default_values.items():
            if field not in result:
                result[field] = default

        return result

# Customer config example (stored per-customer, not in code):
EXAMPLE_CONFIG = {
    "field_mapping": {
        "document_type": "doc_category",    # canonical → customer field name
        "confidence_score": "ai_confidence",
        "extracted_date": "proc_date"
    },
    "category_mapping": {
        "document_type": {
            "invoice": "VENDOR_INVOICE",     # canonical value → customer value
            "contract": "LEGAL_CONTRACT",
            "receipt": "EXPENSE_RECEIPT"
        }
    },
    "default_values": {
        "review_status": "PENDING",
        "source_system": "AI_EXTRACTION"
    }
}
```

**Why this matters:** A customer taxonomy change (renaming "invoice" to "VENDOR_INVOICE") is a config file edit, not a code deployment. Multiple customers can share the same AI system with completely different output formats. Onboarding a new customer is a config authoring exercise, not an engineering sprint.

## Human-in-the-Loop Review Queues

Not every AI output should be served directly to downstream systems. For high-stakes extractions (compliance documents, medical records, financial instruments) or low-confidence outputs, a human review step before final ingestion is essential.

```python
# review_queue.py — route low-confidence extractions to human review
from dataclasses import dataclass, field
from enum import Enum
from datetime import datetime
import uuid

class ReviewStatus(Enum):
    PENDING = "pending"
    APPROVED = "approved"
    REJECTED = "rejected"
    EDITED = "edited"  # Human corrected and approved

@dataclass
class ReviewItem:
    item_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    document_id: str = ""
    ai_output: dict = field(default_factory=dict)
    confidence_score: float = 0.0
    reason_for_review: str = ""
    status: ReviewStatus = ReviewStatus.PENDING
    reviewer_id: str = None
    reviewed_output: dict = None  # Populated if human edits
    created_at: datetime = field(default_factory=datetime.utcnow)
    reviewed_at: datetime = None

class ReviewQueue:
    """Routes AI outputs to human review based on configurable criteria."""

    def __init__(self, storage_backend, confidence_threshold: float = 0.80):
        self.storage = storage_backend
        self.confidence_threshold = confidence_threshold

    def should_review(self, result) -> tuple[bool, str]:
        """Determine if an extraction result needs human review."""
        if result.confidence_score < self.confidence_threshold:
            return True, f"Low confidence: {result.confidence_score:.2f}"
        if result.has_conflicting_fields():
            return True, "Conflicting extracted fields"
        if result.document_type in self.high_stakes_types:
            return True, "High-stakes document type requires review"
        return False, ""

    def enqueue(self, document_id: str, ai_output: dict,
                confidence_score: float, reason: str) -> ReviewItem:
        item = ReviewItem(
            document_id=document_id,
            ai_output=ai_output,
            confidence_score=confidence_score,
            reason_for_review=reason
        )
        self.storage.save(item)
        return item

    def approve(self, item_id: str, reviewer_id: str,
                edited_output: dict = None) -> ReviewItem:
        item = self.storage.get(item_id)
        item.status = ReviewStatus.APPROVED if not edited_output else ReviewStatus.EDITED
        item.reviewer_id = reviewer_id
        item.reviewed_output = edited_output or item.ai_output
        item.reviewed_at = datetime.utcnow()
        self.storage.save(item)
        return item

# Integration pattern:
# AI extraction → review check → if low confidence → enqueue for human review
#                                                   → hold downstream pipeline
# Human approves/edits → downstream pipeline resumes with approved output
# SLA alerting: flag items in PENDING status > N hours to prevent bottleneck
```

**SLA management for review queues:** Every item in the review queue needs a deadline. An item that sits in PENDING for 72 hours while the downstream process waits is a production SLA violation. Implement: age-based alerts, daily queue depth reports to the customer's operations team, and an escalation path for items approaching SLA.

## Data Pipeline Design for Multi-Format Inputs

Enterprise data arrives in every format: email bodies, PDF attachments, CSV exports, API payloads, scanned images, Excel files. A pipeline that handles each format independently becomes unmaintainable. The canonical approach is a **format-agnostic ingestion layer** that normalizes all inputs to a canonical intermediate format before any AI processing.

```python
# ingestion_layer.py — normalize multi-format inputs to canonical text
from pathlib import Path
import mimetypes

class DocumentIngestionPipeline:
    """
    Multi-format ingestion pipeline.
    Normalizes all document types to (text, metadata) pairs.
    """

    def __init__(self):
        self.extractors = {
            "application/pdf": self._extract_pdf,
            "text/plain": self._extract_text,
            "text/html": self._extract_html,
            "application/vnd.openxmlformats-officedocument.wordprocessingml.document":
                self._extract_docx,
            "text/csv": self._extract_csv,
            "message/rfc822": self._extract_email,
        }

    def ingest(self, source: str | bytes,
               mime_type: str = None,
               metadata: dict = None) -> dict:
        """
        Returns canonical document dict:
        {text, pages, source_type, metadata, extraction_quality}
        """
        if mime_type is None:
            mime_type = self._detect_mime_type(source)

        extractor = self.extractors.get(mime_type)
        if extractor is None:
            return {"text": "", "extraction_quality": "unsupported",
                    "source_type": mime_type, "metadata": metadata or {}}

        try:
            text, doc_metadata = extractor(source)
            return {
                "text": text,
                "extraction_quality": self._assess_quality(text),
                "source_type": mime_type,
                "metadata": {**(metadata or {}), **doc_metadata}
            }
        except Exception as e:
            return {
                "text": "",
                "extraction_quality": "failed",
                "source_type": mime_type,
                "error": str(e),
                "metadata": metadata or {}
            }

    def _assess_quality(self, text: str) -> str:
        """Heuristic quality check on extracted text."""
        if not text or len(text) < 50:
            return "empty"
        # Heuristic: high ratio of non-ASCII chars often indicates OCR artifacts
        non_ascii = sum(1 for c in text if ord(c) > 127)
        if non_ascii / len(text) > 0.3:
            return "degraded"
        return "good"

    def _extract_pdf(self, source) -> tuple[str, dict]:
        import pdfplumber
        text_parts = []
        with pdfplumber.open(source) as pdf:
            for page in pdf.pages:
                text_parts.append(page.extract_text() or "")
        return "\n\n".join(text_parts), {"page_count": len(pdf.pages)}

    def _extract_email(self, source) -> tuple[str, dict]:
        import email
        msg = email.message_from_bytes(source if isinstance(source, bytes)
                                       else source.encode())
        parts = []
        if msg.is_multipart():
            for part in msg.walk():
                if part.get_content_type() == "text/plain":
                    parts.append(part.get_payload(decode=True).decode(errors="replace"))
        else:
            parts.append(msg.get_payload(decode=True).decode(errors="replace"))
        return "\n".join(parts), {
            "from": msg.get("From", ""),
            "subject": msg.get("Subject", ""),
            "date": msg.get("Date", "")
        }

# Production Gotcha: PDF extraction quality varies drastically by PDF type.
# Digitally-native PDFs extract cleanly. Scanned PDFs may need OCR (Tesseract,
# AWS Textract, or similar). Always log extraction_quality and alert on high
# rates of "degraded" or "empty" — these indicate upstream data quality issues.
```

## Idempotency Patterns for Submission and Event Ingestion

When a document submission event is processed more than once — due to network retry, queue redelivery, or system restart — the result must be the same as if it had been processed once. Without idempotency, retries cause duplicate records, doubled charges, and inconsistent state.

```python
# idempotency.py — idempotent event processing
import hashlib
import time
from typing import Optional

class IdempotencyStore:
    """Tracks processed event IDs to prevent duplicate processing."""

    def __init__(self, redis_client, ttl_seconds: int = 86400 * 7):
        self.redis = redis_client
        self.ttl = ttl_seconds
        self.key_prefix = "idempotency:"

    def _make_key(self, idempotency_key: str) -> str:
        return f"{self.key_prefix}{idempotency_key}"

    def is_already_processed(self, idempotency_key: str) -> bool:
        return self.redis.exists(self._make_key(idempotency_key)) == 1

    def mark_processing(self, idempotency_key: str) -> bool:
        """
        Atomically set if not exists. Returns True if this process
        acquired the lock, False if another process is already handling it.
        """
        key = self._make_key(idempotency_key)
        # SET NX: only set if key doesn't exist (atomic)
        result = self.redis.set(key, "processing", nx=True, ex=300)  # 5 min lock
        return result is not None

    def mark_complete(self, idempotency_key: str, result_summary: str = ""):
        """Mark as permanently processed with result."""
        key = self._make_key(idempotency_key)
        self.redis.set(key, f"done:{result_summary}", ex=self.ttl)


def make_idempotency_key(doc_id: str, event_type: str, version: str) -> str:
    """Create a deterministic idempotency key from event fields."""
    payload = f"{doc_id}:{event_type}:{version}"
    return hashlib.sha256(payload.encode()).hexdigest()[:32]


class IdempotentEventProcessor:
    """Wraps event processing with idempotency guarantee."""

    def __init__(self, processor_fn, idempotency_store: IdempotencyStore):
        self.process = processor_fn
        self.store = idempotency_store

    def handle(self, event: dict) -> dict:
        idem_key = make_idempotency_key(
            event["doc_id"], event["event_type"], event.get("version", "")
        )

        # Already processed — return early
        if self.store.is_already_processed(idem_key):
            return {"status": "already_processed", "idempotency_key": idem_key}

        # Acquire processing lock
        if not self.store.mark_processing(idem_key):
            return {"status": "being_processed", "idempotency_key": idem_key}

        try:
            result = self.process(event)
            self.store.mark_complete(idem_key, result.get("summary", ""))
            return {"status": "processed", "result": result}
        except Exception as e:
            # Do not mark complete on failure — allow retry
            raise

# Production Gotcha: The idempotency store itself can fail (Redis down).
# When Redis is unavailable, the safest fallback is to process anyway
# (accept occasional duplicates) rather than block all processing.
# Log a warning and proceed — duplicate detection is best-effort.
# The alternative (blocking all events when Redis is down) causes total
# pipeline failure, which is much worse than occasional duplicates.
```

**The Redis-down fallback question** comes up in interviews: if your idempotency check depends on Redis, and Redis goes down, what do you do? The answer is: process anyway with a log warning. Occasional duplicate processing is recoverable (downstream deduplication, idempotent downstream writes). A complete pipeline halt while Redis recovers is not recoverable in many SLA contexts.
